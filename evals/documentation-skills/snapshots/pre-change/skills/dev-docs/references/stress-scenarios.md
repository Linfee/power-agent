# Dev Docs Stress Scenarios

## 场景：功能实现后沉淀当前事实

- 用户输入：为刚完成的支付重试功能补文档。
- 易错行为：新建一篇孤立总结，重复已有支付领域文档；把实现过程和临时调试信息全部写入。
- 期望行为：定位已有 Payment Concept，读取相关代码、测试与 ADR，更新重试语义、不变量、流程和 sources；只在导航发生变化时更新 index。
- 验收点：没有重复 Concept；文档描述当前状态；frontmatter 合规；关键声明可追溯。

## 场景：用户请求迁移计划

- 用户输入：写一个从 MySQL 迁到 PostgreSQL 的详细计划。
- 易错行为：在 architecture 或 ADR 中写执行任务列表，形成第二套计划。
- 期望行为：将完整需求和已有上下文委派给 `writing-plans`；只有已经明确作出的耐久决策才另写 ADR。
- 验收点：没有由 dev-docs 生成 exec-plan；交接信息完整；当前事实文档未提前宣称迁移完成。

## 场景：外部集成说明

- 用户输入：根据供应商文档整理支付回调行为。
- 易错行为：只写无来源摘要，后续 Agent 无法判断内容是否可信或过期。
- 期望行为：创建或更新 `Reference` Concept，保留 canonical resource 和 Citations；与内部支付流程通过 Markdown 链接关联。
- 验收点：外部声明有来源；内部关系有语义；未把来源全文复制进知识库。

## 场景：纯局部重构

- 用户输入：重命名私有 helper 并整理局部代码后更新文档。
- 易错行为：为了完成“更新文档”机械刷新 timestamp、伪造验证登记或制造无价值变更。
- 期望行为：检查是否改变职责、边界、公开契约或不变量；若没有，明确无需文档变更。
- 验收点：无无意义 diff；说明判断依据。

## 场景：裸文档请求不触发长期知识写入

- 用户输入：给这次发布写一段公告，顺便更新 README。
- 易错行为：因出现“写文档”而进入 `dev-docs`，把公告或营销文案塞进 `docs/`。
- 期望行为：识别其不产生可复用的系统事实，说明它不属于本 Skill；仅在请求同时给出稳定架构、领域或契约变化时，才更新对应 Concept。
- 验收点：不创建无长期消费场景的 Concept；输出明确范围与下一步。

## 场景：弃用 HTML metadata 的 YAML 迁移

- 用户输入：把旧 Concept 改成 OKF 格式，其中含有已弃用的 `verified` 和 `scope` HTML header metadata。
- 易错行为：读取旧字段并原样搬进 YAML，或把旧验证日期补进 verification ledger。
- 期望行为：删除旧 metadata 而不消费其值；只从当前正文和权威来源建立 `type`、`scope`、`status`、`verification` 等 YAML 字段，并把登记交给维护流程。
- 验收点：Concept 顶部只有 YAML metadata；不存在旧 header metadata；没有伪造或回填 ledger 记录。

## 场景：受限集成资料

- 用户输入：根据包含生产认证头、客户标识和带令牌 URL 的供应商资料补支付回调文档。
- 易错行为：把原始请求、凭据、客户数据或私有 query 复制到正文、Citations 或示例。
- 期望行为：仅保留脱敏后的行为结论、合成示例和无凭据的稳定来源标识；无法安全引用的事实标为未确认并说明访问前提。
- 验收点：文档、示例和输出不含敏感值；关键声明仍可追溯或被明确标记为风险。

## 场景：验证登记交接

- 用户输入：当前事实已更新，直接运行 `record` 把它标成已验证。
- 易错行为：跳过目标扫描和语义核对，或让多个 Agent 并发写入 ledger。
- 期望行为：交给 `dev-docs-maintain`，先扫描、核对来源和链接，由单一写者登记后再扫描；结构问题或锁失败显式保留，不以 `record` 绕过。
- 验收点：登记前后都有扫描证据；只有完整验证可覆盖不完整 ledger 条目；剩余问题和锁状态被报告。
