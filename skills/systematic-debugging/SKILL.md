# 系统化调试

随机修复浪费时间并制造新 bug。快速补丁掩盖底层问题。

**铁律：**
```
没有根本原因调查就没有修复
```

---

## 环境健康检查（调试开始前）

在进入阶段 1 之前：

1. 确认当前代码能编译 / 能运行基本测试套件
2. 若基础测试已有失败（非目标 bug 引起）→ 记录这些已知问题，与目标 bug 区分，避免干扰根因判断
3. 若无法编译 → 先修复编译错误再开始调试

**目的：** 确保调试环境基线健康，防止在已有故障干扰下误判根因。

---

## 四个阶段（必须按顺序完成）

### 阶段 1：根本原因调查

**在尝试任何修复之前：**

1. **仔细读错误信息** — 完整阅读，包括堆栈跟踪、行号、文件路径
2. **稳定复现** — 确认能可靠触发；不可复现 → 收集更多数据，不要猜测
3. **检查最近变更** — git diff、最近提交、新依赖、配置变更
4. **多组件系统：添加诊断** — 在每个组件边界记录输入/输出，一次运行收集证据，再分析是哪层出问题
5. **追踪数据流** — 坏值从哪里产生？向上追踪调用栈直到源头。见 `<systematic-debugging-path>/root-cause-tracing.md`

### 阶段 2：模式分析

1. 找到同一代码库中类似的**正常工作**代码
2. 完整阅读参考实现，不要只浏览
3. 列出工作代码和损坏代码之间的**每个差异**，无论多小
4. 理解依赖：需要什么配置、环境、外部组件？

### 阶段 3：假设与测试

1. **形成单一假设**："我认为 X 是根本原因，因为 Y" — 写下来，要具体
2. **最小化测试**：做尽可能小的变更验证假设，一次一个变量
3. 假设验证 → 进入阶段 4；假设失败 → 形成新假设，不要叠加修复

### 阶段 4：实现修复

1. **先写失败测试**（使用 `test-driven-development` skill）— 修复前必须有
2. **实现单一修复** — 解决根本原因，不捆绑重构，不"顺手改"其他
3. **验证**（使用 `verification-before-completion` skill）— 测试通过？无回归？

**如果修复不起作用：**
- < 3 次 → 返回阶段 1，用新信息重新分析
- ≥ 3 次 → **停止，质疑架构**（见下文）

**3+ 次修复失败时 — 质疑架构：**
每次修复在不同地方揭示新问题、修复需要大规模重构、每次修复产生新症状 → 这是架构问题，不是 bug。与用户讨论是否重构，不要继续修复症状。

## 支撑技术（本目录中可用）

- `root-cause-tracing.md` — 向后追踪调用栈定位原始触发器
- `defense-in-depth.md` — 找到根本原因后在多层添加验证
- `condition-based-waiting.md` + `condition-based-waiting-example.ts` — 用条件轮询替换任意超时
- `find-polluter.sh` — 定位测试污染来源

## 危险信号 — 停止，回到阶段 1

- "暂时快速修复，稍后调查"
- "试试改 X 看看"
- "同时改多个地方"
- "我不完全理解但这可能有效"
- **"再试一次修复"（已尝试 2+ 次）**
- **每次修复在不同地方揭示新问题**

## 快速参考

| 阶段 | 核心动作 | 完成标准 |
|------|---------|---------|
| 1. 根本原因 | 读错误、复现、检查变更、收集证据 | 理解什么坏了以及为什么 |
| 2. 模式 | 找工作示例、对比差异 | 识别具体差异 |
| 3. 假设 | 形成理论、最小化测试 | 假设确认或证伪 |
| 4. 实现 | 写测试、修复、验证 | Bug 解决，测试通过 |

---

## 常见合理化借口

| 借口 | 现实 |
|------|------|
| "问题简单，不需要走流程" | 简单 bug 也有根本原因，走流程反而更快 |
| "紧急，没时间" | 系统化比随机折腾快得多 |
| "先改这个试试，再调查" | 第一次修复设定了随机猜测的模式 |
| "再试一次修复"（2+ 次失败后） | 3+ 次失败 = 架构问题，不是 bug |

## Eval 数据收集（调试完成后）

调试成功结束时，将以下指标写入调用方的 exec-plan 或当前上下文：

```
<!-- eval: YYYY-MM-DD -->
<!-- skill: systematic-debugging -->
<!-- skill-version: 1.0.0 -->
- 假设验证轮数: N 轮（每次进入阶段 3 计 1 轮）
- 修复尝试次数: N 次
- 是否升级为架构问题: Y/N
```

向用户提问：
> 快速反馈：
> 1. 调试效果？ [满意 / 一般 / 不满意]
> 2. 备注？（可选，直接回车跳过）

用户跳过时标注 `feedback: skipped`，不阻塞主流程。
