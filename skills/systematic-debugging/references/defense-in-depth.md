# 边界防护与不变量

永久修复解决产生偏离的原因，额外防护服务具有独立责任的边界。数据经过某层，不代表该层应该重复校验。事故缓解的顺序由当前影响、风险与授权决定。

## Ownership test

考虑增加防护时，判断：

- 这一层是否拥有被保护的不变量，或位于信任、安全、不可逆操作边界？
- 它能否阻断其它边界无法捕获的独立失败模式，并给出更准确的处置？
- 防护是否会重复上游契约、制造分支漂移或掩盖根因？
- 类型、状态机、权限模型或单一 API 入口能否以更简单的方式约束非法状态？

没有独立责任时，保留单一权威校验点。

## 设计原则

### 区分永久修复与事故缓解

永久修复应消除产生错误状态的原因。任务包含事故止损且动作已获授权时，可以先限制影响、启用可控降级或采取其他有依据的缓解，再继续根因调查。验证缓解是否控制了当前影响及其副作用，记录剩余风险和后续修复；缓解成功不等于根因已修复。下游 fallback 或重复空值检查不能充当根因修复的证据。

### 结构性约束优先

优先用类型、构造边界、状态机、权限模型或 API 契约表达不变量，再考虑分散的运行时守卫。

### 安全边界不可弱化

防护不能绕过或改变既有安全语义。涉及权限、敏感数据、生产或破坏性操作时，遵守主 Skill 和项目授权规则；缺少授权则 `BLOCKED`。

### 观测不是防护

日志和 trace 用于观察，不等于防止错误。临时 instrumentation 只记录区分当前解释所需的信息，脱敏并控制影响；清理运行中的探针与保留复验材料按主 Skill 判断。长期观测能力须有独立运维价值与对应授权。

### 验证真实契约

验证应证明边界不变量和可观察行为，而不是仅证明某个 `if` 存在。若合法路径能绕过防护，重新检查所有权和 API 设计，不要继续堆叠检查。
