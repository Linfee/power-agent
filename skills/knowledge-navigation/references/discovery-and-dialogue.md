# 从项目观察到启发式讨论

本页用于首次建立导航，或已有体系需要重新界定目标与组织边界时。问题来自观察，不是固定问卷；每次只推进影响当前决定的少量取舍。

## 观察到足以提出好问题

先辨认实际仓库边界与入口加载关系。查看根说明、已有索引、构建/测试入口、关键模块和代表性文档；只在任务需要时展开子仓、历史或外部来源。记录哪些是可核对事实，哪些还只是目录名产生的猜测。

关注会改变设计的差异：单仓或多仓、主要任务类型、读者是否熟悉领域、代码与运行环境是否一致、长期事实散落在哪里、已有工具能检查什么。无需为每个维度产出报告。

用一个现有任务尝试定位：能否选择入口、到达相关知识、判定来源和版本？把实际断点带入讨论。入口文件存在并不证明宿主加载它，普通 Markdown 引用也不等于被自动注入。

## 用实例引出需求

围绕“观察 → 影响 → 可选择的做法 → 推荐理由”提问。示例是提问方式，不是每次必问的题目：

| 观察 | 启发式问题示例 | 回答改变什么 |
|---|---|---|
| 代码按服务分目录，故障却跨服务传播 | “最近最费定位时间的一类任务是什么？如果主要沿业务链路排查，我建议首页按问题进入，服务目录保留作参考。” | 任务入口和模块入口的优先级 |
| README 描述历史部署，运行环境另有记录 | “运行态结论以哪一处受控记录为准？当前 README 是否应标为历史说明并指向它？” | 权威位置与历史适用范围 |
| 用户已经给出明确文件，Agent 仍通读总览 | “这类任务是否直接从文件及相关契约进入？总览可以留给归属不明的任务。” | 直达路径和必读负担 |
| 同一事实出现在多篇文档中 | “未来谁负责更新这项事实？我建议保留其所在模块的正文，其余页面只维护摘要与引用。” | 正文所有权与更新成本 |
| 团队愿意维护知识，但没有文档检查工具 | “目前更需要修正断链，还是跟踪来源变化？可以先复用现有校验，按实际漂移再扩展。” | 机械化范围与维护投入 |

用户反馈“经常找错”“文档太多”时，追问一个可定位案例、期望行为和实际影响。用户无需记得完整路径；现有会话或仓库可以补足证据。将明确偏好与事实结论分开记录。

## 讨论如何收敛

可以据以实施的结论应让 Agent 知道：优先支持哪些任务、哪些约束保留、事实归谁维护、本轮改变哪些入口、什么结果可以验收。表达可以是几句话、现有 issue 或设计文档，不创建专用交接 schema。

可逆选择由已知目标和证据决定；用户已明确指定目录、语言、工具或保留边界时遵循它们。关键未知确实改变权威位置、迁移范围或风险时，解释取舍并等待该答案。用户暂未回答不表示同意。

讨论结果应进入实际修改：例如把已选择的任务分类写入入口，把权威来源写到相关知识附近。只有决定有跨轮恢复或长期复用价值时才持久保存理由；原始问答无需整段复制进知识库。

## 初始化的最小形状

沿用宿主实际发现的入口，用短摘要路由到已有知识；缺少独立导航且文档规模需要时再增加索引。优先补齐影响代表性任务的来源、范围、术语或操作契约，目录随内容建立。

知识较少时，一个入口加少量文档可以足够；知识较多时，任务导航、专题索引和横向链接可以共同存在。以真实消费路径判断是否需要下一层，不按照模板补全 docs、wiki、CONTEXT、ADR 或 Skill 目录。
