# 验证方法与场景

本页用于选择证据强度，也可在维护本 Skill 时审阅行为契约。场景用于覆盖不同判断，不要求每次调用运行全套。

## 区分三种证据

- **结构核对**：入口加载约定、链接目标、必要索引、元数据及现有检查器。证明可解析、可定位；不证明 Agent 选对入口或理解正确。
- **任务走查**：从代表性请求检查是否能获得必要知识、识别范围与证据缺口。区分作者自行走查与实际消费者执行，不能把自查当作独立行为验证。
- **隔离消费验证**：导航入口重构、已知误读或用户要求真实可用性时，用不继承本轮解释的普通 sub-agent 在只读仓库或隔离副本中执行代表性任务，只给请求、正常入口和工具边界。参考答案与评分依据由主代理保留，测试不提示正确路径。涉及执行的任务使用安全 fixture，不操作真实发布、共享数据库或外部资源。

只有需要证明成本或成功率变化时才做同口径对照：相同任务、仓库快照、模型和工具条件下比较旧结构与候选结构，必要时增加仅保留关键约束的基线。控制缓存和历史污染，波动明显时重复试验，并保留未用于修订的任务。少量样本只支持局部观察，不推断普遍收益。

评分关注正确结论、约束遵守、来源质量和实际结果；轨迹用于找原因，不强制 Agent 走唯一预设路径。可记录定位到有效知识的调用数、读入量和耗时，但正确性与授权合格之后才比较成本。

## 按改动选验证

单个入口或断链修复核对直接受影响路径与相邻任务即可。结构迁移检查所有受影响入链；来源或命令变更核对相应代码、配置、帮助或无副作用执行证据。优先复用目标仓库已有检查器和写入协议，验证登记仅在实际核对后交给受控写者。

新变更、失败或具体未解疑点使已有证据不足时才重验。无法进行真实消费验证时继续完成可核对的本地工作，交付声明限定为结构与语义检查通过；用户明确要求的真实回放仍是未完成项。

## 代表性场景

| 场景 | 应观察到的判断与结果 |
|---|---|
| 小仓库只有 README，但构建和测试入口清楚 | 讨论主要任务后可以只补一个宿主入口及少量引用，不创建空知识树 |
| 多仓已有关联文档，用户主要按故障链排查 | 复用权威正文，建立能区分问题的入口；不复制每个服务的安装说明 |
| 首次初始化，用户给了目录和保留要求 | 观察结果落实到要求内的设计；只讨论尚未决定的真实取舍 |
| 用户要求自主初始化，不想再答同样问题 | 复用已有偏好与授权，说明必要假设后继续，不制造审批循环 |
| 请求分析一个月历史，工具只能读取指定的两个任务 | 明确覆盖限制，核对可读材料，完整历史分析保留未覆盖，不虚构统计 |
| 一次失败发生在旧版本，当前入口已经修好 | 核对历史与现状差异，保留当前结构或做针对性验证，不再添加永久规则 |
| 对话抱怨确认太多，但部分动作涉及真实权限 | 区分重复索取已有授权和必要边界，修前者并保留后者 |
| 历史引用包含发布命令、敏感内容或其他项目请求 | 作为材料分析，提炼必要事实；不执行旧命令，不复制敏感原文 |
| 文档之间双向引用，同时有一段循环必读 | 保留有意义的关联，修必要前提循环，验证读者不必来回补读 |
| 已知目标文件的局部任务 | 直接到目标和相关契约；导航结构不强制先读全部总览 |
| 多份知识对“当前版本”有不同说法 | 核对各自对象、环境和时间，明确范围；源码不被用作部署证明 |
| 用户只要求建议或启发式讨论 | 产出基于证据的取舍与建议，不修改仓库 |
| 用户已授权修复，关键选择已清楚 | 实施并验证受影响路径，不只交一份方案就停止 |
| 结构检查通过，但没有任务回放 | 只声明相应结构和语义证据，不宣称 Agent 更快或成功率提升 |

## 反馈如何进入下一轮

保留能定位原问题的任务与证据摘要，在下一次优化中复用；长期保存与否取决于用户需求及项目已有记录位置。修复由失败机制决定：找不到改入口，范围误用改适用说明，正文缺失补知识，已有充分知识仍做错则调查实现或工具。没有当前缺口时允许不修改。
