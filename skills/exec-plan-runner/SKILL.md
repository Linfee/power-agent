# Exec-Plan Runner

自主执行 exec-plan，最大化并行度，持续更新进度。

**核心理念：** 主代理只做规划、编排、协调——**绝不自己写代码**。所有实现由子代理完成。子代理是一次性的，主代理不重复和同一子代理对话，修复问题时启动新子代理。

## 整体流程

```
加载计划 → 依赖分析 → 划分 batch
    ↓
[对每个 batch]
    ├─ 并行启动实现子代理（每任务一个）
    ├─ 等待所有返回 → 处理阻塞/问题
    ├─ 并行启动代码审查子代理
    ├─ 若有问题 → 并行启动修复子代理 → 重新审查
    ├─ 更新 exec-plan 进度
    ↓
[所有 batch 完成]
    └─ 启动验证子代理 → 最终报告
```

---

## Step 1: 加载、恢复检测与分析

1. 读取 exec-plan 文件（单文件或目录中的 README.md + tasks.md）
2. 读取项目 AGENTS.md 了解代码规范和约束
3. **恢复检测：** 扫描进度标记（`[x]` / `[ ]`）和"当前状态" section
   - 有已完成任务 → 进入**恢复模式**：验证已完成产出是否有效（启动验证子代理），从中断点继续
4. 提取所有**未完成**任务全文，构建依赖图，划分 batch

**依赖分析原则：**
- 修改同一文件的任务 → 有依赖，串行
- 上游产出是下游输入的 → 有依赖
- 操作不同模块且无数据依赖 → 可并行
- 不确定时视为有依赖（安全优先）

**Batch 划分示例：**
```
Batch 1 (并行): [Task A: 用户模型] [Task B: 权限模型] [Task C: 配置模块]
Batch 2 (并行): [Task D: 用户API (依赖A)] [Task E: 权限API (依赖B)]
Batch 3 (串行): [Task F: 集成测试 (依赖D,E)]
```

若 exec-plan 有关键缺陷（任务模糊、缺少验收标准、存在矛盾）→ 向用户提出问题，不盲目开始。

---

## Step 2: 逐批执行

### 2a. 并行启动实现子代理

batch 内无依赖的任务**同时启动**，每个任务一个子代理（如果用户约定了最大并行度，不要超过它）。

**为每个实现子代理组装完整上下文包：**

```
Task 工具：
  description: "Implement [Task Name]"
  prompt: |
    你是一个实现工程师。**你必须使用 test-driven-development skill** 完成所有实现。

    ## 整体背景
    [exec-plan 摘要：目标、架构、技术栈]
    当前执行阶段：Batch N / 共 M 个 batch
    本任务在计划中的位置：[任务编号和名称]

    ## 你的任务（完整内容）
    [任务全文，包含 TDD 步骤、文件路径、代码片段、命令]

    ## 关键上下文
    [来自 AGENTS.md 的代码规范]
    [相关文件路径和关键代码片段]
    [测试运行命令]

    ## 要求
    - 严格遵循 TDD（先写失败测试，再实现，再验证通过）
    - 实现后运行全量测试，确认无回归
    - Commit 所有变更
    - 不要修改本任务范围之外的代码

    ## 报告格式
    完成后报告：
    - 状态：DONE | DONE_WITH_CONCERNS | BLOCKED
    - 创建/修改的文件列表
    - 测试结果摘要
    - 若 DONE_WITH_CONCERNS：描述疑虑
    - 若 BLOCKED：描述阻塞原因
```

**子代理状态处理：**

| 状态                 | 处理方式                                                                                                   |
| -------------------- | ---------------------------------------------------------------------------------------------------------- |
| `DONE`               | 进入代码审查                                                                                               |
| `DONE_WITH_CONCERNS` | 评估疑虑：若影响正确性，先解决再审查；若是观察性的，记录后进入审查                                         |
| `BLOCKED`            | 分析原因：上下文不足 → 启动新子代理补充上下文重试；任务太大 → 拆分后重新启动；计划有问题 → Escalate 给用户 |

**注意：** 子代理是一次性的。若需修复，启动**新子代理**，提供具体指令和额外上下文，不要尝试重联旧子代理。

### 2b. 并行启动代码审查子代理

所有实现子代理返回 DONE 后，并行启动审查子代理（可一任务一个，或一批一个）：

```
Task 工具：
  description: "Code review [Task Name]"
  prompt: |
    你是一个代码审查员。使用 receiving-code-review skill 进行评估。

    ## 审查范围
    [任务名称和实现目标]

    ## 对应规格
    [任务在 exec-plan 中的验收标准]

    ## 代码变更
    Git 命令获取 diff：
    git diff [BASE_SHA]..[HEAD_SHA]
    涉及文件：[文件列表]

    ## 审查维度
    1. 规格符合性：是否覆盖所有需求，有无过度实现
    2. 代码质量：DRY、可读性、错误处理、测试充分性

    ## 报告格式
    **规格符合性：** ✅ 通过 | ❌ 问题
    **代码质量：** ✅ 通过 | ⚠️ 建议 | ❌ 问题
    **Issues（如有）：** [具体问题 + 影响]
    **建议（Advisory）：** [非阻塞建议]
```

**审查结果处理：**
- 无阻塞问题 → 进入 Step 2c
- 有阻塞问题 → 启动**新修复子代理**（提供审查结论 + 修复指令）→ 再次启动审查子代理
- 修复循环最多 3 轮；超过则 Escalate 给用户

### 2c. 更新 Exec-Plan 进度

每个 batch 完成后立即更新：

```markdown
## 进度
- [x] Task A: 用户模型 — src/models/user.py, 测试 5/5 通过
- [x] Task B: 权限模型 — src/models/permission.py, 测试 3/3 通过
- [ ] Task D: 用户API

## 当前状态
Batch 1 完成。下一步：Batch 2，从 Task D 用户API 开始。

## 决策日志
| 日期 | 决策 | 理由 |
|------|------|------|
| YYYY-MM-DD | ... | ... |
```

## Step 3: 全量验证

所有 batch 完成后，启动专用**验证子代理**：

```
Task 工具：
  description: "Final verification"
  prompt: |
    你是一个验证工程师。使用 verification-before-completion skill。

    ## 验证目标
    [exec-plan 完成标准列表]

    ## 要运行的命令
    [lint 命令]
    [完整测试套件命令]
    [build 命令（如适用）]

    ## 报告格式
    对每个验证命令：
    - 命令：[实际运行的命令]
    - 输出摘要：[结果]
    - 结论：✅ 通过 | ❌ 失败

    最终结论：全部通过 | [N] 项失败
    失败详情：[具体错误，供主代理决策]
```

若验证失败 → 启动新修复子代理解决具体错误 → 重新启动验证子代理。

---

## Step 4: 收尾

1. 将 exec-plan 状态标记为 completed
2. 向用户报告：
   - 全部任务完成情况
   - 验证结果（带命令输出证据）
   - 实现过程中的关键决策
   - 建议：是否需要同步 docs/（architecture、domain 等）

---

## Escalation 规则（停止执行，向用户请示）

- 任务描述有歧义且多种解读工作量差异 ≥ 2x
- 需要引入 exec-plan 未预期的破坏性变更
- 修复子代理反复失败（3 轮）且无法定位根因
- exec-plan 的前提假设不成立

无需 Escalate（自主处理）：
- 实现细节选择（库函数选择、命名等）
- 可通过重试或换方向解决的临时失败
- lint 警告修复

---

## 禁止事项

- 主代理自己写代码（违反核心理念）
- 并行调度有依赖关系的任务
- 重用同一子代理（子代理是一次性的）
- 子代理未验证就声称完成
- 未更新 exec-plan 就进入下一 batch
- 修改 exec-plan 范围之外的代码

---

## 依赖 Skills（子代理应使用）

- `test-driven-development` — 实现子代理必须遵循 TDD
- `receiving-code-review` — 审查子代理评估代码的准则
- `verification-before-completion` — 验证子代理的执行标准
