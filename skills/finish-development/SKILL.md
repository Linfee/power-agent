# Finish Development

两类判断：**当前工作有没有足够的新鲜证据支持完成**，以及**当前工作怎么处置**（提交 / PR / 合并 / 保留 / 丢弃）。不实现代码、不查根因、不补任务定义——缺什么写清楚，交回调用方。

## 完成证据：什么值得判断

没有证据就没有完成。证据必须真实运行过、与本轮改动相关、且新鲜——对应当前 HEAD 或当前工作树内容。

- **证据强度与风险相称**：文档 / Skill 类改动，引用与结构检查、diff 审查即可；代码改动要目标测试或最小脚本的实际结果；UI 改动要浏览器操作与截图；bugfix 必须重跑 original repro（有 minimal 也重跑）；性能 / 稳定性要有同口径对照——功能通过不能替代非退化证据，单次绿色不能证明 flaky 已修复。
- **哪些事实改变判断**：证据范围是否盖住改动范围；证据对应当前 HEAD / 工作树还是旧状态；声称已验证却拿不出可复查的命令或路径；创建过临时产物却无处置记录；计划运行但还没跑的命令不是证据。
- **什么证据足够**：至少一条与完成声明直接相关、成功、可复查的证据。缺口明确可补时，补跑最小相关验证后可以判定完成，已接受的证据不重跑；缺口不可补时如实说明缺什么，不包装成完成。

`commit_sha`、退出码、时间只能来自真实工具输出、CI 或用户提供的可复查记录；拿不到就写 `unknown`，且不能据此声称完成。代码实现缺验证结果、bugfix 缺复现、高风险缺证明策略 → 不声称完成，写明缺口。

## 工作区状态：什么值得判断

- **验证不要求 clean 工作区**。未提交的改动同样可以验证——证据对应当前工作树内容即可，dirty 时完成声明绑定工作树而非某个旧提交。
- **只有 commit-bound 行为才要求绑定 commit**：例如"这个提交通过了验证"、基于特定 commit 的合并或交接。此时证据必须对应当前 HEAD，HEAD 变了证据就过期。
- **有未提交改动时**，处置先回答"要不要提交"：要提交则先提交，提交是外部副作用，在执行点确认；提交后回到当前状态重新判断。不提交则说明后果：无法基于 commit 交接，merge / PR 会带上前置内容或失败。

## 分支处置：什么值得判断

用户要求处置当前工作时，按实际状态判断哪些选项可行，不套固定菜单：

- **未提交改动**：提交后继续，或保持现状。
- **有提交、准备共享**：推分支 + 创建 PR，PR 说明改了什么、怎么验证的。
- **本地快速收尾**：合并到目标分支；detached HEAD 或外部管理工作区没有本地合并，说明原因。
- **延后处理**：保留分支与工作区。
- **丢弃**：永久删除分支与相关 worktree——破坏性动作，执行点确认。

推荐因上下文而异：准备共享 → PR；本地收尾 → 合并；还要继续或不确定 → 保留。选项不可行时说明原因，不硬推。

## 保护什么

- **授权在执行点**：推送远端、创建 PR、合并、丢弃、删除 worktree 都是外部副作用或破坏性动作，在真正执行的那一刻逐项确认，核对精确目标：分支、commit 范围、worktree 路径。一次性预先授权或笼统同意不替代执行点确认。
- **worktree 只清理自己创建的**：创建时记录来源；外部或来源不明的 worktree 一律不动，只报告需要人工清理。创建 PR 与保留路径保留 worktree，便于继续处理反馈。
- **完成声明与实际结果一致**：声称完成的每件事都有对应的新鲜证据；旧提交的证据不能充当前工作树的证据，计划不能当结果。
