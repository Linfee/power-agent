# Retro

从实际摩擦或项目材料出发，找出能改善 Agent 后续工作的环境变化。用户指定会话时读取可获得的原始记录；未指定时可使用当前会话。主动评估项目 Harness 时直接查看相关环境材料，无需会话日志。材料不足只限制相应结论，不阻止基于已有材料分析；需要时指出最关键的缺口。

按实际问题审视：入口与知识指针能否找到正确材料，工具和信息是否可用且成本合理，测试、lint、CI 等反馈是否能暴露错误，规则与授权边界是否有效，文档、状态或步骤是否有真实消费者。先看项目已有配置和检查；一项检查已存在但未接入或失效，与完全缺失不是同一问题。

用会话中的具体片段选择调查方向，而不是默认每类都有问题：

- **导航**：反复搜索或误入错误目录时，找出缺少的入口或隐含依赖；建议在实际加载的入口添加指向权威资料的条件指针。
- **自动检查**：发生本可自动捕获的错误时，先读项目的检查命令、CI 和 hook。区分“已有但未接入或失效”与“没有”；也可指出项目没有任何运行 lint、类型检查或测试的 guardrail，但要结合项目风险与成本，不把新增工具当成必然结论。
- **编码标准和审查**：审查遗漏后先分类。禁用 API、导入形状、目录位置等机械规则适合已有 linter、hook 或 CI；跨文件一致性、是否符合周边风格等判断，才考虑放在审查者实际读取的标准中。先确认检查是否已存在，避免重复发明。
- **常驻入口与无效指令**：入口文件过长时，找出可以放到针对性资料或自动检查中的细节；逐条识别没有改变行为的指令，以实际证据判断，而不是只因某条规则简短就删除。
- **工具成本**：一次调用返回大量无关数据、重复读取或执行昂贵命令时，寻找可缩小查询、复用结果或改善工具输出的方法。
- **信息访问**：根因因缺少日志或外部状态而无法判断时，考虑在获授权范围内提供开发服务日志、只读服务访问或其他适当信息；不要为了可观测性扩大秘密或权限暴露。

比较实施者和审查者实际拥有的上下文：实施者还要探索和调试，审查者通常从 diff 与需求出发，但也可能需要补充代码和运行环境。把规则放在真正会读取并能执行的位置，而非假设所有工作必然有独立审查者。入口优先放定位信息；长篇判断准则和参考资料可以按场景链接到已有文档。

可确定、可重复的机械错误优先建议由项目实际可运行的检查捕获，结合已有工具与接入点，不以追加提示口号替代检查。需要判断的规则才考虑文字；不因单次失误自动新增禁令，也不把未使用的机制仅因存在就判为无用。

结论关联可观察证据（如具体路径、记录、配置或运行结果），区分事实、推断和未知；按影响给出相称的改进建议与理由，不设固定评分、维度或报告格式。用户只要求评估或建议时不修改配置或实施改进；只有已有授权覆盖具体改动时才实施。需要修改 Agent 指令时按需使用 `writing-for-agents`；需要改进知识结构时按实际问题使用 `dev-docs`，知识导航设计由用户显式调用对应入口，不强制串联。
