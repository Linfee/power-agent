# To Spec

把已有讨论、issue 和项目事实整理为一个可独立消费的目标说明。先复用已确认的决定，按需查看代码、项目术语和相关决定，不重新采访已回答的问题。现有 issue 已具备清楚目标、边界和验收时，它本身就是 spec，无需复制。

写明当前问题及期望结果、范围和非目标、会改变结果的约束与已定选择，以及可观察的验收与适当的证明方式。指出仍缺的产品、权限或高风险决定，不能把猜测写成既定事实；同一句需求存在多个会改变可观察结果的合理解释时，即使改动成本低，也保留为未决并询问，不把自行选定的解释写成确定验收。只暂停受该决定阻碍的部分，独立部分继续。实现细节通常留给执行者；原型、接口或路径若准确表达已定契约，可以引用并注明来源，原型不能代替行为验收。

篇幅和形式服从消费者，不需要固定数量的 user stories、章节或另建本地计划。小而明确的任务可直接实现。用户只要求方案或草稿时，交付草稿，不暗示允许实施或发布。

需要持久协作时使用项目已配置的唯一 tracker；按项目入口查找配置，缺配置仅阻塞依赖 tracker 的发布，不阻塞起草或普通实现。创建或修改 tracker 条目要有覆盖目标与操作的授权，草稿授权不等于发布授权。已授权且目标充分明确时可继续拆票或实施，不强制等待下一次指令。

## 为谁写，怎样组织

读者可能是后来接手的开发者、审查者或执行 Agent。让他们不依赖本次聊天也能判断问题、已决定的结果和完成条件，而不是按实现步骤照抄。先看已有代码如何工作，沿用项目领域词汇及相关 ADR；来源有冲突时指出冲突，不把未经确认的推断当决定。

从用户视角描述现状、痛点和解决后的体验。用场景或 user story 覆盖不同角色、主要路径、失败与边界，而非为凑数量罗列同义句。例如：“作为移动银行客户，我想看到各账户余额，以便判断可用资金。”再把它变成可判定条件，如“有两个账户时分别显示名称与最新余额；余额无法获取时显示错误，不显示旧余额为最新值”。具体行为以已确认需求为准。

讨论证明方式时，优先选择能覆盖真实用户行为的现有入口和测试边界（seam），参考仓库里类似测试；不为了测试方便新增多个接口或只断言内部调用。需要新边界时解释它能观察什么以及为什么现有边界不足；不强制特定数量或逐个向用户确认。列出待验证模块、关键交互、已有测试先例和适用的验证方式，让执行者能据此选证据，而不是把测试代码写进 spec。

## 可复用的 spec 结构

按任务调整章节，但不要省掉消费者需要的信息：

```markdown
## 问题
<谁在什么情境遇到什么问题；当前表现与影响>

## 目标方案
<从使用者视角描述结果；引用决定的来源>

## 用户场景与验收
- 作为 <角色>，我希望 <行为>，以便 <收益>。
- [ ] <在给定条件下可观察的结果，包括必要边界或失败行为>

## 已定实现与约束
- <涉及的模块及接口、数据形状、API 契约、交互或架构决定；只写已决定且会影响结果的内容>

## 证明方式
- <外部行为、测试边界、关键模块及相似测试先例；必要时说明不能自动验证的部分>

## 不在范围内
- <容易误认为属于本次交付的相邻事项>

## 补充与未决
- <来源、相关决定和仍需谁决定的问题；标明它阻碍的部分>
```

不要把容易过期的文件路径或代码片段冒充长期契约；确有助于定位时可给路径并说明它是指针。若原型里的状态机、类型或 schema 比文字更精确地表达已确认决定，可保留最小片段并标明原型来源，不把整个演示当成验收。
