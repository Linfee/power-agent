# To Spec

把已有讨论、issue 和项目事实整理为一个可独立消费的目标说明。先复用已确认的决定，按需查看代码、项目术语和相关决定，不重新采访已回答的问题。现有 issue 已具备清楚目标、边界和验收时，它本身就是 spec，无需复制。

写明当前问题及期望结果、范围和非目标、会改变结果的约束与已定选择，以及可观察的验收与适当的证明方式。指出仍缺的产品、权限或高风险决定，不能把猜测写成既定事实；同一句需求存在多个会改变可观察结果的合理解释时，即使改动成本低，也保留为未决并询问，不把自行选定的解释写成确定验收。只暂停受该决定阻碍的部分，独立部分继续。实现细节通常留给执行者；原型、接口或路径若准确表达已定契约，可以引用并注明来源，原型不能代替行为验收。

篇幅和形式服从消费者，不需要固定数量的 user stories、章节或另建本地计划。小而明确的任务可直接实现。用户只要求方案或草稿时，交付草稿，不暗示允许实施或发布。

需要持久协作时使用项目已配置的唯一 tracker；按项目入口查找配置，缺配置仅阻塞依赖 tracker 的发布，不阻塞起草或普通实现。创建或修改 tracker 条目要有覆盖目标与操作的授权，草稿授权不等于发布授权。已授权且目标充分明确时可继续拆票或实施，不强制等待下一次指令。
