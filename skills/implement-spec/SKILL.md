# Implement Spec

从指定 spec 和项目唯一 tracker 读取当前目标、票据、关系、所有权和必要讨论；已有完整 issue 直接交给 `implement`，不为使用本 Skill 额外造票。tracker 未配置且确需持久任务图时，由用户显式完成项目配置；普通实现和审查不因此阻塞。协调者在运行中维护调度视图，不把它当第二个可独立更新的状态源。

把真正的 blocker 已完成、未被其他执行者占用的开放任务作为 ready frontier。核对当前状态后，按真实依赖和不相交的写所有权并行派发；共享文件或出口指定单一写者、串行处理或在明确授权的隔离环境中集成。每个子代理使用新上下文，给出目标、范围、共享契约、写入归属、验收、证据、允许和禁止动作及可信源指针。无固定并发上限；结果不完整或冲突时核实证据并补做，不能只汇总完成声明。依赖或目标变化后重新计算 frontier，独立工作继续。

**无 Git 隔离模式是完整路径**：仅一名协调者持有任务图和集成责任；子代理在当前工作区只写各自不相交范围，共享文件串行或交单一负责人。协调者检查实际工作树与交互，解决语义冲突后验证整体行为。不能擅自创建 branch/worktree、commit、merge、push、PR，或关闭任务、删除 worktree；这些都须已有明确授权覆盖具体目标和动作。确有授权且适合时可使用 Git 隔离，但不能把局部提交或合并冒充组合验收；保护已有未提交、未推送及他人工作，清理前核对归属和删除授权。

本地 tracker 的 `Kind`（spec/implementation/map/decision）、`State`（open/active/done）、`Blocked by` 和 `Owner` 分开，外来请求可另有 `Triage`。只有协调者写本地认领与完成状态，子代理返回结果；同图多会话若没有现成可靠原子认领机制则串行协调。远程 assignee 或写唯一标记后重读不是原子锁；遇竞争先重新核对，不能假定独占。状态写入、认领、评论及关闭都须分别获得覆盖实际目标的授权，实施许可不等于 tracker 写入许可。

每个切片按 `proof-oriented-development` 获取与行为匹配的证据；行为改动默认进入 `implement` 的 review–fix 循环（finding 编号、处置、每轮净减少、无 blocker/高严重度且剩余项有处置时退出），由协调者维护账本、执行修复并收敛，审查由 `code-review` 执行。纯文档、注释、格式或已有工具完整覆盖的机械切片可以跳过审查并说明理由。协调者复用仍有效的证据，对共享接口、集成点和完整 spec 做组合验收；必要时检查 staged、unstaged 与新文件，不能将子票全完成等同整体满足。只在代码、证明和整体范围相符且获得写授权时更新相应状态；父 spec 不因子票完成自动关闭。报告实际完成、证据和缺口；未经授权的发布或状态回写单独说明，不伪称已执行。

## 调度与交接

先把目标和票据读成图，而不是按列表顺序执行：找出哪些依赖确实阻止开始、哪些可并行，以及共享接口和文件由谁写。探索量大时可用独立探索子代理，给它明确问题和所需证据；结果可作为短期上下文指针供执行者使用，不作为 tracker 状态副本。不要为每个执行者重复复制完整 spec；给可访问的权威来源指针，并在任务中直接写明会影响本次行为的关键约束。

一个执行交接应回答：交付什么、可写什么、不该动什么、与其他切片共享的接口、前置工作及其真实结果在哪里、如何证明完成、何种变化需要协调者决定。执行者从新上下文读取相关票据和来源，返回实际改动、证据、风险与阻塞；协调者根据实际结果而非状态口头声明推进下游。

例如 A 实现查询入口，B 与其无依赖地制作导出格式，C 组合查询结果和导出。A、B 可在写入不冲突时同时进行；C 只在其真实依赖具备时进入 frontier。若 A、B 都必须修改同一个注册表，将该文件交给协调者或单一写者，不因任务逻辑独立就假装写入也独立。A、B 各自测试通过后，还要验证 C 经真实入口拿到的结果及完整 spec 的验收。

每次结果落地后核对它改变了哪些依赖和可写范围，及时调度新解锁的独立工作；无需等待整个批次。某票失败或需要产品决定时说明缺口，继续不依赖它的分支。所有切片完成后，对照原目标检查遗漏、共享接口和端到端组合；默认由协调者按同一 review–fix 循环驱动整体审查与修复，审查由新上下文 reviewer 执行，纯机械组合可跳过并说明理由。授权允许且需要 Git 隔离时，执行者须以约定基线工作，集成者负责解决差异并在集成结果上取证；不以某分支的局部成功代替最终组合验收。
