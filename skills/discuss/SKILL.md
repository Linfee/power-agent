# 产品需求探索（目标与约束导向）

在实现之前，通过结构化对话将模糊需求变为经过评审的需求 spec 文档。


<HARD-GATE>
仅当任务被识别为“需要 discuss”（需求不清、存在产品分歧、需要范围/验收澄清）时生效：
在 spec 文档经用户明确批准之前，绝不编写代码、脚手架或执行实现动作。
若任务明确且简单，先建议用户跳过 discuss，直接进入实现。
</HARD-GATE>

<SCOPE-BOUNDARY>
discuss 的核心是**明确需求**，类似 PM 与工程师的早期讨论。

**可以讨论：**
- 产品决策：用户目标、功能范围、交互行为、验收标准、优先级取舍
- 用户流程与数据流：用户操作路径、页面跳转、信息流向（产品层面）
- UI 结构：页面布局、信息层级、交互模式（不涉及视觉细节或具体组件实现）
- 技术可行性与高层方向：能不能做、主要阻碍、前置条件。
  一旦讨论进入接口定义、库选型、数据模型、架构分层或代码实现细节，立即停止并转交 writing-plans。
**不做的事：**
- 具体实现方案、库选型、接口设计、数据模型、架构细节
- 这些交给 writing-plans，输入是本 skill 产出的需求 spec
</SCOPE-BOUNDARY>

## 目标（必须达成）

1. 输出一份可评审 spec，能够回答：
   - 谁在用、要解决什么问题、成功长什么样
   - 功能范围包含什么、不包含什么
   - 验收标准与成功指标如何验证
   - 仍未确定的问题是什么
2. 在有产品分歧时，给出可比较的方案与推荐理由。
3. 在任务明确且简单时，触发分流，建议直接实现而不创建 spec。

## 约束（必须满足）

- 只在产品/体验层讨论，不进入实现细节。
- 问题要分批提问：无依赖合并，有依赖分批。
- spec 必须经用户明确批准后，才可交棒给 writing-plans。
- 识别超出目标的内容，主动做 YAGNI 收敛。

## 默认执行方式（可按上下文合并/跳步）

### A. 建立上下文
- 读取 AGENTS.md，理解项目与产品背景。
- 若需求涉及现有功能，按需分析相关模块用于可行性判断。

### B. 澄清与收敛
- 给出你对目标/范围/验收的初步理解。
- 提出澄清问题（优先选择题，附推荐与理由）。
- 执行简单任务分流与规模检查。

### C. 方案对比（仅在有真实分歧时）
- 提供 2-3 个产品方案，说明体验差异、适用场景、取舍。
- 需要图示时：简单场景用 ASCII；复杂场景可写 Mermaid 到文档。

### D. 产出 spec
- 写入 `docs/specs/YYYY-MM-DD-<topic>.md`。
- 模板使用：`references/spec-template.md`（已包含头部元信息）。

### E. Review Gate 与交棒
- 提示用户审阅并等待明确批准。
- 若需修改，迭代更新后再次审阅。
- 批准后将状态改为 `accepted`，并建议执行：
  - `writing-plans [spec-path]`

---

## 关键原则

- **边界意识**：滑入实现细节时立即收住并回到需求层。
- **目标优先**：优先保证产出物可验证，不追求固定步骤完整执行。
- **按需流程**：允许合并步骤，但不得跳过关键约束与 gate。
- **YAGNI**：优先确保核心用户价值闭环。
