# 产品需求探索

在实现之前，通过结构化对话将模糊需求变为经过评审的需求 spec 文档。

**声明于开始：** "我正在使用 discuss skill 进行产品需求探索。"

<HARD-GATE>
在 spec 文档经用户批准之前，绝不编写代码、脚手架或执行任何实现动作。
无论需求多么"简单"，需求澄清总是必要的——即便很短也要完成并获得批准。
</HARD-GATE>

<SCOPE-BOUNDARY>
discuss 的核心是**明确需求**，类似 PM 与工程师的早期讨论。

**可以讨论：**
- 产品决策：用户目标、功能范围、交互行为、验收标准、优先级取舍
- 用户流程与数据流：用户操作路径、页面跳转、信息流向（产品层面的"数据从哪来到哪去"）
- UI 结构：页面布局、信息层级、交互模式（不涉及视觉细节或具体组件实现）
- 技术可行性：这个方向能不能做、有没有明显阻碍、现有代码是否支撑
- 高层技术方向：大方向对不对（如"需要实时推送"vs"轮询就够"），不涉及具体实现

**不做的事：**
- 具体实现方案、库选型、接口设计、数据模型、架构细节
- 这些交给 writing-plans，输入是本 skill 产出的需求 spec
</SCOPE-BOUNDARY>

## 流程

### Step 1: 建立上下文

1. 确认 AGENTS.md 已加载，获取项目概览
2. 从产品视角理解当前状态：现有功能、用户群体、产品定位
3. 若需求涉及现有功能的扩展或改动，启动 `explore` 子代理分析相关模块，了解现状与约束——用于可行性判断，不在此阶段做实现设计

### Step 2: 需求分析与提问

基于上下文，呈现初步理解：

- **用户目标**：谁在用，想解决什么问题，期望达到什么结果
- **功能范围**：具体包含哪些能力/子功能，明确**不包含**什么
- **验收标准**：怎样算做好了，用户能感知到的成功信号
- **优先级**：核心功能 vs. 可选功能，MVP 边界在哪里
- **约束与边界**：已知的限制条件（不讨论技术限制，只讨论产品/业务约束）

然后提出待澄清问题。**按主题分批提问**：无依赖关系的问题合并同批；有顺序依赖的拆分为多批。每个问题附带推荐答案和理由，选择题优先。

**YAGNI 审查**：识别可能超出当前目标的功能，主动建议精简，聚焦核心用户价值。

**规模检查**：如果需求涵盖多个独立功能域，先帮用户拆分，每个功能域单独走完 discuss 循环，不要把所有内容塞进一个 spec。

### Step 3: 产品方案对比（如有分歧）

仅当存在**产品/体验层面**的真实分歧时，提出 2-3 个方案对比：

- 每个方案：用户体验差异、适用场景、取舍（不讨论技术复杂度）
- 给出推荐方案和理由
- 需要展示流程、布局、结构关系时，使用图示辅助：
  - **简单场景**：直接在对话中输出 ASCII 图
  - **较复杂场景**：将 Mermaid 图表写入 `docs/specs/diagrams/YYYY-MM-DD-<topic>-<diagram>.md`，告知用户路径供其在支持 Mermaid 的编辑器中查看
- 询问用户选择，等待明确回复后进入 Step 4

如果需求已足够清晰，无产品层面分歧，**跳过此步**，直接进入 Step 4。

### Step 4: 写 spec 文档

需求澄清完成后：

1. 写入 `docs/specs/YYYY-MM-DD-<topic>.md`，内容聚焦需求层面：

   ```markdown
   ## 背景与目标
   [用户问题和期望结果]

   ## 功能范围
   ### 包含
   - [功能点]
   ### 不包含（Out of Scope）
   - [明确排除的内容]

   ## 用户故事
   - 作为 [用户角色]，我希望 [操作]，以便 [价值]

   ## 验收标准
   - [ ] [可验证的行为描述]

   ## 约束与假设
   [业务/产品层面的限制，不包含技术约束]
   ```

2. 顶部元信息：
   ```markdown
   <!-- verified: YYYY-MM-DD -->
   <!-- scope: [涉及范围] -->
   <!-- status: proposed -->
   ```
3. **不在此步骤提交。** spec 文件仅写入磁盘，等用户批准后在 Step 7 提交。

如果 `docs/specs/` 目录不存在，创建它并在 AGENTS.md 的知识库导航中添加对应指针。

### Step 5: 用户 Review Gate

> "需求 Spec 已通过审查，写入 `<path>`。请查看后告知是否需要调整，确认后可以进入技术规划阶段。"

等待用户回复。如需修改 → 修改并重新运行 Step 5。**只有用户明确批准后才进入 Step 6。**

### Step 6: 交棒

用户批准后：

1. 更新 spec 头部 `status: accepted`
2. 提交 spec 文档到 git：
   - **必须在非主干分支提交**（如当前在主干，先创建分支）
   - **仅提交 discuss 自身的产出物**，不捆绑其他不相关内容
3. 给出后续建议：
   - `writing-plans [spec-path]` — 基于此需求 spec 进行技术规划，产出 TDD 结构的 exec-plan
   - `/feature-dev [topic]` — 进入完整功能开发流程（含代码探索、架构设计、exec-plan）

## 关键原则

- **边界意识**：技术可行性和高层方向可以讨论；一旦讨论滑入具体实现（怎么写、用什么库、接口怎么定义），立即收住并说明"这属于 writing-plans 的工作"
- **按主题分批提问**，无依赖的问题合并同批；选择题优先，附带推荐
- **HARD-GATE**：需求 spec 获批前不做任何实现或技术规划动作
- **方案对比按需执行**：只在存在产品/体验层面真实分歧时才对比，无需强制 2-3 个方案
- **用户 Review Gate**：spec 必须经用户明确批准后才能交棒
- **YAGNI**：主动识别并建议精简超出当前目标的功能
