# 讨论、澄清与对齐

把模糊的问题讨论、澄清、对齐成可评审的 `Discussion Conclusion` / `讨论结论`——产品需求、架构设计、方案选择、营销策略，任何需要想清楚再行动的问题都适用。本 Skill 只做讨论与对齐：产出结论和建议去向，不持有后续路由——往哪走由主代理和用户判断。

## 准入与边界

问题清楚、答案明确时直接回答，不启用讨论流程。启用信号：问题本身模糊（真正要解的是什么还不清楚）、存在真实取舍（多个方向各有代价）、或决策需要同他人或未来的自己对齐。

讨论的深度由决策需要决定：产出的是**决策与方向**，不是可执行工件。讨论开始滑向可以直接动手的细节（编码、逐行计划、精修稿件）时收住——那是执行阶段的事；为锁定决策所必需的具体化（如架构讨论中的接口形状）属于讨论本身。

## 怎么讨论

1. **建立上下文**：读取相关背景；从用户材料中提取已明确事实、冲突点和缺口。只获取支撑当前决策所需的上下文，不做无缺口的全量探索。
2. **判断要不要讨论**：简单明确的问题直接答；多目标、多子问题时先拆解，推荐先解最有杠杆的一个，经用户确认后只推进当前子问题。
3. **澄清与收敛**：先给当前理解和不确定点；澄清问题少量分批，关键取舍一次只问一个；优先选择题并给推荐和理由；用户回答后立即沉淀为事实、假设或 open question。只在真实分歧存在时比较 2-3 个方向并先给推荐；比较围绕该问题的真实判据——效果、成本、风险、可逆性、与约束的契合度。
4. **按需可视化**：仅当“看见”比“阅读”更容易决策时使用 HTML（布局、流程、状态切换、关系结构、side-by-side 方案）；能用文字/表格说清的不用。启用前读取 `references/visual-companion.md`。一屏只解决一个主题，终端文字反馈优先于 HTML 点击事件。
5. **输出讨论结论**：默认在对话中内联输出。结论沉淀最终决定，不转录对话；未确认内容进入 Open Questions 并标明 blocking / non-blocking。产品需求类结论的正文可使用 `references/spec-template.md`。只有用户明确要求、合规/流程要求或需要长期维护的结论才落盘。
6. **审查与去向**：审查强度与决策权重相称——结论将驱动实质行动或不可逆决策时，先自查（无占位符、前后一致、未滑入执行细节），再派独立 reviewer 审查（产品需求类可用 `references/spec-reviewer-prompt.md`），blocking issue 修正后重审；探索性讨论自查即可。通过后给出建议去向：软件开发类——边界清楚的可携结论直接交 `implement`，复杂或高风险工作先经 `writing-plans` 成型；长期知识类——`dev-docs` / `dev-docs-maintain`；其他结论到此为止。

## 输出契约

讨论结论必须回答：

- 真正的问题是什么（问题框架，不是原始提问的复述）
- 目标与成功长什么样
- 已确认事实、关键假设、约束
- 选项与取舍 + 推荐及理由（如有真实分歧）
- 结论与决定
- blocking / non-blocking open questions
- 建议去向（若有下一步）
- 审查状态：`DRAFT` / `APPROVED` / `ISSUES_FOUND`（若经审查）

## 关键原则

- 问题先行：先确认在讨论的是真正的问题；问题问错，答案再好也白费。
- 分歧才发散：没有真实分歧不堆选项。
- 永远带推荐：列出选项就必须给推荐和理由，不和稀泥。
- 深度与权重相称：可逆的小决策轻讨论，不可逆的重决策严审查。
- 默认内联：结论只在确有需要时落盘。
- 可视化服务理解：HTML 是辅助决策，不是交付物。
