# 需求探索与设计讨论

在实现之前，通过结构化对话将模糊需求变为经过评审的 spec 文档。

**声明于开始：** "我正在使用 discuss skill 进行需求探索与设计讨论。"

<HARD-GATE>
在 spec 文档经用户批准之前，绝不编写代码、脚手架或执行任何实现动作。
无论需求多么"简单"，设计总是必要的——即便很短也要完成并获得批准。
</HARD-GATE>

## 流程

### Step 1: 建立上下文

1. 确认 AGENTS.md 已加载，获取项目架构概览和知识库导航
2. 按需加载相关文档：`docs/architecture.md`、`docs/arch-decisions/index.md` 等
3. 如果需求涉及具体代码区域，启动 `explore` 子代理并行分析相关模块
4. **判断是否有可视化问题**（UI 布局、架构图、设计方案对比）→ 如果有，Step 1 结束后单独发送 Visual Companion 邀请（见"Visual Companion"章节），不与任何其他内容混合，等待用户回复后再继续

### Step 2: 需求分析与提问

基于上下文，呈现初步分析：

- **需求拆解**：具体包含哪些能力/子功能
- **影响范围**：涉及哪些现有模块，是否需要新模块
- **与现有架构的关系**：是否符合当前架构方向，有无冲突
- **关键决策点**：需要做出哪些技术选择
- **风险和边界**：可预见的难点、兼容性问题、性能影响

然后提出待澄清问题。**按主题分批提问**：无依赖关系的问题合并同批，一次呈现；有顺序依赖（后续问题取决于前面答案）的拆分为多批。每个问题附带推荐答案和理由，选择题优先。已有明确 arch-decision 记录的方面直接引用，不重复提问。

**YAGNI 审查**：识别可能过度设计的部分，主动建议精简非必要功能，聚焦核心价值。

**规模检查**：如果需求涵盖多个独立子系统，先帮用户分解为独立的子项目，每个子项目单独走完 discuss→feature-dev 循环，不要把所有内容塞进一个 spec。

### Step 3: 提出 2-3 个方案

基于澄清结果，**必须**提出 2-3 个方案：

- 每个方案：核心思路、关键权衡（优势/劣势/复杂度）、适合场景
- 给出推荐方案和理由，推荐方案放第一位
- 询问用户选择，等待明确回复后进入 Step 4

### Step 4: 分段呈现设计

按复杂度覆盖以下维度，简单的几句话，复杂的 200-300 字。每段呈现后询问用户是否认可，确认后再继续。随时准备回溯修改。

覆盖：**架构**、**组件职责**、**数据流**、**错误处理**、**测试策略**

**设计隔离原则：**
- 每个模块一个明确职责，通过接口通信，可独立测试
- 能否在不读内部实现的情况下理解它做什么？能否改内部而不影响调用方？不能 → 边界需要重画
- 在已有代码库中，先探索现有模式再提议变更；不引入与当前目标无关的重构

### Step 5: 写 spec 文档

设计获批后：

1. 写入 `docs/specs/YYYY-MM-DD-<topic>.md`，包含完整设计（架构/组件/数据流/错误处理/测试策略）
2. 顶部元信息：
   ```markdown
   <!-- verified: YYYY-MM-DD -->
   <!-- scope: [涉及范围] -->
   <!-- status: proposed -->
   ```
3. **不在此步骤提交。** spec 文件仅写入磁盘，等用户批准后在 Step 8 提交。

如果 `docs/specs/` 目录不存在，创建它并在 AGENTS.md 的知识库导航中添加对应指针。

### Step 6: Spec Reviewer 循环

写完 spec 后，按 `<discuss-path>/spec-reviewer-prompt.md` 模板 dispatch `tech-plan-reviewer` 子代理：

1. 若 **Issues Found** → 修复并重新 dispatch，最多 3 轮
2. 若超过 3 轮仍有阻塞问题 → 向用户 escalate，描述具体分歧，由用户决策
3. 若 **Approved** → 进入 Step 7

### Step 7: 用户 Review Gate

> "Spec 已通过自动审查，写入 `<path>`。请查看后告知是否需要调整，确认后我们可以开始实现规划。"

等待用户回复。如需修改 → 修改并重新运行 Step 6。**只有用户明确批准后才进入 Step 8。**

### Step 8: 交棒

用户批准后：

1. 更新 spec 头部 `status: accepted`
2. 提交 spec 文档到 git：
   - **必须在非主干分支提交**（如当前在主干，先创建分支）
   - **仅提交 discuss 自身的产出物和本次会话中的相关文件**，不捆绑其他不相关内容
   - 如果不能确定某些文件是否捆绑提交，则不要提交，在后续建议中添加提交询问
3. 给出后续建议：
   - `/feature-dev [topic]` — 进入完整功能开发流程（代码库探索、架构细化、exec-plan 创建、实现）
   - 如果架构在本次讨论中已足够清晰，可直接使用 `writing-plans` skill 创建 TDD 结构的实现计划

## Visual Companion

可选的浏览器可视化伴侣，用于展示线框图、架构图、设计方案对比。

**邀请时机：** 当预计将有可视化问题时（UI 布局、组件层级、架构图、设计方案对比），在 Step 1 结束后单独发送一条邀请消息：

> "接下来的一些问题通过图示可能更直观。我可以在浏览器中展示线框图、架构图、方案对比等内容。是否想开启这个功能？（需要打开本地 URL，功能较新且消耗 token 较多）"

**这条邀请必须独立成一条消息，不与任何其他内容混合。等待用户回复后再继续。**

**按问题单独判断：** 即便用户接受，也要对每个问题独立判断是否用浏览器。标准：**用户看到比读到更容易理解时才用浏览器**。

| 用浏览器 | 用终端 |
|---------|--------|
| UI 线框图、布局对比 | 需求文字确认、方案权衡表 |
| 架构图、数据流图 | 技术选择（A/B/C 文字描述） |
| 空间关系、状态机 | 澄清性问题、范围确认 |

关于 UI 话题的问题不自动等于可视化问题。"需要什么风格的个人页面？"是概念问题 → 用终端；"这两种布局哪个更合适？"是可视化问题 → 用浏览器。

用户接受后，读取详细操作指南：`<discuss-path>/visual-companion.md`

## 关键原则

- **按主题分批提问**，无依赖的问题合并同批；选择题优先，附带推荐
- **HARD-GATE**：设计获批前不做任何实现动作
- **2-3 方案对比必须执行**，不跳过
- **Spec 双重 gate**：自动 reviewer 审查 + 用户确认，缺一不可
- **YAGNI**：主动识别并建议精简过度设计
