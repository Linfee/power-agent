# 产品需求讨论与 PRD 细化

把模糊需求或不完整 PRD 收敛成可评审的 `Discussion Conclusion` / `需求结论`；只有结论将导向软件资产变更时才交给 `writing-plans`。

## 准入

- 仅在需求不清、PRD 不完整、范围/流程/验收缺失，或存在真实产品取舍时启用。
- 若目标、范围和验收已清楚，建议直接推进；只有后续会修改软件资产时才进入 `writing-plans`，其他工作按其专长入口处理。

## 边界

讨论产品与体验层，以及会影响产品范围、验收或计划方向的上层技术方案：目标用户、问题、成功结果、功能范围、最小闭环、用户流程、关键状态、异常路径、验收标准、产品方案取舍、系统级约束、集成/迁移/兼容性方向。

不做实现细节：具体接口签名、库选型、数据表/字段、类/函数拆分、文件路径、测试实现、视觉风格精修。若讨论开始要求可直接编码的技术设计，且后续会修改软件资产，收住并转交 `writing-plans`；若只是决定“走哪类上层方案”以锁定范围和验收，可在 discuss 内完成。

## 流程

1. **建立上下文**
   - 读取项目背景；若涉及现有功能，只分析足够判断范围和可行性的相关模块。
   - 从用户材料中提取已明确事实、冲突点和缺口。

2. **判断是否需要 discuss**
   - 简单明确任务：建议跳过。
   - 多角色、多目标、多子系统或多个可交付闭环：先拆成候选子需求，推荐最小闭环，经用户确认后只推进当前闭环。

3. **澄清与收敛**
   - 先给当前理解和不确定点。
   - 普通澄清每批最多 3-5 个问题；关键产品取舍一次只问一个。
   - 优先选择题，给推荐和理由；用户回答后立即沉淀为事实、假设或 open question。
   - 只在真实分歧存在时比较 2-3 个产品或上层技术方向，并先给推荐；比较范围限于用户体验、范围、验收、风险和 planning 影响。

4. **按需可视化**
   - 仅当“看见”比“阅读”更容易决策时使用 HTML：布局、流程、状态切换、权限/对象关系、side-by-side 方案。
   - 术语、范围、指标、优先级、上层技术方向用文字/表格；接口、模型、库选型、代码结构不在 HTML 中展开。
   - 启用前读取 `references/visual-companion.md`，按其中流程启动服务、写屏、读取事件和停止服务。
   - 一屏只解决一个主题；终端文字反馈优先于 HTML 点击事件。

5. **输出需求结论**
   - 默认在对话中输出内联 `Discussion Conclusion` / `需求结论`，使用 `references/spec-template.md` 的正文；不得展示其 YAML frontmatter。
   - 结论沉淀最终决定，不转录对话；未确认内容进入 Open Questions，并标明 blocking / non-blocking。
   - 只有用户明确要求、合规/流程要求，或需要长期维护的产品资产时，才额外落盘 spec/doc；落盘时保留模板的 YAML frontmatter，并将 `status` 设为实际审查状态。

6. **审查与交棒**
   - 先自查：无占位符；目标、范围、流程、验收一致；上层技术方向只服务范围/验收/planning，未滑入可直接编码的实现细节；仍聚焦单个可计划闭环。
   - 使用 `references/spec-reviewer-prompt.md` 派发独立 reviewer 审查内联结论；blocking issue 修正后重审。
   - reviewer `Status=APPROVED` 且 Evidence 非空、Missing Evidence 无 planning 阻塞缺口后，按当前主要交付物交棒：软件资产变更交给 `writing-plans` 并折叠进 `plan.md`；项目长期知识交给 `dev-docs` / `dev-docs-maintain`；面向读者的实质文档交给 `doc-coauthoring`；其他非开发结论不创建 exec-plan。

## 输出契约

需求结论必须回答：
- 谁在用、解决什么问题、成功长什么样。
- In Scope / Out of Scope / 最小闭环。
- 用户流程、关键状态、异常路径。
- 方案取舍与推荐理由（如有真实分歧）。
- 上层技术方向与约束（如影响范围、验收或 planning）。
- 可验证验收标准、成功指标或手动验收路径。
- blocking / non-blocking open questions。
- 审查状态：`DRAFT`、`APPROVED` 或 `ISSUES_FOUND`。

## 关键原则

- 需求优先：把 PRD 和必要的上层方案讨论清楚，不提前实现。
- 默认内联：spec/doc 只在确有需要时落盘。
- 可视化服务理解：HTML 是辅助决策，不是设计实现。
- 一屏一决策：避免把讨论页做成大而全展示。
- YAGNI：优先锁定核心用户价值闭环。
