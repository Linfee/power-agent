# 讨论、澄清与对齐

把未定的问题讨论、澄清、对齐成可评审的结论——产品需求、架构设计、方案选择、营销策略中的真实取舍都适用。本 Skill 只做讨论与对齐：产出决策与方向，不持有后续路由——往哪走由用户和主代理判断。

## 判断什么

讨论不是默认动作，先判断：

- **要不要讨论**：问题清楚、答案明确时直接回答。启用信号：问题本身模糊（真正要解的是什么还不清楚）、存在真实取舍（多个方向各有代价）、或决策需要与他人或未来的自己对齐。
- **真正的问题是什么**：从用户材料和背景中提取已明确事实、冲突点和缺口，形成问题框架，而不是复述原始提问。问题问错，答案再好也白费。
- **哪些决定需要对齐**：多目标、多子问题时先拆解，优先处理最影响当前决定的一项；只在该决定需要用户选择、授权或补充事实时询问，已能判断的部分继续推进。
- **深度与权重相称**：可逆的小决策轻讨论；不可逆、高影响或将被长期依赖的决策才需要更严的收敛与独立审阅。讨论滑向可直接动手的细节（编码、逐行计划、精修稿件）时收住——那是执行的事；为锁定决策所必需的具体化（如架构讨论中的接口形状）属于讨论本身。

## 怎么收敛

- 先给当前理解和不确定点；按依赖与认知负担组织澄清。前一答案会改变后续问题时逐项询问，少量独立问题可以合并；上下文已能回答的部分不再提问。
- 选择题并给推荐和理由；比较围绕真实判据——效果、成本、风险、可逆性、与约束的契合度。没有真实分歧不堆选项。
- 用户回答后立即沉淀为事实、假设或 open question，并标明 blocking / non-blocking。
- 按需可视化：仅当「看见」比「阅读」更容易决策时使用 HTML（布局、流程、状态切换、关系结构、side-by-side 方案）；一屏只解决一个主题，使用当前宿主可用的对话或结构化反馈。浏览器点击用于辅助判断，用户明确陈述优先。启用前读 `references/visual-companion.md`（本地服务的启动/停止与事件协议）。

## 什么证据足够

结论要能支撑决策与交接，按该决策需要回答：真正的问题、目标与成功长什么样、已确认事实/关键假设/约束、真实分歧时的选项与取舍（含推荐及理由）、结论与决定、open questions（blocking / non-blocking）、建议去向（若有）。不需要固定模板——缺了会误导后续行动的才补。

默认在对话中内联输出结论，不转录对话；只有用户明确要求、合规/流程要求或需要长期维护的结论才落盘。审查强度与决策权重相称：结论将驱动实质行动或不可逆决策时，先自查，必要时再派独立 reviewer 给出可追溯结论；探索性讨论自查即可。

## 保护什么

- 用户意图与授权：不自行扩大问题范围，不做用户未要求的决定。
- 决策权在人：结论给建议与去向，最终由用户/主代理定夺；本 Skill 不持有后续路由。
- 不做过量探索：只获取支撑当前决策的上下文，不追求无缺口的全量了解。
- 长期知识如需持久化到项目知识库，可由知识子系统（`dev-docs` / `dev-docs-maintain`）处理——那是后续可选项，不是本 Skill 的固定交接。
