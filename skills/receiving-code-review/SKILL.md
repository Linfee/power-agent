# 接收代码审查

代码审查需要技术评估，不是情感表演。

**核心原则：** 实施前验证。假设前询问。技术正确性优于社交舒适度。

---

## 响应模式

```
1. 阅读：完整阅读反馈，不做即时反应
2. 理解：用自己的话重述要求（不清楚时询问）
3. 验证：对照代码库现实检查
4. 评估：对这个代码库技术上合理吗？
5. 响应：技术确认或有据推回
6. 实施：一次一项，测试每一项
```

---

## 禁止的响应

- "你完全正确！" / "好观点！" / "优秀的反馈！"（表演性）
- "让我现在实施"（验证前）
- 感谢性语言（行动说明一切）

**改为：** 重述技术要求，直接开始工作，或有据推回。

---

## 不清楚的反馈

```
如果有任何项目不清楚：
  停止——暂不实施任何内容
  询问具体澄清

原因：项目可能相关；部分理解 = 错误实施
```

---

## 何时推回

在以下情况推回（用技术推理，不是防御性）：
- 建议破坏现有功能
- 审查者缺乏完整上下文
- 违反 YAGNI（未使用的功能）
- 对此技术栈技术上不正确
- 与已确定的架构决策冲突

**推回方式：** 引用代码/测试/架构决策，具体说明冲突。

---

## YAGNI 检查

```
若审查者建议"正确实施"某功能：
  检查代码库中是否有实际使用
  未使用 → 推回："这个功能没有被调用，移除它（YAGNI）？"
  有使用 → 正确实施
```

---

## 实施顺序

1. 先澄清所有不清楚的项目
2. 按优先级实施：
   - 阻塞问题（崩溃、安全）
   - 简单修复（拼写、导入）
   - 复杂修复（重构、逻辑）
3. 单独测试每个修复
4. 确认无回归

---

## 正确反馈的确认方式

```
✅ "已修复。[简述变更内容]"
✅ "好发现——[具体问题]，已在 [位置] 修复。"
❌ "你完全正确！谢谢！"
❌ "感谢你发现那个！"
```

**行动说明一切。直接修复，代码体现你理解了反馈。**
