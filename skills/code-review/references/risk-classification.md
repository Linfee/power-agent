# 重要性与实现风险

用于选择审查投入。两个独立维度，分开判断。

## 重要性：变更出错后的影响面

- `低`：仅文档、注释、纯测试、格式或不影响运行时的配置微调。
- `中`：局部/单模块逻辑或 bugfix，不触及跨模块契约、权限安全或持久化协议。
- `高`：公共 API/跨模块契约、数据/持久化/迁移、鉴权/敏感数据、关键并发/事务语义。

## 实现风险：当前实现出错的可能性

只依据 diff、验证、复杂度和未解决不确定性：

- `低`：改动集中直接，相关验证充分，无关键未知。
- `中`：跨路径逻辑、局部复杂度或验证缺口提高了出错概率，但关键假设可追溯。
- `高`：证据显示实现可能错误，或关键假设/路径有重大未受控缺口。
- `未评估`：信息不足。

## 判断的使用

重要性决定初始投入；实现风险是审查过程中的实时判断，不由重要性推导。高重要性或高实现风险的变更，收敛前应让一个未参与该目标的独立 reviewer 复核，把先前结论只当主张重新验证。阻塞 finding 的修复由原 owner 在授权范围内实施并验证；owner 不可继续时，替代者必须拿到原 finding、证据、修复说明、delta 与新验证后再复验。
