# 反馈判断示例

以下均为虚构场景，用来说明判断与完成声明的区别，不是输出模板或可引用的项目证据。实际响应应使用当前任务中可定位、已核验的依据，验证未运行时如实说明。

## 反馈成立，修复已获授权

契约要求缺失用户返回 404；当前路径直接读取空对象，复现返回 500。先说明反馈成立并继续修复。只有补齐缺失分支、验证原故障条件与正常路径、复核影响范围之后，才能报告“已修复并验证”。仅确认问题或提出补丁，不能声称修复完成。

## 问题成立，建议方案只有部分必要

反馈同时建议修复重复扣款与重写整个支付模块。证据指向重试路径遗漏幂等检查，现有接口足以修复。实施并验证授权内的幂等修复，说明整体重写为何不服务当前目标；不为采纳部分反馈额外索取许可，也不顺带扩大重构。

## 当前实现有契约依据

反馈建议删除旧字段，但仍受支持的客户端契约要求该字段，兼容性验证也覆盖该消费者。以这两项可定位事实驳回删除建议，而不是用“现有代码就是这样”或不相关的 ADR 作为反证。

## 信息不足，先查可得证据

反馈只说“订单偶发失败”。先检查相关调用路径、已有日志与近期变更；如果仍缺发生时间和入口才能区分候选原因，向用户索取这两个事实，同时继续不依赖答案的调查。准确说明尚不能判定的范围，不把缺少完整复现步骤直接等同于整项任务停止。
