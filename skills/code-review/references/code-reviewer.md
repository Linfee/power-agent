# 独立审查 Brief

此文件可单独派给 reviewer，附上已可得的需求、范围、diff 或工作树、已有验证、先前 finding 与修复增量。缺少材料时先判断是否影响结论，再索取最小必要上下文。遵守委派的读写边界；独立复核者不参与实现。

使用 `code-review` 的需求符合性与工程正确性两维独立判断；以有效需求和契约判断应有行为，以当前 diff、相关 staged / unstaged / untracked 文件、受影响调用路径与适用运行证据判断实际行为。旧结论和口头声明是待核验主张，不能用现有实现覆盖需求。

反馈范围与证据缺口；每个 finding 给出定位、触发条件、影响和所需行为改变。修复复核覆盖原问题、增量与受影响路径；关键范围或契约实质改变时重审受影响部分。具体工程准则和严重度判断以 `code-review` 主文件为准。

## 标准与 diff 气味基线

先读适用于变更范围的项目标准，包括存在的 `CODING_STANDARDS.md`、`CONTRIBUTING.md` 和目录级规则，报告违反标准时引用文件及具体规则。除项目标准外，用下列 Fowler 气味检查**此次 diff**；读相邻代码只是为了理解受影响行为，不借机审查整个仓库。项目明确采用的做法优先于基线；已经由工具可靠覆盖的样式问题不重复报告。气味只是调查线索，须说明实际负担、触发条件及影响；不是发现一个名字就自动违反规则，建议的处理方式也要符合具体约束。

| 气味 | 变更中留意什么 | 可能的处理 |
|---|---|---|
| Mysterious Name | 名称不能说明函数、变量或类型的作用 | 改成表达含义的名称；若无法命名，检查职责是否含混 |
| Duplicated Code | 多处新增相同逻辑形状 | 在确有共同变化理由时收敛共享逻辑，不强行合并偶然相似 |
| Feature Envy | 方法主要读取和操纵另一对象的数据 | 考虑把行为移到拥有数据及不变量的位置 |
| Data Clumps | 同一组字段或参数反复一起出现 | 考虑用表达该概念的类型集中它们 |
| Primitive Obsession | 原始值或字符串反复承担未受保护的领域概念 | 在真实不变量或误用风险存在时引入小类型 |
| Repeated Switches | 多处对同一类别重复分支 | 考虑统一查表或多态，避免增加不必要的间接层 |
| Shotgun Surgery | 一次逻辑变化迫使多处相关文件同步修改 | 集中共同变化的知识和责任 |
| Divergent Change | 同一模块因互不相关的原因反复变化 | 考虑按独立变化原因拆分 |
| Speculative Generality | 为需求未出现的扩展添加钩子、参数或抽象 | 删除无现实用途的机制，回到实际需求 |
| Message Chains | 调用方依赖一长串对象导航及内部结构 | 让恰当的模块提供表达意图的操作 |
| Middle Man | 一层基本只转发，未承担不变量、协议或资源责任 | 可能直接调用真正的目标 |
| Refused Bequest | 子类或实现者忽略、大量禁用继承的行为 | 考虑调整接口或改用组合 |

将项目规则违背与「可能的气味」分开说明。例如一个单消费者的资源对象如果集中连接所有权和关闭顺序，就不能仅凭 Middle Man 或实现数量认定多余。需求维度独立核对遗漏、部分实现、错误行为与无关扩张，引用原请求或契约；需求不完整时标明无法判断之处。两个维度默认交给不同 reviewer 并行独立覆盖；只有用户明确要求合并时才由同一 reviewer 覆盖，交接需包含实际比较范围、需求来源和标准，而不是默认对方知道。
