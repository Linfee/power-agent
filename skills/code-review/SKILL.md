# 代码审查

分别判断**需求符合性**与**工程正确性和质量**：实现可能工程良好却遗漏目标，也可能满足目标但引入故障。按实际请求确定比较基准与范围；无需为了审查先提交或创建 spec。任务请求、issue、约定和已有契约都可能提供需求；缺少特定材料时利用现有证据，说明无法判断的部分。

查看相关 staged、unstaged 和 untracked 文件及受影响调用路径；普通 diff 不包含新文件时直接读取它们。指定提交、分支或 PR 时按实际目标选择比较方式，不假定三点 diff 总能覆盖请求。把已有测试结果、实现者说明和先前结论当待核验主张，不以现有实现覆盖需求。

审查前确认基准实际存在、比较结果与用户请求一致；分支比较可使用 merge-base 三点 diff，但用户要求逐提交或包含工作树时应选择相应方式。结果为空时先核对范围和 staged / unstaged / untracked，不能把选错基准当作无问题。

查找需求时结合用户给出的请求或路径、提交信息中的 issue 引用及已有 tracker、与功能对应的设计/规格文件；不强制其顺序覆盖用户明确指定的来源。查不到正式 spec 时仍按现有请求和可查契约审查，并说明缺口，不要求先补一份。查找项目适用标准：包括已有的 `CODING_STANDARDS.md`、`CONTRIBUTING.md`、项目/目录级 agent 指令及相关约定；检查改动文件所在范围。针对变更的 Fowler smell 启发及标准优先级见 [审查 brief](references/code-reviewer.md#标准与-diff-气味基线)。

## 两个维度

- **需求**：目标与验收是否完整，是否有漏做、错误实现或无关扩张；实际行为、错误体验和适用的可访问性是否满足使用者需要。
- **工程**：结合变更检查正确性、边界、并发与事务、安全及数据、资源所有权与生命周期、失败恢复、性能、兼容与测试。项目已记录的标准适用，但不把工具已覆盖的风格或抽象原则本身当 blocker。验证须覆盖真实行为和故障机制，替身不能掩盖待验协作。

删除新增层、配置或状态后，是否仍能满足相同约束？比较复杂度及其承担者；真实 I/O、资源所有权或不变量边界即使只有一个实现或消费者也可能有价值。性能 finding 须有实际路径、规模或可核验成本；具体吞吐、容量和延迟结论需要代表性测量。

每个 finding 给出可定位证据、触发条件、影响和所需行为改变；设计问题说明具体负担及可满足同一约束的更简单方案。按已核实影响区分严重、重要和轻微；猜测、风格偏好或仅仅存在替代方案不是 blocker。分别呈现两维的结论与证据缺口，不让一维通过掩盖另一维失败。

## 审查投入与复核

独立性与投入取决于出错后果和实现不确定性，而不是人数规则。小改动可由一名 reviewer 覆盖两维；高影响或高不确定性时使用未参与实现的独立 reviewer。用户明确要求多角度时按请求组织；独立委派使用新上下文并提供范围、需求来源、当前变更与相关证据，可用 [审查 brief](references/code-reviewer.md)。需要细分影响和实现风险时读 [risk-classification.md](references/risk-classification.md)。

收到反馈先核验契约、触发条件和实际影响，再在授权范围内修复；只要求评估时不改代码。修复后复核原问题、增量与受影响路径；范围或关键契约发生实质变化时重审受影响部分，不机械重跑无关审查。例子见 [response-examples.md](references/response-examples.md)。

只有明确提供 Review Assets manifest 时才使用 [Review Assets 协议](references/code-reviewer.md#review-assets)；无 manifest 不扫描 `.power-agent`，校验失败报告证据缺口，不扩大搜索。结论说明范围、已核验问题和未验证面。
