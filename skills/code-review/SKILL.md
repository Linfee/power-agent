# 代码审查

## 审查判断

判断当前变更是否值得合入：既满足需求、保护契约，也采用与当前目标相称的最小充分设计，不把不合理的成本与风险转嫁给消费者、运行环境或维护者。有效需求和契约定义应有行为，当前代码、diff 与适用运行证据说明实际行为；冲突时检查版本、范围、执行条件和契约依据，不能用实现覆盖需求。按实际变更选择深入的维度，不把以下关注点变成每次必跑的全量清单：

- **需求与范围**：验收项是否覆盖，有没有漏掉的行为、无关重构或顺手扩展；用户或调用方的正常路径是否易用，错误是否可行动，适用时检查可访问性。
- **正确性**：边界、状态与错误语义；适用的并发、幂等、事务与缓存不变量。
- **安全 / 数据**：注入、鉴权、密钥、隐私、SSRF、不安全的默认值、持久化与支付语义的变化。
- **设计与复杂度**：新增概念、抽象、状态、配置、依赖及跨模块协调是否必要；职责、资源所有权与生命周期是否清楚，调用方是否仍需理解内部机制或记忆隐含顺序。仓库已文档化的约定优先，不把设计偏好当硬违规。
- **性能与资源**：相对原路径是否增加无收益的计算、分配、复制、I/O 或网络往返；检查 N+1、全量加载及内存、队列、缓存、并发的边界，并结合真实规模判断增长成本。
- **可靠性与运行**：局部失败、取消、超时和部分成功是否可恢复；重试、缓存与上下游机制叠加后是否放大故障；故障是否可诊断，日志是否有必要上下文且不泄密。
- **兼容与演进**：真实消费者、存量数据与独立发布是否受影响；新依赖的维护、许可证和部署成本是否合理；切换后的旧入口、配置、测试与文档是否仍服务当前支持范围，避免无依据的双轨残留。
- **测试保护**：可观察行为、关键边界与失败路径是否有变更绑定的证据；测试能否区分正确与错误实现，是否因绑定内部结构或过度使用替身而漏掉真实风险。

### 最小充分设计与成本

以奥卡姆剃刀追问：去掉这个实体、间接层、配置、依赖或持久状态，是否仍能正确、清楚地满足当前需求？若能，要求其保留有具体收益；若它封装了真实不变量、生命周期或运行边界，即使只有一个消费者也可能必要。简单不等于代码短、类少或一律去重，不能靠隐藏错误语义或把责任推给调用方来“简化”。

比较变更前后的整体复杂度：哪里新增、哪里消除、由谁承担，是否用局部简洁换来全局耦合、状态组合或运维负担。新增复杂度须由当前需求、消费者、运行边界或风险支撑，不以假想扩展为理由；不要求每次变更净减少复杂度，也不按行数计分。

性能判断结合路径频率、输入规模和资源预算。明显无收益的工作可据代码指出；吞吐、尾延迟或容量结论需要代表性测量或可核验的成本分析，不凭猜测下结论，不为低影响路径强制 benchmark 或引入收益不明的微优化。

### 问题与审查投入

每个 finding 必须绑定可定位证据（file:line、diff hunk、命令输出），说明触发条件、影响和需改变的行为。设计类问题还须指出具体负担及满足同一约束的更简单替代，不只引用原则名称。风格偏好、猜测或已由工具强制的项目不构成 finding；设计和性能问题也不自动降为建议。严重度只由证据支持：`严重`（安全 / 数据丢失 / 崩溃 / 核心故障、unsafe merge）、`重要`（缺需求、语义错误、明确回归、关键测试缺口，或有证据的显著性能、复杂度与维护负担）、`轻微`（非阻塞建议）。复杂度负担是否显著，须结合具体使用、修改或运行场景说明；仅新增机制或存在更简单方案，不足以阻塞合入，非阻塞建议不得成为通过条件。

审查投入由两个独立维度决定，不用未限定的"高风险"：

- **重要性** = 变更出错后的后果：受影响的用户和操作、损害程度、可恢复性及兼容性义务。按实际影响判断，不用文件类型或 API 标签直接定级；危险操作文档和安全测试的改动也可能有高影响。
- **实现风险** = 当前实现出错的可能性，只依据 diff、验证、复杂度和未解决不确定性：集中直接且验证充分 → 低；跨路径逻辑或验证缺口 → 中；证据显示可能错误或关键路径有重大缺口 → 高。

分级拿不准时读 [risk-classification.md](references/risk-classification.md) 的影响与不确定性判据。

## 证据与复核

- 读取当前 diff、任务相关的 staged / unstaged / untracked 文件及受影响路径。资产、日志和验证必须真实、可复查、适用于当前范围；旧结论、口头声明或过期材料只能作线索。一项通过结果不能覆盖未测试的路径。
- 修复后检查当前代码、修复增量与受影响路径；若实质改变范围、验收、公共契约、数据、权限、安全、并发或迁移边界，重新审查该范围，不能沿用旧结论。
- 未解决的 blocker 阻止审查通过或合入，授权内修复与验证继续；无 blocker 且证据覆盖当前需求与风险才判通过。材料不足时明确缺口。

提供 Review Assets（`REVIEW_ASSETS_MANIFEST`、权威 run root、`ALLOWED_ASSET_SENSITIVITY` 等）时，读取并执行 [code-reviewer.md 的 Review Assets 协议](references/code-reviewer.md#review-assets)，通过全部校验后才读取资产。无 manifest 不扫描 `.power-agent`；校验失败只报 evidence gap，不扩扫。

## 反馈评估

收到内部 finding、外部 reviewer 或 PR 评论时，逐项对照契约与实际行为，给出成立、部分成立、反证或信息缺口的可定位依据，不套状态模板。用可得上下文和区分性验证解决技术分歧；用户已授权修复时，实施采纳项、验证并复核，仅请求评估时交付判断。只有关键事实无法取得、需要用户决策或继续会越过授权时才询问，破坏性操作不能从普通修复授权推导。需要判断示例时读 [response-examples.md](references/response-examples.md)。

## 独立审查

高重要性或高实现风险时，收敛前由未参与该目标的独立 reviewer 复核，把先前结论只当主张重新核验。委派时可单独提供 [code-reviewer.md](references/code-reviewer.md) 及当前任务材料；它供独立审查者使用，不是主代理每次审查的附加必读。

用户明确要求双审时，两名独立 reviewer 各自完成完整审查；同一问题合并证据，按核验后的触发条件与实际影响确定严重度。结论冲突时查证分歧，不机械取最高级。修复优先由提出 finding 的 reviewer 复核；更换复核者时，提供原 finding、证据、修复增量及新验证，由替代者形成当前判断。需要独立复核时，替代者仍须独立于实现。
