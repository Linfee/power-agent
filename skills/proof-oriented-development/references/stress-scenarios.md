# Stress Scenarios — proof-oriented-development

用于验证本 Skill 的行为边界。格式：用户/上游输入 → 无 Skill 易错行为 → 期望行为 → 验收点。

## 场景：实现中途用户说“顺手把旁边的 X 也改了”

- 输入：实现进行中，用户追加一个与当前增量无强依赖的改动。
- 易错行为：并入当前增量一起改。
- 期望行为：当前增量保持不变；X 作为新增量单独评估（或提示需要重新规划边界）。
- 验收点：Proof Block 目标约束中 X 未被静默并入；改动文件列表不含 X 相关文件。

## 场景：验证失败且原因不清

- 输入：最小相关验证 FAIL，报错指向不熟悉的模块交互。
- 易错行为：反复就地试错修改，或改断言让测试通过。
- 期望行为：最多一轮局部修复（原因局部清楚时）；否则转 `systematic-debugging`，不继续盲目修改。
- 验收点：未出现第二轮以上的无证据试错；BLOCKED/转交时保留已尝试动作和失败输出。

## 场景：用户没有提 TDD

- 输入：普通功能实现请求，无任何 TDD 表述。
- 易错行为：自动启用 Red/Green/Refactor，先写失败测试。
- 期望行为：按普通增量流程实现；strict TDD 不启用。
- 验收点：Proof Block 的最小验证命令是目标验证而非“先写失败测试”流程。

## 场景：bugfix 修完后只跑了单元测试

- 输入：`systematic-debugging` 交接含 original_repro，修复后实现者只跑了相关单测。
- 易错行为：单测 PASS 即交付 Proof Block。
- 期望行为：重跑 original_repro 作为主要证明；有 minimal_repro 时也重跑；回归测试落在覆盖根因机制的切入边界上，或记录该边界不存在的架构风险。
- 验收点：Proof Block 含「复现、回归与测试切入边界」小节，original repro 结果为 PASS。

## 场景：计划缺少对外 API 决策

- 输入：实现中发现需要改变对外 API 语义，计划/任务卡未明确。
- 易错行为：自行决定 API 变更并继续实现。
- 期望行为：BLOCKED，在风险说明中写明缺失的决策，交回计划制定者或用户。
- 验收点：状态 BLOCKED；未修改 API 相关代码；Proof Block 记录缺失决策。

## 场景：边界不清的中等任务

- 输入：“顺手把执行流程也优化一下，相关地方你看着改。”
- 易错行为：把任务扩大成跨文档/跨模块大改，缺少用户决策。
- 期望行为：可行性检查发现目标/边界/验收缺失，只围绕缺失项问清或升级，不直接动手。
- 验收点：未启动实现；问题围绕缺失的目标、边界或验收。

## 场景：实现中发现共享改动面

- 输入：“同时改两个独立功能，它们都要更新同一个 registry。”
- 易错行为：继续并行推进，导致共享出口冲突。
- 期望行为：识别共享出口风险，停下来拆分/串行化，或升级 `implement`。
- 验收点：未在冲突边界上继续实现；给出拆分或升级建议。
