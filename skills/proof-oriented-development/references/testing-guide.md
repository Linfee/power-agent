# 好测试、接缝与 Mock 的位置

**加载时机：** 设计测试、决定在哪一层写测试、犹豫要不要 mock 时。反面清单见 `testing-anti-patterns.md`；本文件讲怎么做对。

## 好测试的定义

好测试验证用户或调用者依赖的行为，读起来像规格说明书（"user can checkout with valid cart"），与契约无关的内部重构后依然成立。特征：

- 优先通过稳定的可观察接口验证用户或调用者在乎的行为。
- 描述 WHAT，不描述 HOW。
- 围绕一个清晰行为组织测试，可用多个相关断言共同证明。

坏测试的红旗是依赖与契约无关的私有方法、调用结构或存储布局，使行为未变的重构也导致失败。调用次数、顺序或持久化结果本身属于契约时可以直接断言，例如支付重试上限、消息顺序和事务落库；测试应说明这些观察与目标行为的关系。

## 接缝（测试切入边界）

接缝是能稳定观察相关行为的边界，可以是模块接口、协议或副作用边界。优先选择能覆盖故障机制、且不随无关实现变化的切入点。

**先识别接缝再写测试**：从用户目标、当前契约和故障机制确定本次要测的接缝。不可能什么都测；这个判断让测试投入落在关键路径和复杂逻辑上，而不是撒到每个边角。bugfix 的回归测试还必须落在能覆盖根因机制的接缝上，保留相关调用链、并发语义或组件交互——覆盖不到根因机制的浅层假绿不算回归保护。

没有理想接缝时不硬造公开接口：记录缺口与受影响边界，选择能覆盖机制的现有入口、原场景重放或等价观察，并说明仍未覆盖的条件。

按覆盖能力、运行成本和稳定性选择真实组件测试或隔离测试，不预设哪一类必然更快、更稳。

## Mock 的位置

按副作用和真实契约决定隔离位置：外部 API、时间、随机、数据库、文件系统，以及自己拥有的远程组件都可能需要替身。进程内确定性协作优先使用真实对象；确需内部替身来控制昂贵、不可达或不稳定条件时，保留最小隔离并说明覆盖限制，不能替换掉正要验证的交互。

需要隔离时优先复用现有接口，只有运行边界或消费者需求支持时才调整设计：

- **依赖传入**：需要控制的外部依赖可由组装处传入，普通内部对象不因测试而一律改成注入。
- **接口表达真实操作**：当通用 fetcher 迫使调用方重复协议与错误处理时，可用窄的操作接口收敛复杂度；不只为方便 mock 新增 wrapper。

## strict TDD 的补充规则（仅用户明确要求时）

- 可以先列出待覆盖的行为与测试案例，再选择下一项要验证的行为；不固定每轮的测试函数数量。
- 先红后绿：先运行测试并确认它因目标行为尚未实现而失败，再写满足当前行为的最小实现，使测试通过。
- 绿后重构：在测试保持通过的条件下，整理本次实现所需的结构、命名与重复；重构属于 Red/Green/Refactor 循环，范围仍由当前目标约束。
