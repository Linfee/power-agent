# 好测试、接缝与 Mock 的位置

**加载时机：** 设计测试、决定在哪一层写测试、犹豫要不要 mock 时。反面清单见 `testing-anti-patterns.md`；本文件讲怎么做对。

## 好测试的定义

好测试通过公开接口验证行为，读起来像规格说明书（"user can checkout with valid cart"），内部重构后依然成立。特征：

- 测用户/调用者在乎的行为，只用公开 API。
- 描述 WHAT，不描述 HOW。
- 一个测试一个逻辑断言。

坏测试的红旗：mock 内部协作者、测私有方法、断言调用次数或顺序、绕过接口做侧信道验证（直接查库而不是用 `getUser`）、行为没变重构后测试却红了。

## 接缝（测试切入边界）

接缝是观察行为的公开边界——不伸手进内部就能看见行为的那一层。测试只住在接缝上。

**先约定接缝再写测试**：Proof Plan 阶段写下本次要测的接缝并确认。不可能什么都测；先约定接缝，是让测试投入落在关键路径和复杂逻辑上，而不是撒到每个边角。bugfix 的回归测试还必须落在能覆盖根因机制的接缝上，保留相关调用链、并发语义或组件交互——覆盖不到根因机制的浅层假绿不算回归保护。

没有理想接缝时不硬造：记录接缝缺口与受影响边界，以 original repro 为主要证明（见 `verification-before-completion` 的条件性门槛）。

通过公开接口的集成式测试通常比深 mock 更快、更稳——这就是最小相关验证该有的形状。

## Mock 的位置

只在系统边界 mock：外部 API（支付、邮件）、时间与随机、有时数据库（优先 test DB）和文件系统。不 mock 自己控制的代码——自己的类、内部协作者、任何你拥有的模块。

边界上要 mock 时，把接口设计成好 mock 的形状：

- **依赖注入**：外部依赖传进来，不在内部 `new`。
- **SDK 风格接口优于通用 fetcher**：每个外部操作一个函数。mock 时一个函数返回一种形状，不需要在 mock 里写条件分支，也一眼能看出测试覆盖了哪些端点。

## strict TDD 的补充规则（仅用户明确要求时）

- 先红后绿：先写失败测试，再写刚好够过的实现；不预写未来测试，不加投机功能。
- 一次一片：一个接缝、一个测试、一个最小实现，纵向切片前进。
- 重构不属于循环，归审查阶段。
