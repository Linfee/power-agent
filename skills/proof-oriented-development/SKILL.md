# Proof-Oriented Development

以最小充分改动实现目标，交付与结果匹配的低成本、可复现证据。本 Skill 独立完成实现与验证；调试、审查、收尾等如有需要是独立动作，不是本 Skill 的前提或固定交接。

## 判断什么

- **做什么**：目标（要改变什么）、边界（什么不能顺手改）、验收（凭什么判断完成）三样要齐。缺哪样问哪样，问题只围绕缺失项。
- **增量多大**：一次只做一个可验证的增量，不把多个独立目标混在一次改动里。每个增量能独立证明即可，粒度由验证成本与风险决定。strict TDD 只在用户明确要求（`TDD`、`测试驱动`、`先写失败测试`、`Red/Green/Refactor`）时启用。
- **复杂度值不值**：进入会新增长期所有权的方案前（新依赖、跨模块边界、外部配置面、持久/跨请求共享状态、具有 init/cleanup/concurrency 语义的生命周期），先用当前需求、真实消费者或运行边界举证，并说明为什么复用已有实现、平台原生能力或既有依赖不够用；局部变量、派生状态、内部 helper 不进入此判断。简单优先是启发，不是必须攀登的阶梯——不能因它牺牲正确性、安全、数据完整性、错误语义、契约或 Proof，也不能拒绝由真实外部约束购买的 SDK、adapter、配置、状态或 cleanup。seam / adapter 深度与模块边界的裁决由具备设计判断的一方负责。
- **验证什么**：选与改动强相关、成本最低、可复现的方式，不固定菜单——代码改动跑目标测试或最小脚本；UI 改动留浏览器/桌面操作与截图证据；文档改动做引用与结构检查；bugfix 必须重跑用户报告的 original repro（有 minimal repro 也重跑，二者不替代）。

## 根因不明的 bug

按用户目标完成诊断后再修：用区分性证据定位第一处偏离并解释传播路径，主要替代解释被排除后才能称为根因；证据不足时不猜改。修复落在产生偏离或拥有相关不变量的位置，不在下游掩盖症状。授权不含本次修改时，先请求最小授权，不动文件。性能 / 不稳定问题用同口径比较或频率证据——功能正确不能替代性能非退化证据，单次绿色不能证明 flaky 已修复。

## 实现时的判断

围绕当前增量持续核对：要证明的目标和边界是否已清楚、哪种实现最直接地满足契约、什么最小观察能推翻错误实现，以及结果是否仍支持声明。根据证据自由选择调查、实现、验证和说明的顺序；不把多个互不相关的目标混成一个无法归因的改动。

涉及测试或 mock 时，按需读 `references/testing-guide.md` 与 `references/testing-anti-patterns.md`。验证失败而原因局部清楚时可以就地修复再验证；原因不清、超出边界或需要未授权决策时停下说明，不用猜测或状态标签伪装进展。

## 什么证据足够

交付应让读者能定位本次改变、观察到的结果，以及仍未覆盖的风险；具体表达取决于读者与结果，不要求固定字段或 Proof Block。至少保留能复查的实际命令、路径、操作或输出，并让声明精确匹配它们。

以下情形需要覆盖对应事实：

- **bugfix**：original repro 重跑结果与回归测试的切入边界（回归要覆盖根因机制，保留相关调用链、并发语义或组件交互；覆盖不到根因机制的浅层假绿不算回归保护，此时以 original repro 为主要证明并记录架构风险）；
- **临时产物**：位置、敏感性/安全影响、删除或保留及保留原因；
- **安全 / 数据 / 权限 / 公共 API / 性能与稳定性影响面**：相应的专门证据，或为什么该属性不受影响。

没有对应情形就不添加仪式性说明。

继续需要的高风险决策缺失时停下：数据模型 / Schema 变更未定、对外 API 语义破坏或删除未定、鉴权 / 权限 / 隐私 / 并发一致性 / 事务边界不清、继续会超出允许范围、验收或授权。停下时写清已确认事实、已尝试动作、缺什么决策。范围明显需要更大编排（跨模块多阶段迁移、预期多轮交互等）时，说明规模与原因，由用户决定如何继续；可完成的部分仍然先完成。
