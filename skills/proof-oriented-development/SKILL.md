# Proof-Oriented Development

以最小完整改动实现用户目标，并取得匹配证据；本 Skill 可独立完成实现和验证。

## 实现判断

- 从请求、代码与项目约定确定目标、不可越过的边界和可观察验收。只有无法自行补齐且会改变结果的缺口才询问。
- 按依赖、契约清晰度、未验证假设和反馈成本组织增量。相关实现与测试可以批量完成；关键假设先取证，无法归因的失败先缩小范围。
- 新依赖、跨模块边界、外部配置、持久共享状态或生命周期责任须由当前消费者或运行约束支持，并检查已有能力是否足够。普通局部变量和 helper 无需单独论证；简化不能牺牲正确性、安全或契约。
- 验证失败时，原因明确就修复，原因不明先调查。跨模块、多阶段或技术分歧本身不要求重新授权；在原目标内自主拆解和推进。

## Bug 与证据

永久修复落在产生偏离或拥有不变量的位置。称为根因前，需要连接触发条件、第一处偏离和症状的区分性证据，并排除主要替代解释。用户目标含事故止损时可先做授权内的缓解，再调查；缓解与根因修复分别验证和声明。

原失败场景可安全重跑且覆盖当前风险时优先复跑，minimal repro 按额外诊断或回归价值复验。原场景不可重跑时，说明替代证据保留和省略的故障条件，区分代码修复与原环境尚未验收。回归须保留根因所需的调用链、并发或组件交互，浅层通过不能证明原问题解决。

按实际契约选择最小充分验证，并保留项目明确门禁：代码用目标测试或可复现脚本；UI 用实际交互与视觉证据；文档核对引用、结构与关键语义。安全、数据、权限、公共 API、性能和稳定性有影响时，补相应证据或说明不受影响的依据；功能通过不能证明性能未退化，单次绿色不能证明 flaky 已修复。

测试切入点或 mock 选择拿不准时读 [testing-guide.md](references/testing-guide.md)，排查假绿和实现耦合时读 [testing-anti-patterns.md](references/testing-anti-patterns.md)。用户明确要求 TDD / 测试驱动 / 先写失败测试时，遵循 Red/Green/Refactor；其他任务的验证顺序由现场决定。

## 完成与授权

已有证据仍覆盖当前内容、依赖和环境时直接复用；没有新改动、失败或未解疑点时不扩大或重复验证。交付说明实际改变、支持结论的命令或观察、可复查路径与未验证面；本次临时产物注明位置、安全影响及删除或保留原因。

继续需要未定的 Schema、破坏性 API、鉴权、隐私、并发或事务决策，或会超出范围、验收和授权时，暂停依赖它的动作，说明事实与缺口；独立部分继续。达到用户目标且证据充分后结束，不追加固定审查或交接流程。
