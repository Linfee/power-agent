# Proof-Oriented Development

以用户可观察的行为为目标，做最小完整的改动并取得匹配的证据。沿用项目已有的领域术语、相关决定和验证门禁。

## 行为驱动的增量

可自动化验证的行为变更默认使用 **Red → Green → Refactor**：

1. 选择能覆盖当前行为及关键故障机制的稳定观察边界；编写测试并运行，确认它因目标行为缺失或错误而失败，而不是环境、语法或无关错误。无需逐个向用户确认测试边界。
2. 写足以实现当前行为的代码，运行相关测试使其变绿。以纵向切片取得反馈，再根据所学继续下一个行为；一轮可有多个相关测试或断言，不固定测试数量。
3. 测试保护下整理本次实现所需的命名、结构与重复，保持行为绿色；不把所有重构推迟到审查阶段。

不要先横向写完所有测试、再一次性实现：这会在不了解真实接口和行为时固定测试结构，让测试验证想象中的代码形状，而不是调用者的能力。纵向切片先打通一个可观察行为，用红绿反馈发现接口、边界与下一步，再继续扩展；切片内可以包含相互关联的多个测试。示例与替身选择见下方测试指南。

已有失败已覆盖缺陷时复用它，不为演示红色而改坏代码。纯重构以覆盖已有行为的测试保持绿色；UI、文档和机械变更等不适合红测的目标，用实际交互与视觉、文档结构/事实核对或适当差分证明，不伪造红色阶段。环境或授权使应有验证无法执行时说明限制，不能声称已验证。

测试从调用者依赖的行为出发，期望来自需求、契约或独立事实；真实组件与替身按覆盖、成本和稳定性选择，不能 mock 掉正要证明的协作。调用次数、顺序和落库结果属于契约时可断言。需要选择测试边界与替身时读 [testing-guide.md](references/testing-guide.md)；排查假绿和实现耦合时读 [testing-anti-patterns.md](references/testing-anti-patterns.md)。

## 修复与验收

永久修复落在产生偏离或拥有不变量的位置；根因结论需有连接触发、第一处偏离和症状并区分主要替代解释的证据。已授权的事故缓解可先止损，但须与永久修复分别验证和声明。根因未明时可使用 `diagnosing-bugs`；实现时保留其原场景和因果信息。

原失败场景能安全重跑且覆盖风险时优先复跑；否则说明替代证据保留和缺失的条件，区分代码修复与原环境尚未验收。回归需保留相关调用链、并发或组件交互，不以浅层假绿替代故障机制。功能绿色不证明性能未退化，单次绿色不证明 flaky 已修复。

新依赖、公开边界、配置、共享状态和生命周期应有当前消费者或运行约束支持；接口取舍不清时参考 `codebase-design`。证据仍覆盖当前内容、依赖和环境时可复用；影响结论的变化应补验。报告实际改变、观察或命令结果及未验证面。未经授权不执行生产、破坏性或发布动作；需要用户决定且工具无法取得的信息只阻塞相关工作。
