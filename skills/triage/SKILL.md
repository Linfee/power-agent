# Triage

处理尚未分诊的外来请求；已确认并进入执行图的票据不要重复分诊或降级。沿用项目配置的 tracker、分类与状态角色及 AI 披露政策，不假定固定标签存在，也不伪装成维护者。项目把外部 PR 作为请求入口时，同样分析其说明、讨论及实际 diff；按配置区分 issue 与 PR。

先读请求全文、相关讨论、既有分类和维护者决定，查项目范围、相关代码和历史记录；按概念查重，区分已经实现、重复请求、明确拒绝和暂缓。对 bug 在安全且获准的条件下复现；无法复现或信息不足时说明实际证据和缺失条件，不将猜测写成事实。PR 分析说明现有 diff 与尚待完成的行为，不假设可以检出或执行不可信代码。不要重问已解决的问题。

据证据建议不同处理：范围外附已有决定及理由；重复附关联对象；信息不足只问影响判断的具体问题；可执行请求保留目标、验收与约束，可按需使用 [agent brief](references/agent-brief.md)。需要维护者作产品或取舍决定时，明确哪些问题需要人回答；技术事实可自主核查。对历史拒绝理由的复用见 [out-of-scope](references/out-of-scope.md)。

遵循项目既有角色、标签和迁移约定；缺少非必要标签不盲目创建或套用。按项目入口读取 tracker 配置及实际命令能力；需要配置时可使用 `setup-power-agent`，缺 tracker 不阻塞普通实现或审查。只读请求只报告建议。只有对具体 tracker 目标和操作有授权时才应用分类、认领、评论、创建或关闭；已有明确授权不需逐步重复询问。发布文字遵守项目披露要求，关闭或公开评论不因生成草稿自动获准。

## 如何查找需要处理的请求

理解自然语言的范围：“哪些需要我关注”“看看这个 issue/PR”“把它移到可由 Agent 处理”“有哪些可领取”。列清单时按项目实际配置查询未分类、待评估、等待补充信息且报告者已有新回复的请求，给出数量、标题、简短摘要和对象链接；可按最久未处理优先。若包含外部 PR，标注 issue/PR 并在发现时遵守项目对外部贡献者的定义；用户明确指定的 PR 不因作者身份被忽略。已在执行图中的工作不作为新请求重新分诊。

例如收到“搜索结果为空”，先查看报告和讨论、用领域概念查已有实现和相关决定，再判断是缺陷、已有能力的使用问题还是需求。对 bug 记下运行条件、步骤与观察到的输出；安全或权限不允许执行时检查代码并说明限制。对 PR 分清作者已经完成的代码、能证明的行为和剩余缺口；运行不可信代码前先确认安全与授权。

## 分类、决定与输出

分类（如 bug / enhancement）回答“是什么”，分诊角色（如待评估、待信息、可由 Agent 或人处理、拒绝）回答“下一步由谁做什么”，与执行图的 Kind 和 State 不同。名称、迁移规则和标签取项目配置；无对应角色时用文字建议，不造标签。冲突分类或不寻常迁移先核对维护者决定，不能自行覆盖；维护者已明确决定某个角色时，无须重复讨论其产品取舍，但仍按授权处理写入。

给维护者的建议应包含：分类及理由、相关实现和查重范围、已有决定、验证结果（已确认 / 未复现 / 信息不足及证据）、推荐处理和需要其决定的具体问题。已经实现时指出证据和使用入口，不记为被拒绝；真正的产品拒绝才引用或维护拒绝理由。决定等待人工实现时说明原因，例如需要外部权限或人工判断。

信息不足时可用下面的草稿，只问改变判断的具体问题：

```markdown
## Triage Notes

**已经确认**
- <复现、代码或讨论支持的事实，附来源>

**需要报告者补充**
- <具体条件、步骤、实际输出或期望行为>
```

恢复此前会话时先读取已有 notes 和后续回复，更新已知与未知，不重问已回答问题。向 tracker 发评论、改标签或关闭仍须相应授权；按项目 AI 披露政策写明生成来源，而不假设所有项目都有同一固定文案。
