# Agent Brief

当请求需要交给其他执行者时，在已有 issue 或 PR 的约定位置写简短、可独立消费的说明；现有正文已足够时不重复造一份。

- 当前行为及期望行为；PR 要说明已有 diff 的状态与剩余工作。
- 明确的范围、约束、必要接口或既定决定；相关路径或来源确有帮助时可引用，不把偶然的行号当契约。
- 可观察、可验证的验收及非目标；复现或核验事实附来源，未知注明未知。
- 需要人决定或缺少权限的事项，不让执行者替维护者作产品决定。

以行为而不是逐步操作规定结果，让执行者自主选择实现。写回 tracker 须有相应授权，草稿不等于已发布。

## 写法与结构

Brief 可能在几周后才被执行，代码会移动。写行为契约、相关类型或接口与约束，而不是“打开某文件第 42 行加入一个 switch”。路径能帮助定位时可注明为线索，不把易失的路径和行号当成唯一契约。每条验收应可独立观察；“功能正常”“修复 bug”无法判断完成。对 PR，当前行为要描述已有 diff，目标是完成或修正它，不是忽略现有工作重做。

```markdown
## Agent Brief

**类别：** bug / enhancement，按项目词汇
**摘要：** <一行说明需完成的事>

**当前行为：**
<实际现象或现有功能；PR 说明已有 diff 的工作和缺口>

**期望行为：**
<完成后的行为，包括已确认的边界和错误处理>

**关键接口与约束：**
- <相关类型、函数、配置或行为契约，以及需改变什么>

**验收：**
- [ ] <独立可验证的结果>
- [ ] <边界或失败场景>

**范围外：**
- <容易被误认为本次一并完成的内容>

**待决定 / 权限：**
- <未决事项及其阻塞范围；没有则省略>
```

### 示例：缺陷

**当前行为：** 描述超过 1024 字符时在第 1024 个字符截断，可能切断单词。**期望行为：** 在允许长度内的最后一个单词边界截断并加 `...`。**关键接口：** 读取 skill 元数据的描述处理逻辑，不要求修改类型。

验收：不超过上限的描述不变；超长描述在单词边界结束并有省略号；含省略号的总长度不超过 1024。范围外：更改长度上限或增加多行描述支持。这里的数值是示例条件，不是项目通用限制。

### 示例：功能请求

**当前行为：** 维护者拒绝功能请求后，理由只留在已关闭 issue 中，后来的相似请求难以发现。**期望行为：** 按项目现有知识协议记录被拒绝的概念、持久理由和相关请求，分诊时按概念相似性提示维护者。若项目没有这种需求，不因本示例创建新的知识库。

验收：已授权的拒绝决定能关联原因和来源；同一概念的新请求能找到已有决定，而不是被视为无关的新问题；维护者仍可区分、确认或重新考虑。范围外：自动代维护者作相似性或拒绝决定、自动重开旧请求，以及把已实现能力记成拒绝。

### 示例：完成 PR

PR 已给 `triage list` 增加 `--json`，成功路径可序列化，错误仍是普通文本。期望复用已有序列化方式，让成功与错误输出均为有效 JSON，退出码与非 JSON 模式一致，默认人类可读输出不变。验收分别覆盖成功、错误及默认模式；其他命令的 JSON 支持不在范围内。

### 反例

“修复 triage，在主文件第 150 行附近改函数”没有当前与期望行为、可观察验收和范围，而且依赖易变行号。应先核对请求和已有代码，把缺失事实与真正需要维护者决定的选择分开，再形成可执行 brief；不知道的内容标为未知，不替维护者作决定。
