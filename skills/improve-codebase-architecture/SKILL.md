# 发现架构改进机会

先明确用户是要建议，还是已授权实施。只要求探索或建议时不修改代码、知识文件或远端状态。

从用户指出的痛点和相关调用路径入手；没有指定范围时，可参考近期变动寻找候选，但频繁修改只提示调查，不证明设计有问题。阅读相关领域词汇、现有决定和实际消费者，找出理解或修改一个行为需要跨越的模块、泄漏给调用者的细节、重复协调和难以在真实边界验证的交互。必要时用新上下文委派独立调查，不按固定人数或候选数量工作。

对每个有证据的候选，说明具体位置、实际摩擦及其触发条件、既有约束、可考虑的更简单方案，以及复杂度被删除还是转移到了调用者。比较保留现状的成本；使用删除测试判断移除模块后复杂度是消失、集中还是散落。需要设计接口时按 `codebase-design` 的边界判断处理，不以 adapter 数量、模拟测试需要或抽象数量证明价值。证据不足的地方明确标为待调查，避免凭“更优雅”立项。与现有 ADR 冲突时指出原因和重新讨论的依据，不默认推翻。

按用户问题排序并给出建议及不确定性。图有助于理解时，可参考 [可选图示指南](references/visual-report.md)；普通文字足够时无需生成报告。用户选择深入后再讨论有实际影响的约束与方案；只有实施已获授权才修改代码。
