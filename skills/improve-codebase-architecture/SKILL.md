# 发现架构改进机会

先明确用户是要建议，还是已授权实施。只要求探索或建议时不修改代码、知识文件或远端状态。

## 探索

先限定范围：用户指出模块或痛点时从它及调用路径入手；没有方向时可查看近期反复变化的区域，再沿实际调用关系展开。频繁修改只提示调查，不证明设计有问题。阅读相关领域词汇、现有决定和实际消费者；必要时用新上下文委派独立调查，不按固定人数或候选数量工作。

沿真实任务寻找摩擦，而非仅统计文件或层数：

- 理解一个概念是否要在许多小模块之间跳转？修改一项行为需同步哪些调用方？
- 某模块的接口是否几乎与实现一样复杂，调用方仍需了解内部顺序、状态或依赖？
- 纯函数是否为测试而抽出，但真实缺陷发生在调用方式和组件协作中？
- 相互耦合的模块是否把内部知识泄漏到 seam 的另一侧？关键行为能否通过当前接口观察？
- 假设删除可疑模块：复杂度真的消失、被集中管理，还是散落回各调用方？仅删除转发层不自动代表更好。

## 比较候选

对每个有证据的候选，列出涉及文件和消费者、具体摩擦及触发条件、既有约束、可考虑的更简单方案、收益和代价。指出方案是否改善 locality（修改和理解行为所需跳转更少）或 leverage（调用方无需重复承担复杂度），以及测试在哪个真实行为边界更有价值。比较保留现状的成本；区分集中复杂度和只是转移给调用者。

例如，订单提交流程的三个调用方各自排序校验、定价与保存；候选是让一个订单模块负责顺序并暴露提交行为。应先确认重复协调确实存在，再比较集中后故障语义、依赖和现有消费者会怎样变化，而不是凭文件多就合并。依赖可能是进程内实现、可隔离的本地资源或需要适配的外部系统；按真实运行性质和契约判断。只有一个实现时先假设 seam 可能不存在：一个 adapter 只是假设的 seam，两个 adapter 才说明变化真实存在；独立资源所有权、不变量或真实消费者边界可以证明单实现 seam 有价值，但不要默认新增公开多态接口。需要具体接口设计时调用 `codebase-design`。

## 生成报告

候选形成后，写一个自包含 HTML 报告到系统临时目录：`<tmpdir>/architecture-review-<timestamp>.html`，用默认浏览器打开，并告知绝对路径。报告是供人扫读的探索产物，不是实施授权。

- 开头一屏总结范围、主要摩擦和最重要的候选；顶部图例解释模块、seam、泄漏和深模块。
- 每个候选一张卡片：涉及文件与消费者、当前问题、建议变化、收益与代价、前后对照、推荐强度（例如强烈建议 / 值得探索 / 证据不足）。有冲突的 ADR 注明编号和重新讨论的具体理由。
- 用 Tailwind 与 Mermaid 的 CDN 版本快速排版和画图；图表必须与关系匹配（依赖或调用图、顺序图、层次截面、接口与实现面积对比、调用树折叠），不要每项都套同一种图。
- 图把拟议结构标为“建议”而非现状；文字在图无法渲染时仍可读，颜色不是唯一信息。使用 GLOSSARY 的领域词汇和 `codebase-design` 的架构词汇，不用实现类名代替概念。敏感代码和调用细节留在本地，不上传外部服务。
- 最后给出最推荐先探索的候选及原因；避免把“更整洁”当作理由。格式细节见 [架构候选报告](references/visual-report.md)。

## 讨论选择

不要在这一步提出具体接口设计。先问用户要深入哪个候选，或是否要调整范围；用户选定后再用 `grilling` 讨论真实约束、依赖、模块职责、seam 后放什么以及保留哪些测试。决定成形时同步处理副作用：新概念或术语变化直接通过 `domain-modeling` 更新 GLOSSARY/上下文；需要比较深化后的接口时调用 `codebase-design` 的 design-it-twice。用户以承载理由拒绝候选时，按 `domain-modeling` 的 ADR 三条件判断是否值得记录，并说明“记录后可避免未来架构审查再次提出”；临时理由（“现在不值得”）和自明理由不记录。

只在实施获授权时修改代码或知识；探索不自动授权外部动作。
