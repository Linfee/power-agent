# 界面原型

适用于布局、信息层级或交互方案的视觉比较，例如“设置页应该怎样组织”或“先看几种仪表盘布局再决定”。先写明问题和展示位置；默认 3 个结构不同的方案，最多 5 个，超过后差异会退化为噪音。

## 放在哪里

优先选择子形态 A：**在现有页面内替换待比较区域**。真实导航、内容密度、屏幕尺寸和相邻功能能暴露空白画布看不出的设计问题；保留现有数据读取、参数和权限，只切换渲染。新板块、设置页卡片或现有流程中的新步骤，也属于这一形态。

只有待验证对象确实没有可嵌入的现有页面时，才用子形态 B：遵循项目路由约定建立明确标为 prototype 的临时路由，不发明新的顶级结构。

两种形态都使用同一个浮动切换栏。

## 生成并切换方案

围绕同一目的和可用信息设计真正不同的结构：例如一版以侧边导航组织设置，另一版按任务分组。不同布局、信息层级或主要操作才构成有意义的比较；仅换颜色或文案不是。可以共享头部等固定上下文，但不要让共同布局限制每个方案的结构。

需要对比时，在同一入口提供清晰的变体切换。一个可适配框架的实现是使用 `?variant=`：

```text
variant = URL 中的 variant，缺省为默认方案
数据与安全上下文放在切换器外
根据 variant 渲染对应方案 + 标明“原型”的切换栏
切换时更新 URL 的 variant，保留其他参数
```

让每个方案的 URL 可分享、刷新后仍显示同一方案；未知参数回退到明确默认值。展示当前编号和描述，例如 `B · 侧栏布局`，上一项/下一项可循环切换。浮动栏应明显不同于待评估设计，不遮挡主要操作。若提供左右方向键，焦点在 input、textarea、select 或 contenteditable 等可编辑控件时不要截获，避免破坏输入和控件操作；修饰键组合也不应被抢占。

**生产门禁**：切换栏和原型路由/变体都应通过项目适用的构建或路由机制排除生产访问，而不只是隐藏控件。若无法证明门禁生效，不把原型合入生产路径。具体方式取决于宿主，不能假定某个环境变量天然可靠。

## 展示和收尾

交互使用隔离数据或本地替身；视觉问题不需要连真实 mutation。实际打开页面，检查切换、URL 分享与刷新、输入焦点和关键交互，记录展示环境，提供入口及各变体参数。反馈可能是“取 B 的头部和 C 的侧栏”，不必强迫整套胜出。需要保留决定依据时按主文把整套变体捕获到 throwaway branch，再清理 main 中的切换器和废弃变体。

不要直接把原型实现提升为生产代码：原型省略的错误处理、可访问性、测试和数据安全须在获授权的正式实现中重新处理。现有页面移除切换器及废弃变体；独立页面则按项目路由处理正式实现并移除临时入口。

## 反模式

- 变体只在颜色或文案上不同；真正的变体在结构上不同。
- 变体共享过多布局；共享头部可以，共享整体布局会抹掉比较。
- 把变体接到真实 mutation；问题只是“应该长什么样”时用只读数据或替身。
- 把原型直接提升为生产代码；正式实现要重新处理错误、可访问性、测试与数据安全。
