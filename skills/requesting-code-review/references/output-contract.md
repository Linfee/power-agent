# 审查输出协议（Output Contract）

`requesting-code-review` 与审查子代理之间统一使用以下 Markdown 结构：

```markdown
## 代码审查结果

状态：通过 / 通过_含建议 / 阻塞 / 需澄清
重要性等级：低 / 中 / 高
实现风险：低 / 中 / 高 / 未评估
审查强度：常规 / 增强

### 证据
- <source>（<locator>）：<summary>

### 阻塞问题
- [严重 / 重要] <issue>
  - 影响：<impact>
  - 必须修复：<required_fix>

### 非阻塞建议
- [轻微] <suggestion；无则写“无”>

### 下一步
- 继续流程 / 启动修复子代理 / 重新审查 / 升级处理
```

## 字段说明

- `状态`
  - `通过`: 无阻塞问题，可继续。
  - `通过_含建议`: 无阻塞问题，但存在改进建议。
  - `阻塞`: 存在必须修复的问题。
  - `需澄清`: 信息不足或需求歧义，需补充后再判定。

- `重要性等级`
  - 由编排器按 `risk-classification.md` 判定，用于决定审查投入，不代表当前实现危险。

- `实现风险`
  - 只描述当前实现出错的可能性，依据 diff、验证证据、复杂度与未解决不确定性独立判断；不得由重要性等级直接推导。

- `审查强度`
  - `常规` 为单审，`增强` 为两个独立审查子代理并行审查。

- `证据`
  - 必须来自可追溯信号（diff、测试输出、日志、文件定位）。

- `阻塞问题`
  - 仅包含阻塞合并/继续执行的问题。
  - `severity` 仅允许 `严重 | 重要`。

- `非阻塞建议`
  - 非阻塞建议，不得与阻塞问题混写。

- `下一步`
  - `继续流程`: 继续后续流程。
  - `启动修复子代理`: 启动修复子代理。
  - `重新审查`: 修复后重新审查。
  - `升级处理`: 连续修复-复审耗尽后升级处理。

## 一致性约束

- `阻塞问题` 非空时，`状态` 必须是 `阻塞`。
- `状态=通过|通过_含建议` 时，`阻塞问题` 必须为空。
- `状态=阻塞` 时，`下一步` 不能是 `继续流程`。
- 达到修复-复审轮次上限时，`状态=阻塞` 可搭配 `下一步=升级处理`。
- `状态=通过|通过_含建议` 时，`证据` 不能为空。
- `重要性等级=高` 时，`审查强度` 必须为 `增强`。
- `实现风险=高` 时，最终 `审查强度` 必须为 `增强`。
- 不得用未限定的“高风险”替代任一结构化字段。
