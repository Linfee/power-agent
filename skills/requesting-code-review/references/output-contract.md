# 审查输出协议（Output Contract）

`requesting-code-review` 与审查子代理之间统一使用以下 Markdown 结构：

```markdown
## 代码审查结果

状态：通过 / 通过_含建议 / 阻塞 / 需澄清
审查阶段：主审 / 主审修复验证 / 独立终审 / 终审修复验证 / 并行审查 / 并行修复验证
重要性等级：低 / 中 / 高
实现风险：低 / 中 / 高 / 未评估
审查强度：常规 / 增强

### 证据
- <source>（<locator>）：<summary>

### 阻塞问题
- [严重 / 重要] <issue>
  - 影响：<impact>
  - 必须修复：<required_fix>

### 非阻塞建议
- [轻微] <suggestion；无则写“无”>

### 下一步
- 继续流程 / 启动修复子代理 / 重新审查 / 进入独立终审 / 升级处理
```

## 字段说明

- `状态`
  - `通过`: 无阻塞问题，可继续。
  - `通过_含建议`: 无阻塞问题，但存在改进建议。
  - `阻塞`: 存在必须修复的问题。
  - `需澄清`: 信息不足或需求歧义，需补充后再判定。

- `重要性等级`
  - 由编排器按 `risk-classification.md` 判定，用于决定审查投入，不代表当前实现危险。

- `实现风险`
  - 只描述当前实现出错的可能性，依据 diff、验证证据、复杂度与未解决不确定性独立判断；不得由重要性等级直接推导。

- `审查阶段`
  - `主审` 与 `独立终审` 对完整目标范围做多维审查；`主审修复验证`、`终审修复验证` 与 `并行修复验证` 分别验证对应阶段的原 finding、修复增量和受影响路径；`并行审查` 仅用于显式并行双审。

- `审查强度`
  - `常规` 为主审收敛后通过；`增强` 为主审收敛后增加一个全新 reviewer 独立终审。显式并行双审也记为 `增强`，但不是高重要性或高实现风险的默认策略。
- `证据`
  - 必须来自可追溯信号（diff、测试输出、日志、文件定位，或通过当前 manifest 校验的命名 review asset）。
  - 引用 review asset 时必须给出权威 review run root、manifest path、资产 path，以及 scope 对 target+paths/finding、freshness、source 的校验结果；字段无效、跨 run、越界、过期或 sensitivity 未授权的资产只能报告为 evidence gap，不能支持通过结论。
- `阻塞问题`
  - 仅包含阻塞合并/继续执行的问题。
  - `severity` 仅允许 `严重 | 重要`。

- `非阻塞建议`
  - 非阻塞建议，不得与阻塞问题混写。

- `下一步`
  - `继续流程`: 常规主审或增强审查的独立终审无阻塞。
  - `启动修复子代理`: 启动修复子代理。
  - `重新审查`: 信息补齐、范围变化或无法消费当前结论时重新审查。
  - `进入独立终审`: 增强审查的主审及修复验证已无阻塞。
  - `升级处理`: 修复-复审耗尽后升级处理。

## 一致性约束

- `阻塞问题` 非空时，`状态` 必须是 `阻塞`。
- `状态=通过|通过_含建议` 时，`阻塞问题` 必须为空。
- `状态=阻塞` 时，`下一步` 不能是 `继续流程`。
- 达到修复-复审轮次上限时，`状态=阻塞` 可搭配 `下一步=升级处理`。
- `状态=通过|通过_含建议` 时，`证据` 不能为空。
- `重要性等级=高` 时，`审查强度` 必须为 `增强`。
- `实现风险=高` 时，当前输出的有效 `审查强度` 必须为 `增强`；低/中重要性即使以 `常规` 初始派发，也必须在主审 verdict 中完成升级。
- `审查强度=增强` 且 `审查阶段=主审|主审修复验证` 无阻塞时，`下一步` 必须是 `进入独立终审`；不得因初始强度为常规而继续流程。`审查阶段=独立终审|终审修复验证` 无阻塞时才能 `继续流程`。显式并行审查及其修复验证按归并规则结束，不额外进入独立终审。
- 修复验证必须产生新 verdict；不得把旧 verdict 改写为新结论。
- 不得用未限定的“高风险”替代任一结构化字段。
