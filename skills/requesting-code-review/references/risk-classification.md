# 重要性与实现风险校准指南

用于 `requesting-code-review` 选择审查策略；文件名仅为兼容既有引用。

## 重要性分级

重要性只表示“变更出错后的影响面”，用于初始派发：

- `低`：仅文档、注释、纯测试、格式或非结构化配置微调，且不影响运行时路径；常规审查。
- `中`：单模块逻辑、局部功能或 bugfix，且不触及跨模块契约、权限安全路径或持久化协议；常规审查。
- `高`：涉及公共 API / 跨模块契约、数据模型 / 持久化 / 迁移、鉴权 / 敏感数据、关键并发 / 事务语义；增强审查，主审收敛后增加全新 reviewer 独立终审。

## 实现风险

实现风险只表示“当前实现出错的可能性”，依据 diff、验证、复杂度和未解决不确定性独立判断：

- `低`：改动集中、语义直接，相关验证充分且没有未解决的关键不确定性。
- `中`：存在跨路径逻辑、局部复杂度或验证缺口，使实现出错的可能性上升，但关键假设仍可追溯。
- `高`：已有证据显示实现逻辑可能错误，或关键假设、关键路径存在重大且未受控的验证缺口。
- `未评估`：信息不足，无法作出有证据的判断。

## 实施规则

- 常规审查由一名主审 reviewer 完成；增强审查是“主审收敛后独立终审”的顺序策略，不等同于默认并行双审。
- 高重要性从主审开始即采用增强审查；低或中重要性的初始主审或主审修复验证若判定 `实现风险=高`，当前 verdict 立即升级为增强审查，主审阶段收敛后进入独立终审。
- 重要性不得推导实现风险；输出三个独立字段，不使用未限定的“高风险”。
- 发现阻塞问题必须进入修复-复审循环；修复验证优先继续提出 finding 的 reviewer，不能继续时回退为新的替代 reviewer。

## 校准场景

- 公共 API 错误响应契约调整，改动集中且回归充分：`重要性等级=高`、`实现风险=低或中`、`审查强度=增强`；主审收敛后独立终审。
- 单模块复杂改动缺少关键路径验证：`重要性等级=中`、`实现风险=高`，本轮升级为 `审查强度=增强`；主审收敛后独立终审。
- 纯文档修正且不影响运行时：`重要性等级=低`、`实现风险=低`、`审查强度=常规`。
