# 重要性与实现风险

用于选择审查策略；文件名保留既有引用。

## 两个独立维度

重要性是“变更出错后的影响面”，决定初始投入：

- `低`：仅文档、注释、纯测试、格式或不影响运行时的配置微调。
- `中`：局部/单模块逻辑或 bugfix，不触及跨模块契约、权限安全或持久化协议。
- `高`：公共 API/跨模块契约、数据/持久化/迁移、鉴权/敏感数据、关键并发/事务语义。

实现风险是“当前实现出错的可能性”，只依据 diff、验证、复杂度和未解决不确定性：

- `低`：改动集中直接，相关验证充分，无关键未知。
- `中`：跨路径逻辑、局部复杂度或验证缺口提高了出错概率，但关键假设可追溯。
- `高`：证据显示实现可能错误，或关键假设/路径有重大未受控缺口。
- `未评估`：信息不足。

## 路由

- 低/中重要性初始 `常规`；高重要性初始 `增强`。
- 低/中重要性的初始主审或主审修复验证判定实现风险高时，当前及后续主审阶段升级并保持 `增强`，收敛后独立终审。
- 常规由一名主审收敛；增强采用“主审收敛后全新 reviewer 独立终审”，不等同默认并行双审。
- 阻塞 finding 进入修复验证，优先 finding owner；不可继续时使用携带完整 repair context 的替代 reviewer。
- 三个字段独立输出，不使用未限定的“高风险”。
