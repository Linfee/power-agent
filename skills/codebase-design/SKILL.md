# Codebase Design

## 解决什么

没有这项判断时，Agent 容易为了“整洁”新增只转发调用的模块、为了 mock 创建公开 seam，或把实现细节泄漏给调用方。

本 Skill 只处理一个**具体模块簇**：使其用尽可能小的接口封装足够多的复杂度，并确定其可观察测试表面。它不决定需求、领域语言、迁移策略、计划任务或最终 Proof。

## 使用方式

### 1. 锁定模块与消费者

从变更涉及的调用方、候选模块和直接依赖开始，先回答：谁调用它、调用方真正需要什么结果、什么复杂度不应由调用方承担。已有 `CONTEXT.md` 时沿用其中术语；不存在时从代码和用户描述提取术语，不创建新的项目记忆文件。

完成判据：目标是一个具体模块簇和其消费者，而不是“改善架构”之类的泛化目标。

### 2. 先设计深模块，再决定是否拆分

- **接口**是调用方能看到、也应优先测试的行为表面；只暴露消费者完成工作所需的操作、结果、错误语义和必要约束。凡是消费者必须依赖的不变式、调用顺序、性能或资源语义，也属于接口，不能只藏在实现或调用惯例中。
- **实现**承载协调、状态、依赖细节和算法选择；调用方不应知道这些细节才能正确使用模块。
- **深度**来自小接口替调用方消去的复杂度，而不是文件数量、类数量或抽象层数。
- **locality** 越好，理解或修改一个行为越少跨越无关文件和概念；**leverage** 越高，越多调用方不必各自处理同一复杂度。

对每个候选模块运行删除测试：假设删除它，复杂度是否会清楚地回流到多个调用方？会回流，说明它可能是有价值的封装；不会回流，优先合并、内联或不创建它。

完成判据：能说明模块的窄接口、藏起的复杂度，以及删除测试为何支持保留或拒绝该模块。

### 3. 以证据建立 seam

seam 是可隔离或替换的边界，不是所有依赖都应获得的 interface。先读取 [dependency-boundaries.md](references/dependency-boundaries.md)，按依赖的运行性质和所有权选择直接组合、内部替身或稳定 adapter。

建立公开或跨模块 seam 需要真实证据：外部 I/O / 协议边界，或至少两个由需求支持的运行时实现。只有为了测试而加入的 fake，单独不足以证明需要公开 seam；优先在现有的更高层可观察行为处测试。

完成判据：每个 seam 都能说明它隔离的变化或副作用；没有证据的 adapter 被移除或保持为私有实现细节。

### 4. 交接设计约束

不使用固定报告模板。按当前任务把必要结论交给下游：

- 进入 `writing-plans` 时，将模块边界、接口、删除测试、seam 理由和接口级 Proof 写入既有 `Key Decisions` / `Proof Strategy`。
- 直接实现时，将接口和最高可行测试 seam 作为实现约束交给 `proof-oriented-development`；它仍负责运行验证与 Proof Block。
- 领域术语冲突、范围/风险取舍或迁移语义未闭合时，交回相应上游，而非在此 Skill 中自行决定。

完成判据：下游能实施并验证设计，却不需要把本 Skill 的判断重新做一遍。

## 比较替代接口（按需）

只有用户明确要求比较方案，或计划已确认存在高影响、长期稳定的接口决策时，读取 [design-it-twice.md](references/design-it-twice.md)。它不是默认流程。
