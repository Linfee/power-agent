# Codebase Design

设计深模块：让调用方通过易理解的接口使用足够多的行为，同时把应由模块承担的复杂度留在内部。先看实际调用者、需求、已有契约和依赖；使用项目已有领域术语，不为形式新建术语文件。

## 先选择是否需要新增

新增实现前按[最小完整改动](references/minimal-complete-change.md)选择可完整满足约束的最直接方案，先查项目已有实现，再看标准库、平台和已装依赖。找到合适方案就停止扩展，不为小任务额外产出设计报告；确有边界取舍时再使用下文判断。

## 理解模块

- **模块**可以是函数、类、包或一段跨层实现；它有供调用方使用的**接口**和内部实现。
- **接口**不仅是签名，还包括使用者必须知道的不变量、调用顺序、错误、配置、性能和资源责任。不要用隐藏必要语义换取表面简单。
- **深度**是接口提供的能力与它要求调用方理解的负担之间的关系，不按接口/实现行数计算。**Leverage** 是调用方获得的能力；**locality** 是相关知识、改动和验证集中在一起的程度。
- **Seam** 是可在不修改该位置代码的情况下改变行为的位置；测试切入点是观察行为的位置，两者可能重合但并非同义。**Adapter** 是在 seam 处满足接口的具体实现；内部 seam 不必公开。

用删除测试判断：删除模块后，复杂度是否消失，还是流回调用方、破坏不变量或让资源责任难以维持？只有转发而没有实际责任的层可内联；即使只有一个消费者，集中复杂算法、生命周期或不变量也可能值得保留。不要以模块数、方法数或代码行数代替整体复杂度判断。

例如一个订单计算模块只暴露「根据订单和策略计算应付金额」，内部处理优惠顺序和舍入；调用方不需要重复这些规则，接口提供的能力远大于学习负担。相反，若调用方要依次选择折扣器、调用多个步骤、自己处理舍入和错误，一个只转发这些操作的 facade 即使只有一个公开方法也可能很浅。删除 facade 后若复杂度并未回流，它就未必承担了有效责任；若删除后连接关闭与取消顺序散落各调用方，它可能虽薄却保护重要生命周期。

深度属于调用方所见接口与所获能力的关系，不禁止模块内部由多个小函数组成。内部实现、内部测试 seam 和外部接口应分开看；减少方法数也不能隐藏调用方必须知道的顺序、错误和资源语义。测试从实际行为可观察的位置进入，接口改变时仍需覆盖原有公共契约和故障机制。

## 让计算结果可以直接观察

可独立表达的计算优先显式返回结果，而不是只修改传入状态。例如：

```text
calculateDiscount(cart): Discount
  → 给定购物车，直接断言折扣结果

applyDiscount(cart): void
  → 准备可变购物车，调用后重新读取 total，
    还要区分原有总额、折扣计算和状态修改分别是否正确
```

前者把计算契约显式放在返回值，测试无需依赖整个购物车的可变状态，也更容易复用。需要实际应用折扣时，让拥有订单状态的操作使用这个结果并保护其不变量；不要为可测试性复制大对象、强行禁止副作用，或绕开事务、持久化及资源生命周期。副作用本身属于契约时，仍从真实可观察结果验证。依赖接受与替身边界由 [dependency-boundaries.md](references/dependency-boundaries.md) 说明。

## 选择边界

从消费者需要的结果和真实运行性质选择直接组合、内部隔离或稳定 adapter。只有一个实现时，先假设 seam 可能不存在：一个 adapter 只是假设的 seam，两个 adapter 才说明变化真实存在。第三方 I/O 的协议隔离、独立资源所有权或消费者依赖的不变量可以证明单实现边界有价值，但不要默认新增公开多态接口。仅为测试替身而需要替换，不能独立证明 seam 必要。按实际行为和风险选择真实组件、契约测试或替身。

依赖性质与安全加深的细节见 [dependency-boundaries.md](references/dependency-boundaries.md)。用户要求比较，或高影响、长期接口存在会改变决定的真实取舍时，读 [design-it-twice.md](references/design-it-twice.md)；无需为凑数设计候选。

给实施者说明接口、调用约束、隐藏的复杂度、边界理由与可观察验证入口；需要用户决定的取舍与代码可查事实分开。不因设计建议自动扩大实现授权。
