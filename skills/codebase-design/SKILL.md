# Codebase Design

## 解决什么

没有这项判断时，Agent 容易为了“整洁”新增只转发调用的模块、为了 mock 创建公开 seam，或把实现细节泄漏给调用方。

本 Skill 只处理一个**具体模块簇**：使其用尽可能小的接口封装足够多的复杂度，并确定其可观察测试表面。它不决定需求、领域语言、迁移策略、计划任务或最终 Proof。

## 先确认对象

从变更涉及的调用方、候选模块和直接依赖开始，回答：谁调用它、调用方真正需要什么结果、什么复杂度不应由调用方承担。已有 `CONTEXT.md` 时沿用其中术语；不存在时从代码和用户描述提取术语，不创建新的项目记忆文件。

## 模块深度

- **接口**是调用方能看到、也应优先测试的行为表面；只暴露消费者完成工作所需的操作、结果、错误语义和必要约束。凡是消费者必须依赖的不变式、调用顺序、性能或资源语义，也属于接口，不能只藏在实现或调用惯例中。
- **实现**承载协调、状态、依赖细节和算法选择；调用方不应知道这些细节才能正确使用模块。
- **深度**来自小接口替调用方消去的复杂度，而不是文件数量、类数量或抽象层数。
- **locality** 越好，理解或修改一个行为越少跨越无关文件和概念；**leverage** 越高，越多调用方不必各自处理同一复杂度。

对候选模块做删除测试：假设删除它，哪些复杂度会回流，哪些不变量或资源责任将更难保持？多个调用方共享复杂度是封装价值的一种证据；单一消费者也可能需要集中管理复杂算法、生命周期或不变量。若只少了一层转发，且没有这些实际责任，优先合并、内联或不创建。封装价值不自动证明需要 adapter、多态接口或独立配置。

## 边界证据

seam 是可隔离或替换的边界，不是所有依赖都应获得的 interface。按实际契约、运行性质与副作用选择直接组合、内部替身或稳定 adapter，代码所有权不能替代判断。依赖边界或测试隔离仍有疑点时，读 [dependency-boundaries.md](references/dependency-boundaries.md) 的分类与检查。

建立公开或跨模块 seam 需要真实证据：需要隔离的 I/O / 协议、多种已确认的运行时实现，或消费者需要独立使用的算法、生命周期或不变量契约。选择承载这些责任的最小边界；单一实现可以有稳定模块接口，不必为可能出现的变体新增抽象。只有为了测试而加入的 fake，单独不足以证明需要公开 seam；优先利用现有可观察边界。

没有证据的新 adapter 不进入设计，既有层仅在当前授权范围内调整。

## 传递结论

不使用固定报告模板。按当前任务把必要结论交给继续实施或写计划的一方：

- 给出模块边界、窄接口、封装的复杂度、删除测试结论、每个 seam 的理由与可观察验证切入点，足以指导实施；不要求下游重做设计判断，具体实现与验证方式由其决定。
- 领域术语冲突、范围/风险取舍或迁移语义未闭合时，交回相应上游（用户或当前的讨论），而非在此 Skill 中自行决定。

## 比较替代接口（按需）

用户要求比较方案，或当前证据表明高影响、长期稳定的接口存在会改变决策的真实取舍时，读取 [design-it-twice.md](references/design-it-twice.md)。无需先创建或批准计划；它不是默认流程。
