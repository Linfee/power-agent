# Design It Twice

这是高影响接口的受控比较工具，不是默认设计步骤。

## 何时使用

仅在以下任一条件成立时使用：

- 用户明确要求比较不同模块或接口方案；
- 当前证据表明接口承担高影响、长期责任，且存在会改变决策的真实取舍；消费者与兼容性约束已经足以比较。

## 方法

1. 固定消费者、必须保持的领域术语、兼容性约束与可观察验收；不要让候选方案重新定义需求。
2. 只提出在接口负担、责任边界或迁移成本上有实质差异的可行候选，数量随真实取舍决定。已有方案也是候选；没有会改变决策的替代方案时停止扩展。独立设计工作有信息价值时可交给 sub-agent，并行度由依赖与工作边界决定。
3. 用代表性调用示例比较接口负担、不变量与错误、隐藏复杂度、删除测试、locality、seam 位置、依赖策略和迁移成本。可按需要探索常用调用、最小接口或明确存在的扩展需求，但不为了灵活性凭空增加需求。
4. 选择满足约束、整体复杂度最低且边界证据充分的方案；可以组合候选中相容的优点。交付推荐及理由，已有计划或设计文档确实需要保存该决策时同步相应位置。

### 构造可比方案

先把问题空间呈现给用户或记录在当前工作上下文：谁调用、必须保留哪些行为和兼容性、资源/依赖由谁拥有、错误与取消如何传播。可用一段粗略调用草图说明约束，但标明它不是已选方案。若使用独立 sub-agent，把相关文件、耦合、依赖性质、seam 及项目领域词汇分别交给每位设计者；不要假设对方拥有当前对话。给设计者不同的真实优化目标，例如：

- 降低常用调用方的步骤和必知规则；
- 在同一小接口内集中当前分散的算法和生命周期；
- 当已有需求确实要求变化时，使扩展和迁移更容易。

没有真实扩展需求时，不为了产生方案而设计插件系统。候选可以并行独立构思，但数量由有意义的差异决定，不强制多代理或固定数目。

每个候选用同一组内容说明：

1. **接口**：类型、入口和参数，以及不变量、调用顺序、配置、错误、取消和资源所有权；
2. **调用例子**：用同一项真实任务展示调用方如何完成正常路径及重要失败路径；
3. **模块内部**：哪些规则和复杂度被封装，哪些知识仍需调用方承担；
4. **依赖与测试**：运行时组合、可替代性及资源生命周期，测试在何处观察真实行为，哪些协作需真实集成证据；
5. **取舍与迁移**：深度、locality、seam 所在位置、兼容性与迁移代价，哪些场景方便、哪些变难。

例如比较订单定价时，方案 A 暴露 `calculate(order)` 并在内部处理现行优惠次序；方案 B 让调用方逐个选择并排序优惠策略。对照相同订单和失败场景：A 的调用方负担较小，但必须明确策略由谁配置；B 只有在调用方确实拥有选择顺序的需求时才可能值得它暴露的复杂度。不能只比较方法数量，也不能把必要的配置或清理义务藏起来。

逐个呈现候选后，以同一约束比较深度、维护修改集中程度与 seam 位置，说明每种方案如何处理依赖、测试和迁移。给出明确推荐与理由；如果两个方案的优点能在保持不变量的前提下组合，可提出混合，但不让混合重启未经授权的实现范围。若缺少决定性信息，指出缺少什么以及它会如何改变选择。

## 完成判据

已经比较会改变当前决策的可行替代方案，选择理由能回到消费者和可观察约束；没有为了达到固定数量而添加候选。若证据只支持当前方案，说明其依据和仍存在的不确定性即可。
