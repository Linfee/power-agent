# 最小完整改动

先区分用户要的是建议、草稿还是已经运行的改动。建议和草稿交付内容本身；需要实施时，从受影响的调用方和它依赖的行为入手。沿项目约定可逆地推进，直到能观察到请求的结果；需要用户决定的是会改变结果的取舍或尚未授权的动作。

选能完整满足约束、总维护成本最低的做法。无需新增就沿用现状；需要实现时，优先复用项目已有写法，再看标准库、平台和已装依赖。已有实现若会丢数据或改变调用约定，就不是合适的复用对象。只为当前需求新增代码，不为将来预留开关或接口。

“最小”不按行数或实现数量算。独立资源所有权、不变量或真实 I/O 边界可以支撑只有一个实现的抽象；只有转发、没有责任的包装则不必引入。不要用短 diff 换掉必要的调用方迁移、错误处理、安全或可访问性。

按项目门禁和所选任务的要求验证实际行为；这里不额外规定统一的审查流程、代理数量或报告格式。把适用的约束传给新上下文的子代理。交付时区分已观察的结果和未验证的部分；用户指定成品格式时，在该格式内如实说明，不另附过程清单。
