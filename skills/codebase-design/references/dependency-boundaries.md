# 依赖边界与 seam

按依赖的性质决定边界，不按“可不可以 mock”决定。

| 依赖 | 默认设计 | 测试策略 |
|---|---|---|
| 进程内、确定性协作 | 直接组合；保持局部 | 通过公开模块行为使用真实对象 |
| 本地可替换逻辑 | 仅在已有真实变体时收敛 interface | 用真实变体或最小替身验证契约 |
| 自己拥有的远程组件 | 保留协议边界，不伪装成普通本地对象 | 契约 / 集成测试优先 |
| 第三方服务、文件系统、时钟等外部效应 | 在 effect 边界隔离；interface 尽量窄 | 在边界使用替身，调用方仍测可观察行为 |

## 判断 adapter 是否值得存在

保留 adapter 必须至少满足一项：

- 隔离不可控的外部效应或不稳定协议；
- 支持两个已确认、运行时会使用的实现；
- 将重复的协议、错误转换或资源管理从多个消费者中移走。

仅因为单元测试希望注入 fake，不足以创建公开或跨模块 adapter。必要的测试替身可以位于外部 effect 边界，且不扩大调用方接口。

## 加深后替换旧层

将多个浅层模块合并为更深的模块后，删除旧的转发路径，以及只断言旧私有层的重复测试。测试应通过新的公开接口验证可观察行为，而不是保留对被隐藏实现的耦合。

## 检查

- adapter 的调用方是否知道它背后的供应商、请求格式或资源生命周期？若知道，边界过浅。
- 删除 adapter 后，是否只有一处直连调用且没有重复复杂度？若是，合并通常更好。
- seam 是否比用户可观察行为更低？若是，优先上移测试，而非增加接口。
