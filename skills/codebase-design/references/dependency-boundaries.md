# 依赖边界与 seam

用于依赖边界或测试隔离仍不清楚时，按运行性质细化主文件的判断。分类帮助选择验证，不自动规定架构。

| 依赖 | 设计与测试考虑 |
|---|---|
| 进程内、确定性协作 | 通常直接组合并以真实对象验证；复杂算法或不变量可由窄模块接口封装。 |
| 有本地替身的依赖 | 可用本地数据库或内存文件系统覆盖协作；替身不自动证明需要公开 port。 |
| 自己拥有的远程组件 | 考虑协议、副作用与运行失败；根据目标选契约、集成测试或必要的边界替身，不因跨网络就强制 port。 |
| 第三方服务、文件系统、时钟等 | 按真实效应隔离供应商或协议复杂度；可以使用窄 adapter，也可直接组合；测试应保留目标所需的真实集成证据。 |

一个实现也可能承载真实协议或生命周期边界；多个 adapter 或一个 fake 均不能单独证明公开抽象必要。内部 seam 可以存在而不进入外部接口。

## 将依赖性质转成具体选择

1. **进程内**：先看哪些计算和状态转换共同承担不变量。若一组浅函数只是迫使调用方安排顺序，可在一个模块内组合，通过新接口运行真实代码；内部仍可保留小函数，不必让它们成为公开 port。进程内共享状态、并发和资源也需要真实生命周期判断，不是所有进程内对象都应直接合并。
2. **可本地替代**：如 Postgres 的兼容本地实现或内存文件系统，可让测试经过新模块接口使用替身，避免为测试把内部细节推到外部接口。确认替身覆盖了所需 SQL、事务、锁或文件语义；关键差异仍要用真实依赖验证。
3. **自有远程服务**：记录调用协议、超时、取消、重试、幂等及服务版本等约束。已有客户端已封装这些责任时可直接组合；若确有多个消费者需要同一协议隔离、故障策略或部署替换，可在拥有责任的位置定义窄接口并由 transport adapter 实现。在测试用内存 adapter 不能证明网络和协议正确，仍需针对实际风险选择契约或集成证据。
4. **第三方服务及其他外部效果**：识别供应商格式、错误语义、凭证和副作用由谁拥有。已有 SDK 足够时不强加包装；若窄 adapter 能把供应商转换及恢复策略集中在一处，测试可替换其响应，并以适当真实契约证据补足模拟的盲区。

例如订单服务调用支付网关：若每个调用者都理解供应商错误码和重试规则，可把这套责任集中到支付操作；但仅因为测试想返回一次超时，并不能推出必须在公共接口新增可插拔 `PaymentPort`。评估替代方案时连同连接/客户端的创建、共享、取消和关闭责任一起考虑，别把复杂度从实现藏到调用方。

## 加深后替换旧层

将多个浅层模块合并为更深的模块后，删除旧的转发路径和只断言旧私有结构的重复测试。将仍保护公共行为或关键故障机制的测试迁到合适接口，确认新证据覆盖后才移除旧测试；不因模块合并无差别删除。

## 检查

- 调用方是否必须知道本应由 adapter 隐藏的供应商、请求格式或资源管理细节？若是，边界可能过浅；消费者本来必须遵守的生命周期义务则应明确留在契约中。
- 测试是否耦合了契约未要求的内部结构？若是，优先观察稳定行为；重试次数、发送顺序或持久化结果本身属于契约时可直接验证，不为断言形式另造接口。
