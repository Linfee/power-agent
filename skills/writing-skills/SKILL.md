# Writing Skills

Skill 是可迁移的判断，不是一次性经验记录。**判断可迁移，结果可验证**：Skill 的价值不在每次运行走同样的流程，而在模型把判断迁移到新情境、并用与结果匹配的证据验证。

审阅或编写时，根据当前缺口检查必要问题：没有这个 Skill 时会发生什么错误、它应改变什么决策、哪些边界必须保护、什么事实能支持或推翻结构选择，以及如何观察结果是否达到。它们是审查维度，不规定固定章节、步骤剧本或输出状态。

判据拿不准或需要示例时，按需读 [criteria.md](references/criteria.md) 对应节；它承载成本模型、机制与完整定义。

## 缺口判断

- **新建**：定义行为缺口——没有这个 Skill 时 Agent 会犯什么错；写清触发场景（用户说什么、任务处于什么阶段）与目标行为（Agent 读完应做出什么不同的决策）。
- **修改**：先读当前 `SKILL.md`、相关 references、调用方和 docs，诊断**文本病灶**——按下方「五失败模式」逐行判断，不同病不同药，不裸精简；同时确认原行为缺口仍然成立。

行为缺口是“没有 Skill 时 Agent 犯的错”；五失败模式是“Skill 文字自身的病灶”——两者别混。

验收判断：能说清要建/要修什么、以及明确不做什么——新建不堆预测性规则，修改不顺手重写整套风格。

## 约束

- 不把项目一次性约定伪装成通用 Skill。
- 不在 Skill 中隐藏破坏性命令或平台私有假设。
- 不把长篇背景故事写进 `SKILL.md`。

## 承重判断

这些判断是 Skill 文字里最值钱的部分，改动时优先保护它们：

- **description 只服务触发**：触发词用“你想要这个 Skill 时自己实际会说的词”——前置、一个分支只写一次、删掉正文已有的身份复述；“要严谨”“全面”这类弱词是 no-op，换强词。长度硬上限约 110 token、目标 ~100——description 常驻上下文，超出部分每轮都在付 load；超限先删同义触发词与身份复述，不动“用于/不用于”边界信息。
- **脚本优于 prompt**：能用脚本、lint 或 schema 机械化的规则不要只写 prompt——确定性动作实现为脚本，prompt 只留给需要判断的部分。
- **渐进披露**：所有使用路径都需要的内容内联，只有部分路径用到的下沉到 references。别让长引用淹没主判断；没有步骤的扁平 Skill 全是引用是合法安排，不硬造结构；指针后的材料模型够不到时，先锐化指针措辞，失败了才回拉内联。
- **删除测试**：对每条规则问“删掉它，行为变不变”。不能表达当前行为、约束或直接 consumer 需要的文字就是 no-op，删除而不改写；每次修改做逐行相关性检查，只加不删会堆积失效规则。
- **调用方式是负载判断**：model-invoked 付 context load，只有模型需要自主触达时才值这笔钱；user-invoked（`disable-model-invocation: true`）零 context load 但付 cognitive load——description 改写成面向人的摘要，并登记到项目的人维护 Skill 索引（power-agent 仓：`AGENTS.md` 速查表）。不要用调用方式把普通 Skill 预绑成依赖链。
- **完成判据防提前交卷**：判据要可检查（模型能自己区分做完/没做完）、重要处穷尽（“每个改动过的文件都已核对”，而不是“产出变更清单”）。先锐化判据；若实际观察到提前收束，再选择合适的上下文边界或补充检查。
- **切分与合并**：只在出现独立、可自主识别的用户目标，或单一 Skill 已经无法清楚承载不同判断时切分。每次切分都花 context 或 cognitive load；合并前确认两个目标的验收不会互相遮蔽。
- **纪律防御只补真实逃逸**：直接界定行为缺口或现有契约的基础规则可直接写；仅当真实会话、review finding、正常交付或事故材料可指认 Agent 的实际回避模式时，才新增额外防御。防御写明可观察条件和替代动作；无证据不做预测性堆叠。

## 证据与验收

- **核对真实消费面**：description 改动核对 frontmatter、项目路由载体和直接调用方的触发语义一致；行为改动读取相关 `SKILL.md`、references、调用方和 docs，确认目标、约束、输入/输出契约没有冲突或遗漏；调用方式改动核对 frontmatter 标志与项目 Skill 索引一致。power-agent 仓有真实机器协议：`scripts/check-description-length.py` 校验长度上限，`scripts/check-invocation-consistency.sh` 校验调用方式标志与索引登记——涉及对应改动时运行它们。
- **路由一致**：新增、删除、改名 Skill 或改动触发词时，grep 全仓对该 Skill 的引用（AGENTS.md、docs、其他 Skill 的引用段），逐处同步——路由信息撒谎比没有路由更糟。
- **主张分级**：没有直接证据时，不把“触发更准”写成事实；已观察事实与推断分开。
- **成本边界**：优化以整条 Skill 链的 context/cognitive load 为准，不按单文件行数。

## 五失败模式

审查既有 Skill 时先诊断得了哪种病，再选配对解药；判定拿不准或需要示例时读 criteria.md §7。

| 失败模式 | 一句话症状 | 解药 |
|---|---|---|
| **no-op** | 相对模型默认行为什么都没改变；弱词也算 | 整句删除，不改写；弱词换强词 |
| **duplication** | 同一含义多处存在 | 单一事实源；重复 token 是刻意的，重复含义才是病 |
| **sediment** | 只加不删，失效规则堆积 | 每次修改做逐行相关性检查 |
| **sprawl** | 每行都活、都独特，但总长失控 | 阶梯下沉 + 切分，不是压缩文字 |
| **negation** | “不要 X”反而让 X 更可用 | 正面表述；硬护栏例外配对替代动作 |

伴随判据 **co-location**：同一概念的定义、规则、警告同居一个标题下；散落在两个以上标题下就是碎片化。
