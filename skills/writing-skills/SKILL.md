# Writing Skills

Skill 是可复用工作流，不是一次性经验记录。修改 Skill 时要像修改代码一样处理：先明确目标行为，再用压力场景验证它是否真的能改变 Agent 行为。

**根美德：过程可预测。** Skill 的存在是为了从随机系统中榨出确定性——目标是每次运行走同样的流程，不是产出同样的结果。本 Skill 的所有规则都服务这一点。

每条规则在此只有一句话表述；完整的成本核算、机制与诊断方法见 `references/criteria.md`。判据分歧按 criteria.md §9 的运行裁决处理，不辩论。

---

## Objective

### 做什么
- 创建或修改 `skills/<name>/SKILL.md`。
- 维护 Skill 与 references、docs、AGENTS.md 之间的触发和交接契约。
- 为关键 Skill 设计压力场景，验证没有 Skill 时的失败模式和有 Skill 后的期望行为。
- 优化 description 与调用方式，使触发准确且上下文成本合理。

### 不做什么
- 不把项目一次性约定伪装成通用 Skill。
- 不为能用脚本、lint 或 schema 机械化的规则只写 prompt。
- 不在 Skill 中隐藏破坏性命令或平台私有假设。
- 不把长篇背景故事写进 `SKILL.md`。

---

## Skill 设计准则

### 1. 先定义行为

修改前写清楚：
- 触发场景：用户说什么、任务处于什么阶段时应使用。
- 目标行为：Agent 读完 Skill 后应该做出什么不同决策。
- 失败模式：没有这个 Skill 时常见错误是什么。
- 输出契约：下游 Agent 或 Skill 需要消费哪些字段。

### 2. 调用方式与上下文成本

每个 Skill 二选一，任一选择都在花两种负载之一（context load / cognitive load，完整成本模型见 criteria.md §1-2）：

- **model-invoked**（默认）：模型看得到 description，可自主触发，别的 Skill 也能按名调用。代价是 description 常驻上下文、每轮都在付费——只有三个理由值得付这笔钱：模型需要自主触达；别的 Skill 需要按名调用；它是自治工作流链路的一环。
- **user-invoked**（`disable-model-invocation: true`）：只有用户输入名字能触发，别的 Skill 也够不到。零上下文成本；description 面向人类写一句话摘要，删掉触发词列表。代价是 cognitive load——人得记得它存在。这是人为能动性的价格，花在人的判断重要的地方；`AGENTS.md` 的 Skill 速查表就是本仓的 router，新增 user-invoked Skill 必须登记进去。

依赖方向固定：user-invoked 可以调用 model-invoked，反之禁止。

### 3. description 只服务触发

description 要回答“什么时候用”，不复述流程。三条硬规则：

- **触发词前置**：最重要的触发词放最前面，开头的词承担主要触发工作。
- **一个触发分支只写一次**：同义词是重复——“需求讨论 / 需求分析 / PRD 细化”是同一个分支写了三遍。保留真正不同的分支，删掉纯同义词。
- **删掉正文已有的身份描述**：只留触发条件和“别的 Skill 何时需要它”，不复述流程。

用词锚定：触发词应该是“你想要这个 Skill 时自己实际会说的词”，与用户 prompt、docs 共享同一词汇（见 criteria.md §3）。“要严谨”“全面”这类弱词是 no-op，换强词。

较好：
```yaml
description: 在收到代码审查反馈、需要判断采纳/驳回/澄清时使用。
```

较差：
```yaml
description: 本 Skill 会读取反馈、分析代码、输出表格、然后建议下一步。
```

### 4. 保持渐进披露

- `SKILL.md` 放入口、边界、流程和输出契约。
- `references/` 放模板、长 prompt、rubric、示例。
- `scripts/` 放可重复、确定性的检查或转换。
- 下沉的判定标准：**所有使用路径都需要的内容内联，只有部分路径才用到的下沉 references**。约 300 行是可参考的体量上限，不是硬指标。

三个补充判据（机制见 criteria.md §4）：
- 有步骤的 Skill 里，长篇引用内联会把步骤挤出注意力——该下沉就下沉。
- 无步骤的扁平 Skill（纯 rubric、纯词汇表）全是引用是合法安排，不要硬造步骤。
- 指针后的材料模型总是够不到时，先锐化指针措辞，失败了才把材料回拉内联。

### 5. 步骤要有完成判据

流程步骤以可检查的完成判据结尾——Agent 能自己区分“做完”和“没做完”。重要处要穷尽（“每个改动过的文件都已核对”，而不是“产出变更清单”）。模糊判据等于邀请提前交卷。

提前交卷的防御有顺序：先锐化判据；判据不可再锐化、且实际观察到 rush，才把后续步骤切出去藏住——只有子代理派发或 user-invoked 交接才藏得住，inline 的 model-invoked 调用把后续步骤留在同一上下文里，什么都清不掉（机制见 criteria.md §5）。

### 6. 切分与合并

每次切分都花一种负载，合法时机只有两个：

- **By invocation**：出现应该自主触发的独立触发词，或另一个 Skill 必须按名够到它。
- **By sequence**：后续步骤诱惑 Agent 草率完成当前步骤，且完成判据已无法再锐化。

合并的反向警告：合并两个串行 Skill 会把前者的后续步骤暴露给当前步骤，可能买回提前交卷——合并前先检查两段各自的完成判据是否足够硬。

### 7. 契约优先

跨 Skill 交接必须明确：
- 上游输入字段。
- 下游输出字段。
- 状态枚举。
- 缺失字段时如何降级或阻塞。

如果上游模板和下游 prompt 对同一任务卡的要求不同，先修契约，不靠执行时临时解释。

## 剪枝：先诊断，再选解药

改 Skill 不只是加规则，更是删。默认命运是**沉积**——只加不删，规则层层堆积直到没人（包括模型）读得完。每次修改都要问“能删什么”，不只问“能加什么”。

审查时先诊断得了哪种病，再选配对解药（详解与示例见 criteria.md §7）：

| 失败模式 | 一句话症状 | 解药 |
|---|---|---|
| **no-op** | 相对模型默认行为什么都没改变；弱词也算 | 整句删除，不改写；弱词换强词 |
| **duplication** | 同一含义多处存在 | 单一事实源；重复 token 是刻意的，重复含义才是病 |
| **sediment** | 只加不删，失效规则堆积 | 每次修改做逐行相关性检查 |
| **sprawl** | 每行都活、都独特，但总长失控 | 阶梯下沉 + 切分，不是压缩文字 |
| **negation** | “不要 X”反而让 X 更可用 | 正面表述；硬护栏例外配对替代动作 |

伴随判据 **co-location**：同一概念的定义、规则、警告同居一个标题下；散落在两个以上标题下就是碎片化。

## 压力场景与评测

两层评测，各管一段（判据见 criteria.md §9）。

**压力场景**管行为。对核心 Skill 修改，至少准备 2-3 个压力场景。每个场景包含：

```markdown
### 场景：[名称]
- 用户输入：[真实用户会怎么说]
- 无 Skill 易错行为：[具体错误]
- 期望行为：[使用 Skill 后应如何处理]
- 验收点：[可观察输出或文件变化]
```

适合压力测试的场景：
- Skill 触发边界容易误判。
- 多个 Skill 可能冲突。
- 子代理任务卡可能缺字段。
- 完成声明可能缺证据。
- destructive / branch cleanup / worktree 操作。

如果当前环境无法运行子代理 eval，仍应把压力场景写入相关文档或 PR 描述，供后续验证。本 Skill 自身的压力场景见 `references/stress-scenarios.md`。

**路由评测集**管触发。description 改动必须过 `evals/writing-skills/` 的路由评测（标注集 + judge 流程）；调用方式（invocation mode）改动不在其覆盖内——靠 frontmatter 机械核对、`AGENTS.md` 速查表同步与依赖方向人工确认。没跑过的触发声明标“未验证”，不写成事实。

**运行裁决**：“这句话改不改变默认行为”的争议，删掉它跑一次评测——行为没变就是 no-op。这是唯一裁决方式。

**成本基准**：优化与否按总路径成本（整条 Skill 链）判断，不按单文件行数。

## 修改流程

1. 读取当前 `SKILL.md`、相关 `references/`、调用方 Skill 和 docs。
2. 明确本次要修的行为缺陷，避免顺手重写整套风格。
3. 修改最小必要文件，优先修正契约、触发、输出格式和缺失 reference。
4. 检查交接链路：上游产物是否满足下游输入。
5. 检查触发与路由的一致性：新增、删除、改名 Skill 或改动触发词时，grep 全仓对该 Skill 的引用（AGENTS.md、docs、其他 Skill 的路由段），逐处同步——路由信息撒谎比没有路由更糟。
6. 若修改 Skill 内容，检查 frontmatter、插件 manifest 和相关 docs 是否需要同步更新。

---

## 完成前检查

- [ ] 新/改 Skill 的 description 能准确触发；触发词无同义重复，前置词能承担触发。
- [ ] 调用方式选择有据：命中三个付费理由之一（自主触达 / 被按名调用 / 自治链路一环）。
- [ ] 正文通过 no-op 测试：没有模型默认就遵守的句子和“要严谨”式弱词。
- [ ] 否定式禁令都是无法正面表述的硬护栏，且配对替代动作。
- [ ] 流程步骤都有可检查的完成判据。
- [ ] 切分/合并命中合法时机；引用没有埋没步骤。
- [ ] `SKILL.md` 没有残留 TODO、TBD、占位路径或旧 Skill 名。
- [ ] references 路径真实存在。
- [ ] 上下游契约字段一致；全仓对该 Skill 的引用已同步。
- [ ] frontmatter / manifest / docs 已按需同步。
- [ ] 至少有 grep、路径检查或压力场景级别的验证证据；description 改动已过路由评测或标“未验证”；调用方式改动已同步速查表。

## 输出格式

```markdown
## Skill 修改结果

状态：DONE / DONE_WITH_CONCERNS / BLOCKED

### 变更
- <修改了哪些 Skill / reference / docs>

### 证据
- [command/file] <证据>

### 风险
- <剩余风险；无则写“无”>

### 下一步
- <继续验证 / 请求审查 / 完成>
```
