# Criteria — Skill 判据体系

`writing-skills` 的 disclosed reference。`SKILL.md` 给规则和一句话判据；本文档给每条规则的完整定义、成本核算与诊断方法。审查或改写 Skill 时以当前契约、直接 consumer 与可观察的系统事实裁决分歧。

## 1. 成本模型：每个结构决策都是两种负载的交易

- **Context load**：model-invoked Skill 的 description 常驻上下文，每轮、每个会话都在付 token 与注意力。这是拆出更多 model-invoked Skill 时的刹车。
- **Cognitive load**：user-invoked Skill 从模型视野消失，人必须记得它存在、何时用——人是索引。这不是要被最小化的成本，而是**人为能动性的价格**：花在人的判断重要的地方，从不重要的地方移除。

判定：任何"要不要加 / 拆 / 改 description"的问题，先问这笔账记在哪一种负载上、值不值。两种负载都不该花的 Skill（模型不需要自主触达、别的 Skill 不需要按名调用、人也几乎不会手动跑）说明它本身该删。

## 2. 调用方式（invocation）

机制见 `SKILL.md` 改动步。一个 Skill 该付 context load 的理由只有三个，满足其一即可：

1. 模型需要**自主触达**它（如 `systematic-debugging` 在根因未知时该被自动想到）；
2. 别的 Skill 需要**按名调用**它；
3. 它是**自治工作流链路的一环**——discuss → writing-plans → implement → code-review → verification-before-completion 的自治交接依赖 model-invoked description 做路由发现。这是自治 Skill 集与“人打字驱动”型 Skill 集的关键差异：router 不靠人工索引，靠 description。

user-invoked 的 cognitive load 由项目的人维护 Skill 索引承担（power-agent 仓：`AGENTS.md` 速查表）——新增 user-invoked Skill 必须登记，改动触发词必须同步全仓引用。

依赖方向固定：user-invoked 可以调用 model-invoked，反之禁止——user-invoked 的 description 不暴露给模型，模型按名也够不到。

## 3. description 判据

`SKILL.md` 改动步的三条硬规则（触发词前置、一个分支一次、删身份描述）之外：

- **Leading word 调用锚定**：description 的用词应该是"你想要这个 Skill 时自己实际会说的词"。同一个词活在用户 prompt、docs、代码和 description 里时，模型把共享语言链接到 Skill，触发更可靠。审查时检查：触发词是用户嘴里的词，还是作者嘴里的词。
- **弱词即 no-op**："要严谨""全面"不改变默认行为，只付负载。修法是换强词，不是加句子。

争议裁决：双方对模型默认行为看法不同时，优先回到当前契约、直接 consumer 和已有系统事实；没有可观察依据时明确保留不确定性，不用猜测扩大规则。

## 4. 信息层级与渐进披露

内容按"模型多快需要它"排一条单一阶梯：

1. **SKILL.md 步骤**——有序动作，主层；
2. **SKILL.md 引用**——按需查阅的规则、定义、边界；
3. **外部引用**——`references/`（模板、判据、示例）、`scripts/`（机械化检查）、`docs/`（跨 Skill 共享的长期知识），由 context pointer 按需加载。

下沉判定（branch 测试）：所有使用路径都需要的内容内联，只有部分路径用到的下沉。三个补充判据：

- **别让引用埋没步骤**：有步骤的 Skill 里，本该下沉的长篇引用内联在 SKILL.md，会把步骤挤到注意力边缘——模型能否注意到步骤变成抛硬币。这是可预测性问题，不只是可读性问题。
- **扁平 peer-set 是合法的**：没有步骤的 Skill（纯审查 rubric、纯词汇表）全是引用是正常安排，不是坏味道。不要为"看起来有结构"硬造步骤。
- **Pointer 措辞优先于内联**：指针后的必须可达材料如果模型总是够不到，这是措辞 bug——先锐化 pointer 的触发条件措辞，失败了才把材料回拉内联。直接内联是绕过修复。

体量参考：SKILL.md 约 300 行是可参考的体量上限，不是硬指标；超过时先问阶梯是不是塌了，不是问怎么压缩文字。

## 5. 完成判据与 premature completion

完成判据两个轴，缺一不可：

- **Clarity（可检查）**：模型能自己区分"做完 / 没做完"。模糊判据（"理解达成一致"）等于邀请提前交卷。
- **Demand（穷尽度）**："每个改动过的文件都已核对" vs "产出变更清单"。demand 驱动 **legwork**——步骤内幕后挖掘的深度；它不需要步骤也能生效：扁平引用 Skill 靠"每条规则都已应用"这类穷尽判据驱动覆盖。

**Premature completion 的机制**：可见的后续步骤（post-completion steps）产生向"已完成"的拉力，判据清晰度是阻力；拉力赢了就提前交卷。

防御有顺序，不要跳级：

1. **先锐化判据**——便宜、局部，大多数提前交卷在这一步就能解决；
2. 判据不可锐化、且实际观察到 rush，**才按 sequence 切分**（§6），把后续步骤藏出视野。

**上下文边界警告**：藏步骤只在真实上下文边界的另一侧才有效——子代理派发（implement 的 worker / reviewer）、user-invoked 交接。inline 的 model-invoked 调用把后续步骤留在同一上下文里，什么都清不掉。给"爱跳步"的 Skill 加"认真点"是 no-op；切分出独立上下文才是机制。

## 6. 切分与合并

每次切分都花一种负载（§1），合法时机只有两个：

- **By invocation**：出现一个应该自主触发的独立 leading word，或另一个 Skill 必须按名够到它；
- **By sequence**：后续步骤诱惑模型草率完成当前步骤（§5），且判据已无法再锐化。

**合并的反向警告**：把两个串行 Skill 合并，等于把前者的 post-completion steps 暴露给当前步骤——可能买回一个 premature completion。合并前先检查两段各自的完成判据是否足够硬。

## 7. 五种失败模式（文本病灶诊断表）

这是 Skill **文字**的病灶，不是“没有 Skill 时 Agent 的行为缺口”——后者在 SKILL.md 诊断步定义，两者别混。审查既有 Skill 时先诊断得了哪种病，再选配对解药；不要裸“精简”。

| 失败模式 | 症状 | 解药 |
|---|---|---|
| **no-op** | 相对当前契约不表达行为、约束或 consumer 需要；弱词（"要仔细"）也算 | 整句删除，不改写；弱词换强词。分歧回到直接 consumer 与当前契约。 |
| **duplication** | 同一含义多处存在，改行为要改多处 | 单一事实源。注意区分：leading word 重复 **token** 是刻意的（提注意力），重复**含义**才是病 |
| **sediment** | 只加不删，失效规则层层堆积 | 每次修改问"能删什么"；逐行相关性检查（这行还影响行为吗） |
| **sprawl** | 每行都活、都独特，但总长失控 | 阶梯下沉（§4）+ 按 branch/sequence 切分（§6）。不是压缩文字，是重排层级 |
| **negation** | 禁令式引导（"不要 X"反而让 X 更可用） | 正面表述目标行为；硬护栏例外必须配对"那该怎么做" |

伴随判据 **co-location**：一个概念的定义、规则、警告要同居一个标题下。散落不是 duplication（含义没重复），是把一个含义碎片化到多处，读一段漏掉邻居。诊断信号：同一概念的信息出现在两个以上标题下。

## 8. Leading words

预训练中已有的紧凑概念（tight loop、red、seam、tracer bullet、fog of war），一个词锚定一整片行为区域：

- **正文里锚定执行**：同一行为每次被同一个词触发；扁平引用里，它把注意力聚焦到一类要检查的东西上；
- **description 里锚定调用**（§3）。

用法：

- 以 token 级重复积累分布式定义，不用句子复述它；
- 优先用预训练已有的词。自造术语要付定义税——首次出现必须定义，且全仓用法一致；项目有 `CONTEXT.md` 时领域词以它为准（缺失时静默继续，不预建）；
- 重构方向：发现同一概念被三处句子复述，collapse 成一个准确的词。省 token 是次要收益，主要收益是给模型一个更锐利的思维钩子。

## 9. 成本与声明边界

- 成本比较按**总路径成本**（完成任务的整条 Skill 链），不按单 Skill 行数——单文件行数下降但总链路上下文上升的“优化”是负优化。
- 对触发或行为的效果主张必须区分已观察事实与推断；没有直接证据时，不将预期写成事实。
- Skill 集跨平台分发时，调用方式与安装机制改动应核对各平台的实际配置；未核对的范围明确说明。
