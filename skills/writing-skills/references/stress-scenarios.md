# Stress Scenarios — writing-skills

用于验证本 Skill 的行为边界。格式：输入 → 无 Skill 易错行为 → 期望行为 → 验收点。

## 场景：新建一个只需要手动触发的工具型 Skill

- 输入：用户要求新建一个"初始化项目配置"类 Skill，明确说"我手动跑就行"。
- 易错行为：默认 model-invoked，写长 Triggers 列表，常驻上下文。
- 期望行为：判定为 user-invoked（`disable-model-invocation: true`），description 改为面向人类的一句话摘要，并在 `AGENTS.md` 速查表登记。
- 验收点：frontmatter 含 `disable-model-invocation: true`；description 无触发词列表；AGENTS.md 有新条目。

## 场景：给现有 Skill 加规则

- 输入：用户说"这个 skill 再补一条：验证前要检查 X"。
- 易错行为：直接追加，不检查是否与现有内容重复、是否有可删的旧规则。
- 期望行为：先定位该规则的含义是否已存在（单一事实源）；加入新规则时顺手做 no-op 测试和沉积检查，删掉失效内容。
- 验收点：同一含义只在一处；被删内容在交付说明中列出；不是纯增量 diff。

## 场景：description 堆同义触发词

- 输入：审查一个 description 为"需求讨论、需求分析、PRD 细化、产品讨论时使用"的 Skill。
- 易错行为：认为触发词越多越好，全部保留。
- 期望行为：识别为同一触发分支的同义重复，收敛为真正不同的分支；确认前置词承担主要触发工作。
- 验收点：修改后的 description 中每个触发词对应一个可区分的触发分支。

## 场景：改了 description 就宣称触发更准

- 输入：用户要求"优化一下这个 Skill 的 description，让它更容易被触发"。
- 易错行为：改完文字就直接宣称"触发率提升"，无任何运行证据。
- 期望行为：description 改动必须过 `evals/writing-skills/` 的路由评测；无法运行时，结论中把触发声明标为"未验证"，不写成事实。（调用方式改动不在路由评测覆盖内，走 frontmatter 核对与速查表同步。）
- 验收点：交付说明中有路由评测结果或明确的"未验证"标注；没有"应该会更准"式无证据断言。

## 场景：Skill 太长，用户要求精简

- 输入：用户说"这个 SKILL.md 300 多行了，帮我精简一下"。
- 易错行为：直接逐段压缩文字，不区分是 sprawl、sediment、no-op 还是该下沉的引用。
- 期望行为：先按五种失败模式诊断（见 criteria.md §7）——每行都活且独特是 sprawl（解法：阶梯下沉+切分），失效堆积是 sediment（解法：删），默认行为复述是 no-op（解法：整句删）；不同病不同药，不裸压缩。
- 验收点：交付说明列出诊断结论（哪种失败模式、在哪些段落）；改动与诊断的解药对应；不是均匀的字数压缩。

## 场景：Agent 执行流程型 Skill 时跳步

- 输入：用户反馈"这个 Skill 的第 2 步总是没做完就跳到第 3 步"。
- 易错行为：在步骤里加"要认真、不要跳步"，或立刻把 Skill 拆成两个。
- 期望行为：按防御顺序处理——先锐化第 2 步的完成判据（可检查、必要时穷尽）；判据不可再锐化且跳步仍复现，才按 sequence 切分；切分时确认后续步骤落在真实上下文边界另一侧（子代理派发或 user-invoked 交接），而不是 inline 调用。
- 验收点：先交付锐化后的完成判据；若切分，说明判据为何不可再锐化、以及切分后的上下文边界在哪里。

## 场景：合并或拆分 Skill 的请求

- 输入：用户说"这两个 Skill 都是讲 X 的，合并成一个吧"或"这个 Skill 太胖了，拆两个"。
- 易错行为：按主题相似度直接合并/按行数直接拆分，不检查切分时机与判据硬度。
- 期望行为：拆分只认两个时机（by invocation / by sequence）；合并前先检查两段各自的完成判据是否足够硬，避免把前段的后续步骤暴露给当前步骤买回 premature completion。
- 验收点：结论中写明命中哪个切分时机（或为何拒绝拆分）；合并时写明两段完成判据的检查结果。
