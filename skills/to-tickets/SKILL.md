# To Tickets

从已有目标、讨论和指定 issue 的正文及相关讨论出发，理解实际约束、术语与决定。仅当跨会话、调度或并行有收益时拆分；一个目标和验收清楚的 issue 可以直接实现，不为形式再造票。

优先切分可交付、可单独验收的端到端垂直切片，而不是按技术层拆成单独不能使用的半成品。每张票写清交付行为、局部验收、必要约束、父 spec/issue 指针和真正阻止开始的依赖；不把研究问题伪装成实现票。影响组合行为的集成工作及其依赖要明确，单票通过不自动证明整体完成。横跨全仓的机械迁移可按真实依赖分批，必要时用兼容的 expand–migrate–contract；不为形式强迫每批成为垂直功能，也不默认创建分支。

在选定 tracker 中以稳定 ID 建关系。按项目配置和实际 CLI 版本、帮助及后端版本或 tier 确认支持的操作，不猜测命令；支持 native parent/blocking 时可用 native，否则在该 tracker 条目的固定正文位置记录。同一关系只选一种可更新真源。先创建依赖目标，再用实际 ID 建边；没有 blockers 的开放任务构成可调度 frontier。若后端是本地文件，遵守配置中的 Kind、State、Blocked by、Owner，外来请求的 Triage 是独立维度，不混作任务状态。

拆分决定已明确且创建票据的授权覆盖目标时直接推进，不逐票要求批准；改变范围、交付承诺或真正未定的产品选择才交用户决定。只授权整理方案、没有 tracker 写权限或配置时，给出含依赖的草案，不擅自创建或维护第二套可独立更新的状态。已有 tracker 沿用项目配置；缺配置时按需用 `setup-power-agent`，不让它阻塞普通实现。父 spec 不因子票完成而自动关闭。
