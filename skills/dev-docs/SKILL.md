# 维护长期开发知识

按真实读者和使用时机保存未来会复用的系统事实、边界、开发方式与决策理由。沿用项目既有布局和协议，优先修订已有正文；不因为安装 Skill 要求普通文档变成 Bundle、建立 ledger 或预建知识树。局部显然的实现细节由代码与测试表达。

先核对变化事实、来源、适用范围与读者用途，区分当前事实、假设、历史决定和任务状态。研究、原型和执行轨迹不自动成为长期事实。术语和决定是否值得记录由 `domain-modeling` 的判断负责；沿用已有 glossary/CONTEXT 与 ADR，不创建第二份权威。已接受决定保留历史，授权重开时记录新决定与替代关系，不从代码反推决定已获批。

敏感资料、密钥、个人或客户标识、私有 URL query 和原始日志不进入正文、示例或引用；使用脱敏事实与可访问的稳定来源，无法核实时明确保留未确认状态。

## 按项目协议写入

普通项目遵循自己的文档与验证约定。已采用 Power Bundle 时，按[项目 Profile](references/project-docs-profile.md)处理 Concept、索引及 ADR 元数据；完整格式按需查[唯一 OKF 参考](references/okf-v0.1.md)。保留未知字段和类型，不因模板缺项而清除。新建或修改不等于验证完成；仅在需要、获授权且已有真实核验时通过 `dev-docs-maintain` 的受控工具登记，不手工刷新 ledger。

移动文档需有实际理由和授权，修复受影响入链；导航变化时更新入口。读取支撑声明的代码、测试、配置、决定和相关链接，按需扩大证据；核对关键声明、范围与引用，不能以结构检查替代语义证明。用户要求仅凭文档完成任务或已知存在误读时，以不继承当前解释的新上下文执行代表性消费任务；报告实际验证与未核实部分。
