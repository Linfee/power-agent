# 构造可区分的反馈循环

反馈循环的作用是快速判断目标症状是否出现，以及一次探针是否改变了它。它不等同于失败测试，也不要求所有问题都能在本地运行。

## 选择 observation boundary

优先复用最贴近真实症状、成本最低且能重复观察的边界：

1. 在正确 seam 上已有或可构造的失败测试；
2. 对开发服务执行 curl / HTTP 请求并断言响应或副作用；
3. CLI + 固定 fixture，对 stdout、exit code、文件或数据结果做精确比较；
4. Headless browser，观察 DOM、console、network 或用户可见状态；
5. 重放已脱敏的请求、消息、事件或 trace；
6. 只启动必要组件的 throwaway harness；
7. property、fuzz 或 stress loop，用频率和输入缩小不稳定症状；
8. 已知好坏版本、配置或数据集之间的 bisection / differential loop；
9. 生产或外部系统的日志、trace、事件 ID、快照与真实副作用差分；
10. 最后才使用结构化 HITL，由人执行最小动作并返回同口径观察。

顺序是启发式，不是固定菜单。选择能最大幅度降低当前不确定性、且不越过安全和授权边界的方法。

### 将观察做成可重复步骤

先把用户说的「订单有时失败」具体化：哪个入口、什么输入类别、期望和实际结果、环境及时间窗口？找到相关的现成失败输出；如果安全且可行，保留命令、退出状态、响应中与该症状有关的字段以及成功/失败对照。例如，若问题是订单被接受但状态未更新，单独检查 HTTP 200 会漏掉它，应再观察同一订单的状态或用户可见结果。

开发服务的示意请求如下；仅对已授权的非生产环境和无副作用的端点使用，实际凭证通过现有安全机制提供，不写入命令或 artifact：

```sh
curl --silent --show-error \
  --header "Authorization: Bearer $DEBUG_TOKEN" \
  "$DEBUG_BASE_URL/orders/$DEBUG_ORDER_ID"
```

这里环境变量应由安全渠道预先提供，不在聊天中输出赋值语句或展开后的命令；也不要启用会显示认证头的 shell tracing、curl verbose 或共享终端记录。响应可能含个人信息：先本地筛选、脱敏，再只展示例如 `status: pending` 与预期 `confirmed` 这类足够判断的行。检查敏感数据读取、网络访问及请求是否产生副作用的授权；不确定时用无敏感 fixture 或现有脱敏 trace。若仅能获得脱敏输出，列出实际观察及其环境限制，不凭示意结果声称跑过命令。

CLI 场景可固定 fixture、比较 stdout 与独立的已知结果，并同时记录退出码；浏览器场景可断言具体 DOM 状态，同时观察 console/network 中与同一操作关联的信号。重放 trace 时保留顺序与关联 ID，并确认脱敏未改变关键字段；harness 隔离掉不相关服务时，记录 mock 掉的边界，避免把需要真实协作的故障隔离掉。

## 收紧 loop

已有 loop 后继续检查：

- **精确**：断言用户报告的症状，不以“没崩溃”或退出码 0 替代业务结果；
- **可区分**：结果能支持或排除至少一个当前解释；
- **可重复**：记录命令或 observation boundary、输入、环境和前置条件；
- **稳定**：固定或记录时间、随机种子、并发、依赖和外部状态；
- **快速**：缓存无关初始化、缩小输入和组件，但不切断真实失败机制；
- **安全**：脱敏敏感值，不为调试扩大权限或改变生产安全语义。

本地不可运行时，“收紧”可以表现为提高 trace 关联度、保留同一事件链、获取可比较的成功/失败 artifact，而非强造本地失败测试。

## 最小复现

最小化用于缩小假设空间。按诊断价值缩减输入、调用者、配置、数据或步骤，用同一 loop 检查是否仍保留故障机制。逐项移除、二分缩减或有依据的分组都可采用；达到足以定位和验证的规模后即可停止，不以“每个元素都不可再删”为完成门槛。

记录 minimal 保留和省略了什么，并映射到 original。original 的故障条件与用户结果是验收锚点，复跑与替代证据按主 Skill「修复与复验」判断；minimal 是否重跑取决于它能增加的机制、边界或回归证据。

## 竞争解释与探针

高歧义时使用以下轻量记录；不要求固定候选数量：

| explanation | prediction | probe | observation | verdict |
|---|---|---|---|---|
| 若 X 是原因 | 改变 Y 后症状应消失或增强 | 控制或记录相关变化，检验 Y 的影响 | 实际结果 | supported / weakened / rejected |

单变量实验便于归因，但不限制所有探针的形状。版本或配置集合可二分；怀疑因素交互时可做受控组合。选择成本相称且能区分解释的实验，记录变化集合、对照和预测，使结果可归因；结果含混时再缩小范围或增加对照。没有可证伪 prediction 的解释仍是猜测；日志数量增加但不能区分解释，不算进展。

例如失败请求的日志显示「收到旧配置」，候选 A 是缓存未失效，候选 B 是配置服务本身返回旧值。若 A 成立，同一请求的配置服务响应应已是新值而应用读取仍旧；若 B 成立，响应本身就是旧值。对同一次操作关联配置服务响应与应用入口值，比单纯增加请求日志更能区分两者。若看不到服务响应，先提出该候选和预测、分析已有 trace 或寻找合法观测方式，不必等可运行红命令才开始推理。

将候选按观察支持度和探针成本排序，简短说明排序与下一步给用户，邀请补充最近变更或已排除因素，同时继续不依赖回复的安全调查。探针返回与预测相反时调整排序；若结果同时符合多个候选，记录未区分而不是宣布根因。

## Flaky 与性能

Flaky 的目标是获得可比较的复现率，而非一次干净失败。记录失败频率、样本条件和受控变量；stress、并行或 sleep 只能作为探针，并需说明它们如何改变系统。单次绿色不能证明根因或修复。

性能问题先定义同 workload、环境、指标和测量边界的 baseline。profile、query plan 或 bisect 用于区分原因；功能正确不能替代性能证据。详细约束见 `performance-and-flakiness.md`。

## 临时 instrumentation

只有现有观测无法区分解释时才增加 instrumentation，并让每个观测点对应一个 prediction。使用唯一、可搜索的 tag，例如 `[DEBUG-a4f2]`，控制采集范围并脱敏。

结束前按 tag 或明确路径检查本轮观测产物，移除无用代码并停止临时运行；按主 Skill 的授权与复验需要保留安全材料。记录实际位置、敏感性/安全影响与处置，保留时说明用途和后续责任；没有临时产物时无需额外扫描或填字段。

## 无法建立有效 loop

明确列出已经尝试的 observation boundary 和失败原因。请求能真正解除缺口的最小条件，例如环境访问、脱敏 HAR/trace/core dump、带时间戳的录屏，或新增最小生产观测的专项授权。没有区分性 observation boundary 时如实报告仍在调查中，或在调查动作受阻时停下说明缺口，不要靠代码阅读直接升级为根因。
