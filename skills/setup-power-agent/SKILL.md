# 配置项目 Agent 入口

只补影响当前 Agent 工作的缺口。先识别宿主实际加载链、现有入口、构建与验证命令、知识位置和 tracker；从项目证据确定内容，保留已有编辑。已有 `AGENTS.md` 是权威入口、`CLAUDE.md`/`GEMINI.md` 转引它时，只更新 AGENTS，不向指针文件复制另一套规则。入口只链接实际存在的项目资料及实际安装位置可定位的 Skill，不假设业务仓库有 `skills/`。缺少配置也不阻塞普通实现与审查。

## 先查看现状

在决定写什么之前，按当前需求查看现有材料，而不是套默认模板：

- 入口：实际宿主会加载哪些 `AGENTS.md`、`CLAUDE.md`、`GEMINI.md`；哪些是正文、哪些只是引用？是否已有相关小节和用户修改？
- 工作方式：项目已有的构建、测试、检查入口在哪里，是否已有 tracker 配置或本地任务目录？远端地址指向什么服务和项目，是否为 fork？
- 领域与文档：寻找现有 glossary、CONTEXT、领域地图、相关 ADR、项目文档索引及其协议；查看跨上下文的真实资料，不因发现目录或 monorepo 配置就认定必须建立多上下文。
- 消费者：哪些已安装入口确实需要 tracker、分诊角色或领域资料，现有导航能否让它们找到对应信息？

总结已有内容和真正缺口；只有后端、目标仓库或项目约定等无法从证据确定且影响接下来配置时才问用户。`CONTEXT.md` 不是必须迁移的旧格式；保留已有权威位置与名称。

## 检查插件默认规则

仅在本次范围包含 Power-Agent 默认规则时，按随本 Skill 安装的[宿主兼容性指南](references/agent-compatibility.md)检查目标宿主是否已安装并启用 Power-Agent 插件或包，以及宿主的信任和加载条件；规则与 25 个 Skill 随同一插件分发，不向业务项目复制或生成规则块。安装或修改用户配置、批准信任前确认具体授权。

在获授权的隔离环境中，分别确认默认规则进入上下文、Skill 发现和适用的子代理传递；只能验证其中一层时如实说明，不把安装或文件存在当作已启用。

## 设计入口与指针

优先更新真实加载的现有入口中的相关段落，不覆盖周围内容或重复追加一套。若没有入口且宿主加载约定不能确定，先确认目标文件；不因模板习惯再创建一份与已有权威入口竞争的文件。

入口只需要简短的消费指针，例如：

```md
## Agent 工作资料
- Issue tracker：<实际后端与项目>；读取和操作约定见 <实际路径>。
- 分诊角色：外来请求需要分诊时，查阅 <实际路径>。
- 领域资料：涉及 <适用领域> 时，读取 <实际术语文档及相关决定路径>。
```

仅写实际需要且存在的指针；现有入口已清楚覆盖时无需重复创建配置。相对链接从消费者所在文件解析，确保实际宿主能找到资料。指针不复制领域定义、决策历史或任务状态；已有文档仍是唯一真源。

复用已有 glossary/CONTEXT、ADR 和知识导航，不预建空文档。领域与决策缺口见[领域指针](references/domain-docs.md)；具体语义由 `domain-modeling` 负责，采用 Bundle 时写入格式按 `dev-docs` 的 profile。普通 docs 不强制 Bundle 或 ledger；Bundle 中生成的 `docs/agents/*.md` 同样须有非空 `type`，不能原样写入无 frontmatter 的 seed。

## 选择 tracker 并写入项目配置

仅在需要 tracker 配置或用户要求时，优先沿用项目实际选用的 GitHub、GitLab 或本地后端；证据不能确定真实后端时才询问。沿用已有配置位置，无约定时写 `docs/agents/issue-tracker.md`。按实际后端选择本 Skill **安装目录**内唯一对应 seed，替换为项目真实位置、版本与操作约定：

- [GitHub](references/issue-tracker-github.md)
- [GitLab](references/issue-tracker-gitlab.md)
- [本地文件](references/issue-tracker-local.md)

仅在需要时生成 [triage 标签角色](references/triage-labels.md)或[领域资料指针](references/domain-seed.md)，分别写入现有约定位置或 `docs/agents/triage-labels.md`、`docs/agents/domain.md`。映射现有分诊、ready 和对象类型角色；不盲建标签，不假设未配置标签存在。现有约定足够时不生成重复文件。

如果现有 tracker 是其他服务（如 Jira 或 Linear），记录项目实际使用的定位、读取、创建、更新及依赖工作方式，不硬套 GitHub/GitLab。需要用户补充时，询问实际项目和简要工作流，而非要求重新设计团队流程。尚不能确认远端目标或 CLI 可用时，明确未核实部分；不为凑完整性初始化 Git、添加 remote 或执行远端操作。

用所选 seed 时：

1. 写明具体目标、如何定位任务与查询状态，以及任务如何表达父子和阻塞关系；实际后端的关系能力不同，只选一个真源。
2. 根据已核对的 CLI 或项目约定记录读取、列出及授权后的创建、评论、更新、关闭方式。命令须指向目标项目；fork 场景尤其要区分 upstream 和用户仓库。
3. 沿用现有角色映射。只有消费者确实需要且尚无映射时，写入分诊或调度角色、实际字段值和用途；标签是否存在或能创建需单独核实和授权。
4. 若入口缺少导航，添加指向这些配置的简短条件指针；消费者应能据此找到后端、关系与角色，不需要再去猜 seed 中的占位符。

例如，本地 tracker 的项目配置应说明实际目录和稳定 ID 的生成方式，以及 `Kind`、`State`、`Blocked by`、`Owner` 分别如何读写；远端 tracker 应说明实际仓库、native 关系或正文关系的选择。不要把文件示例中的 `|` 选项原样写进实际条目，也不要将本地快照与远端状态同时作为可编辑真源。

项目配置应写清后端、目标、读取/创建/更新约定、关系的唯一真源、已有状态及授权边界。命令只在核对本机 CLI 版本、帮助与必要官方契约后写成项目可用操作，源 seed 不保证任意版本可执行；native 关系不可用时按同一 tracker 的固定正文位置记录。远端写入、labels、权限、初始化 git/remote、用户安装目录或敏感配置须有覆盖具体对象和操作的授权；只创建本地入口不推断外部授权。

## 完成

核对真实加载链、新入口和项目指针可达，声明有证据支持；Bundle 产物符合相应元数据。记录实际修改、运行过的检查及无法核实的环境。需要语义写入、扫描维护或整体导航设计时按需使用相应能力，不强制链式执行。
