# 决策记录

ADR 保存未来工作需要、却不容易从代码或当前状态恢复的背景、决定和理由。考虑未来读者、改变成本、是否容易误解、真实约束和替代方案；这些是判断价值的线索，不是需要同时满足的门槛。可逆但重要的运维或边界决定也可能值得记录；普通界面偏好、临时选择和代码已清楚表达的显然细节通常不需要 ADR。

沿用项目已有位置、格式和编号；没有约定时，可以在 `docs/adr/` 按已有最大编号递增建立 `0001-short-title.md`。只在真实决定值得记录且写入获授权时创建目录和文件。内容可以很短：背景、决定、理由，以及对未来读者有价值的约束、备选方案或后果。不要为了模板填充空章节。

无既有模板时，一段也可以：

```md
# Ordering 与 Billing 通过领域事件通信

两者需要独立处理订单和付款。我们选择领域事件而非同步 HTTP，
以避免付款系统暂时不可用时阻塞下单；事件消费者必须处理重复投递。
```

可选的状态、备选方案和后果章节只在有实际信息时添加。例如，记录“手写 SQL 而非 ORM”的原因，可以防止后来者把有意选择当成遗漏；记录禁止使用某云服务的合规限制或合作方要求的响应时间，可以让读者理解代码中不可见的约束。

值得考虑记录的其他例子：事件溯源的写模型与投影读模型、跨上下文的数据所有权和仅按 ID 引用的边界、替换代价高的数据库或消息系统、以及曾认真考虑但因不明显理由拒绝的替代方案。普通库选择或显而易见的局部实现通常不必记录。

修订已接受的历史决定前确认用户已授权重开；用新决定和明确的 supersession 关系保留历史，不因当前实现与旧记录不同便推断新决定已获采纳。普通项目遵循已有生命周期约定。

如果项目采用 Knowledge Bundle，写入和取代关系必须遵循 [dev-docs](../../dev-docs/SKILL.md) 的项目 profile：ADR 使用 `type: Decision`、`verification.strategy: historical` 和有效生命周期关系。不要把上游不含 frontmatter 的裸模板直接写进 Bundle；不需要为了格式职责再委派一个 Agent。
