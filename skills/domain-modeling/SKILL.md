# 领域建模

在设计和讨论中主动澄清项目特有的概念、关系与边界，维护能够供未来工作使用的一致语言。先寻找项目现有的领域文档、词汇表、CONTEXT、上下文地图和相关 ADR；依据内容与已有权威位置，而不是文件名，确定修改位置。已有 CONTEXT 或 glossary 时复用它，不再建立另一份同义术语真源，也不机械迁移既有文档。

- 对模糊、同义或与现有定义冲突的词，提出清晰命名并说明差别；结合具体场景、边界案例与相关代码核对。代码当前行为与讨论的目标不一致时，区分现状与期望，不能把任一方未经确认地写成事实。
- 同一概念在同一业务上下文内保持一致；不同真实上下文可以有同名异义，明确各自含义及关系，不为统一名称抹平差异。上下文边界由领域和实际消费者决定，不按目录或服务数推断。
- 已确认且有未来读者的领域知识，按用户授权在既有位置更新；不收录普通编程术语，不把词汇表当任务记录或实现方案。没有既有约定且确有知识要保存时，按 [词汇格式](references/glossary-format.md) 按需建立 `GLOSSARY.md`；只有多个真实上下文需要导航时才建立地图。
- 需要保留未来读者无法从现状恢复的决定理由或约束时，参照 [ADR 指南](references/adr-format.md) 记录。难逆、反直觉和真实取舍是价值线索，不是必须全部满足的条件；可逆但重要的运维理由也可能值得记录。普通偏好和显然的局部细节不必建 ADR。

写入沿用目标项目的文档协议；采用 Knowledge Bundle 时，遵循 [dev-docs](../dev-docs/SKILL.md) 的项目 profile，包括所需元数据和决定生命周期，不能直接将无 frontmatter 的示例写入 Bundle。语义由本 Skill 判断，格式由 dev-docs 的适用规则决定；当前执行者已掌握这些规则时直接完成，不必每次委派或重新调用。仅讨论、只读或未授权写入时，在对话中给出拟议知识，不修改文件；已授权并有价值时及时落到唯一权威位置。
