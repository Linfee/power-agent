# Writing for Agents

为 Agent 写作时，先确定读者要完成的目标，以及现有材料缺少哪些会改变行动、判断或验收的信息。修改时读取受影响的正文、引用和直接消费者；用户目标、授权和项目现有契约决定边界。不要为统一格式增加流程。

## 指针与内容

- 指针说明材料解决什么问题、什么情况下读取，并指向实际可达的位置。description、项目入口中的导航和正文引用都承担这一作用；区分不同场景，删掉重复同义词和身份介绍。
- 入口保留完成常见任务必需的判断、授权和完成条件；只有部分场景需要的细节放在带明确触发条件的 reference。不要把必需边界藏在没有有效指针的文件里。比较整条实际阅读路径的成本，而不只是主文件长短。
- 将相关规则、例外和操作放在一起；复用权威来源，避免把可从项目配置或命令直接查到的事实复制成易过期的缓存。写明可观察的完成条件和相应证据，不靠口号或固定步骤代替判断。
- 删除不改变行动、边界或验收的文字，同一消费路径内合并重复；但保留安全、授权和机器协议。某句是否只是模型默认行为，应通过当前模型与宿主的实际表现判断，不能仅凭直觉。机械、重复且可确定裁决的约束优先放在真实可运行的检查中。

### 信息层级与上下文成本

一份文档可以主要是按顺序执行的**步骤**、按需查阅的**参考**，也可以混合两者。区分三个位置：

1. 正文中的步骤：接手当前任务的人需要做什么、顺序和完成结果是什么。
2. 正文中的参考：多数使用者要查阅的定义、规则和例外；例如代码审查的规则集可以平铺，不必硬排成步骤。
3. 指针后的独立 reference：只在某个分支需要的操作或背景；说明触发条件和路径。

放得太浅会使入口难以查阅，放得太深则可能使任务必需的边界不可达。判断时追踪具体任务会读取的整条路径：所有分支都需要的放在可见位置，只有特定分支需要的可下沉。将概念的定义、规则和例外放在相邻位置；分散是把一个意思拆得到处都是，重复则是多处写同一意思，两者要分别处理。

常驻入口和 description 占用每次加载的上下文；按需文件仍需要一个足够明确的指针。人还需要知道有哪些材料以及何时使用：不能只把成本从上下文转嫁给读者。先让指针说清材料和不同的适用分支；若实际消费路径仍漏掉必需内容，再考虑在入口内联或重新组织，而不是假定某种措辞必然有效。

### 完成条件与步骤拆分

检查每项工作如何判断完成：

- **清晰度（clarity）**：读者能否区分完成与未完成？“理解已经达成”不如“列出已确认的边界、仍有分歧的问题及其证据”可检查。条件应与任务实际结果匹配，不要求每次固定报告。
- **要求范围（demand）**：条件覆盖多少必要工作？“列一份变更清单”不等于“每个被修改的模型都已列出并说明影响”。同样，平铺的审查规则也需要说明哪些规则适用于本次范围及如何处理发现，而不只关注有序步骤。

观察到工作提前结束时，先核对完成条件、实际证据、授权和引用可达性；必要时再拆分真实独立的阶段。交接或子代理派发会形成新的上下文，而在同一上下文内增加一个标题或调用并不会自动隐藏后续内容。拆分应有明确的责任、输入和完成结果，不靠“隐藏后续步骤必然改善表现”的未经验证假设。

### 概念命名与精简

给反复出现、确实改变判断的概念一个简明名称，并优先复用项目或领域已有、读者可理解的术语。首次使用时解释其操作含义，正文、指针和相关示例保持一致；不要把含糊形容词当作可验证标准。例如，与其说“可信的反馈循环”，可以在需要时定义“红灯”：目标缺陷存在时，所选检查以预期方式失败。又如“快速、确定、低开销的反馈”可以简称“紧反馈循环”，但仍需说明适用的运行条件。名称是沟通工具，不保证模型会因某个词产生特定心理行为。

检查文档时，把每个意思集中在权威位置；项目脚本、配置、目录和 `--help` 也是事实来源，不必复制容易过期的命令清单。保留从环境无法直接得知的约定、理由和陷阱；查找成本确实高时才考虑注明缓存及其更新责任。逐句问它是否仍服务当前任务：删除过时、重复或实际不改变行为的内容，而不是只修短句子；对默认行为有争议时用行为对照而非猜测裁决。

禁止条款若有具体安全或授权边界，应保留并说明可执行的替代动作；一般指引也可以先写期望行为，让读者知道该做什么。不要声称否定句必然使模型执行被禁止行为。

## 写 Skill

Skill 需要明确用户目标与行为缺口；description 用用户实际会说的场景表达触发条件，保持简短而可区分。正文提供达成目标所需判断，避免强加固定报告、人工停顿或无关流水线。拆分看是否有不同的实际消费需要；合并要保留各自验收。整包可按需具名调用其他 Skill 或读取其权威 reference，不承诺单独安装仍完整；依赖和触发条件必须清楚、安装后可达。按需查阅 [Skill 调用与发现](references/skill-mechanics.md)。

检查修改涉及的正文、链接、示例与直接消费者。结构检查能发现路径和元数据问题，但不能证明 Agent 会正确行动；需要判断精简、发现性或行为变化时，以相同任务、模型、宿主、工具和授权比较实际结果与整条路径成本。不要把规则复述当作行为证据，或把未经验证的措辞、注意力和提前完成机制写成事实。文本取舍与行为对照细节见 [按需判据](references/criteria.md)。
