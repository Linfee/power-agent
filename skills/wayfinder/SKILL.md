# Wayfinder

目标笼统或路线仍有关键未知时，先画低分辨率地图：目的地和边界、已定决定及来源、当前可明确表述的问题、仍在范围内但尚不能具体化的未知，以及明确不做的事。简单且路线清楚的工作无需建地图。地图是索引，决定及其依据保存在一个权威位置，避免与 ticket 复制成两份可独立修改的结论。

决策 ticket 回答问题，实施 ticket 交付行为；二者不混用。只把问题已足够清楚的事项列入决策图，依赖未解处保留为未知。维护真实 blocker 和 ready frontier；结果揭示新问题时再细化。技术事实由 Agent 按需研究或原型验证并标明证据；产品偏好、取舍和授权边界由用户决定，不替人回答。需要人决定时只暂停受阻支路，继续独立研究；不限制每次会话只能解决一个决定。

若需要跨会话协调，地图与决策使用项目配置的唯一 tracker 和关系表示；同一关系以 native 或正文其一为真源。按实际配置表示 map/decision 类型，不假定标签存在，不将外来请求的分诊状态当作决策类型。本地任务图由一个协调者写状态；多会话缺少可靠原子认领时串行协调，不把 assignee 或写标记后重读当锁。研究成果可按项目合适位置保留并由地图引用，不强制新建分支、提交或 push，也不将未证实摘要当事实。

默认先解决决定而不是偷做实现。若用户请求的是持续交付且目标和必要决定已清楚，在授权范围内转入 spec、票据或直接实现；仅请求探索、建议或草稿时停止于该结果。创建、认领、修改或关闭 tracker 对象以及发布研究结果各自需要覆盖目标和动作的授权；未授权时提供草稿或报告，不阻塞可安全进行的只读研究。缺少 tracker 时可先在当前会话形成地图，只有确需持久协作时按需使用 `setup-power-agent`。父地图不因子项完成自动关闭。

## 低分辨率地图

先命名目的地：这次要找出通往什么结果的路？它可以是供实施的 spec、待锁定的决定，也可以是在原地完成某项迁移；目的地决定范围和何时算路线清楚。先广泛扫描整个问题空间，找出已知决定、可清楚提出的问题、暂时说不清的区域和范围外事项，不要先深入一个分支就假装已经画完全图。若路线已经清楚、任务也足够小，直接按用户授权推进，不建地图。

跨会话地图可采用下面的内容，具体位置及字段服从 tracker 配置：

```markdown
## 目的地
<一两句话说明要到达的结果>

## 背景和约束
<领域、既有决定及来源、持续适用的偏好>

## 已作决定
- [<决定名称>](<权威记录链接>)：<供判断是否相关的一句话>

## 尚无法具体化
- <仍在范围内、依赖未来决定才能说清的问题区域>

## 范围外
- <排除的工作及理由；如有相关对象则链接>
```

地图让新会话先看全局，再按需展开决策、研究或原型；不是把所有票据正文复制进来。人读的说明中用有意义的名称包住链接，而不是只给一串 ID。唯一 tracker 是任务状态源，地图只提供索引；某个决定的详细内容和依据保存在一个权威位置，地图只保留定位用的摘要和指针。

## 哪些是问题，哪些仍在迷雾中

判断能否建决策票的标准是**现在能否准确提出问题**，不是是否已经知道答案。问题清楚但被别的决定阻塞，可以建票并记录真实依赖；连问题都说不清，则留在“尚无法具体化”，不要预先切成看似精确的票。已决定、已建票、范围外各自不属于迷雾。

例如目的地是决定报表导出方案：“导出是否必须支持离线访问？”已是具体问题，即使要等合规调查也可记录依赖；“将来如何处理大数据量”若连使用场景和限制都未知，就先留作待厘清区域；“重新设计整个后台”若已排除，则记录在范围外而不是待研究。一个决定可能让迷雾区域细化成多个问题，也可能发现它根本不是问题。

范围外表示有意识地不做，不因后续研究自动变为待办。若现有票经判断越过目的地，在获得相应 tracker 写授权后依项目协议移出可调度范围，并记录理由和链接；它不是已完成的路线决定。改变目的地时重新评估范围，不暗中扩张当前承诺。

## 问题类型和处理方式

- **研究**：要找出可以查证的事实，例如目标 API 的版本限制。给研究者具体问题、来源和所需证据；独立研究可并行，结果引用可访问的一手资料并记录未知或冲突。研究结果回答事实，不自行替用户作产品决定。
- **原型**：问题需通过具体画面或可运行行为讨论，如“导出进度如何呈现”。构建合适保真度的原型并关联准确版本，让相关人员基于它决定；原型不是生产实现或行为验收的替代。
- **共同澄清**：存在影响结果的偏好、取舍或领域歧义时，与用户讨论并确认共同理解。用户必须自己表达其选择，Agent 不能代答；按需结合领域术语和已有决定。
- **解锁任务**：本身不是决定，但必须做完才能决定，例如取得允许访问的测试环境、检查一份获授权的数据样本。写清它解锁什么、谁能做、何时完成和所产生的事实；需要人工权限时给明确操作清单，不把申请权限当成已经授权。

一个具体问题可这样表达：

```markdown
## 问题
<需要决定或查证的具体问题及其与目的地的关系>

## 背景和约束
<已知事实、相关决定或研究来源>

## Blocked by
<真正阻止开始的对象；无则 None>

## 完成时
<记录答案、理由和证据的位置；若为解锁任务，记录做了什么及可供后续使用的结果>
```

按项目配置表示类型与关系：本地 `Kind`、`State`、`Blocked by`、`Owner` 各司其职；研究等是问题的处理方式，不能混作外来请求的分诊状态。依赖可用原生边或固定正文位置之一；先创建对象取得真实 ID，再连边，避免占位编号误链。对象是否是子项遵守后端能力，不虚构固定标签。

## 推进地图

从地图及 tracker 读取已知状态，选择用户指定或可开始且无占用冲突的具体问题，按需展开关联记录；不必读取全部历史正文。研究和不冲突的工作可并行，人需要作决定时继续独立支路。每解决一个问题，在权威位置记下结论、依据、原型或研究链接，地图只加可定位的一行摘要；有授权时按 tracker 协议更新状态。检查新结论是否解锁问题、使某些问题无效或让迷雾变得可具体表述，再更新真实依赖与 frontier。

例如先研究 API 的离线能力，再让用户决定是否要求离线导出；研究可与互不依赖的界面原型并行。若研究表明离线不可行，记录证据并提出取舍，不直接把“取消离线”当作用户决定。路线已清楚且用户授权交付时，直接转入适合的实施路径；仅要求探索时交付地图、答案和剩余决定即可。
