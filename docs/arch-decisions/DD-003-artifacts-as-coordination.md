# DD-003: 产出物作为协调介质

## 背景

Skill 之间需要协调和传递信息。需要决定长期状态与跨阶段上下文的协调机制：仅靠直接调用、共享内存、还是通过版本化产出物。

## 约束

- 协调过程必须可追溯、可版本化
- 下游 Skill 无需了解上游实现细节
- 产出物对人类和 Agent 都可读

## 方案对比

| 方案 | 优势 | 劣势 | 复杂度 |
|------|------|------|--------|
| A: 仅靠 Skill 直接调用 | 低延迟 | 紧耦合、不可追溯，难以恢复 | S |
| B: 共享内存/状态 | 灵活 | 难以版本化、调试困难 | M |
| C: 产出物（文件）协调 | 可追溯、可版本化、松耦合 | 需要约定文件格式 | M |

## 决定

选择方案 C：跨阶段状态通过可追溯产出物传递。默认链路中，discuss 的已批准需求结论由 writing-plans 折叠进 exec-plan；只有用户或流程明确需要时才额外落盘 spec 文档。exec-plan 文件、代码变更、docs 文档构成主要产出物链。编排型 Skill 可以在流程中使用下游 Skill，但必须通过明确输入/输出契约交接，不能复制下游实现细节作为第二套真源。

## 后果

- 需要明确定义产出物格式和存放位置（exec-plans/、docs/、按需 specs/）
- 产出物天然版本化（Git）
- 编排调用只负责交接与消费 contract，不成为下游规则的重复维护点
- 中断恢复变得简单——读取已有产出物即可继续
