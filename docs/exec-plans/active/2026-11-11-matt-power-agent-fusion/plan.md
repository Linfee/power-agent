# Matt 主干融合迁移计划

## 计划用途与当前边界

本计划供人工审阅和后续会话实施，[正式设计](../../../specs/2026-11-11-matt-power-agent-fusion.md)是目标、25 个 Skill 的来源/取舍/验收及退出映射的真源。

**用户已确认按本设计推进本地实施。** 可修改目标 Skill、相关脚本、分发及现行文档，并按设计退出旧资产；不执行 commit、branch/worktree、push、远端 PR/tracker、用户安装目录或秘密/生产配置操作。下述验收入口不代表已运行。

本次使用 exec-plan，是因为用户需要跨会话、人可审的迁移参照。唯一持久执行状态为本地 `.scratch/matt-power-agent-fusion/` 的 `spec.md` 与 `01.md`–`15.md`；该目录为本次忽略的执行 scratch，不是产品运行依赖。session todo 是派生视图；本文件只保留设计、依赖、授权和状态源指针，不另记逐任务进度，也不写远端副本。

## 1. 目标、范围与完成条件

### 目标

以 Matt 的轻量能力组织替换 Power-Agent 现有默认，保留 POD、因果诊断、工程审查/设计、项目知识和自主推进。融合是单一规则来源及干净切换，不是并装两套同义技能。

### 纳入

- 正式设计 S01–S25 的 25 个目标入口、必需 references、可选脚本及其实际消费者。
- 现有 14 个 Power 入口的融合或退出；选定的 Matt promoted 工程/生产力内容及许可署名。
- 调用方式、具名依赖、安装路径、tracker 协议、知识协议的协调。
- AGENTS、两个 README、当前架构/工作方式/开发/设计文档、分发配置、受影响校验脚本与必要回归检查。
- 在真实工具环境中的代表性行为验证与证据记录。

### 不纳入

- Matt 的全部生产力、misc、in-progress、deprecated、personal 或本地未跟踪扩展。
- 新品牌 router、通用 workflow engine、分布式任务锁、评测平台或新增外部服务。
- 对业务项目批量迁移 glossary、已有 tracker、历史 ADR、OKF 数据或用户已安装 Skill。
- 未获授权的 commit、push、PR、issue/label/assignee 修改、merge、worktree/用户文件清理及生产配置变化。

### 完成条件

1. 发布目录中恰好是设计的 25 个入口，当前默认不再暴露六个退役名字或独立 `tdd`/`ask-matt`/Matt setup。
2. 每个目标入口有明确来源、保留判断和实际消费者；只有一份权威判断，具名调用可达，不靠人的逐站接力。
3. 小任务可直接完成；大任务能从一个 tracker 恢复、调度并验收组合行为；已有完整 issue 不被强制重包成 ticket。
4. POD 的默认及例外、review 两维、诊断证据资格、知识/状态分离和副作用授权均有与其对应的行为证据。
5. 所有受影响入口、metadata、脚本、说明、分发与许可一致；通过结构/脚本检查不能替代行为证明。
6. 没有留下不再被消费的过渡副本、旧入口、别名或 throwaway 验证产物。历史材料保留但不再作为当前默认约束。

## 4. 必须同步的消费者与机械检查

### 4.1 目录、发现与调用

- 继续使用 flat `skills/<name>/SKILL.md`，不引入 Matt buckets 后让当前只扫描一层的检查漏掉技能。
- AGENTS 的 Skill 速查与两个 README 都覆盖恰好 25 个目标；当前 invocation checker 只核对 AGENTS，故 README 集合仍须另作一次事实核对，不能假称它已经验证。
- frontmatter `name` 与目录、依赖指针、Codex policy 一起核对。当前 checker 不检查所有这些关系；只补实际缺失且会造成消费者故障的确定性检查，不新建万能 schema。
- reference 可在整包内共享；其相对路径必须从实际 Skill 安装位置解析。目标项目不必有 `skills/` 目录。
- 更新只为旧名称存在的提示和链接，尤其 `scripts/check-description-length.py`、开发指南的 Skill 写作判据链接，以及 Matt 的 setup/tdd 具名调用。
- 不把 description 长度检查误当触发质量评测。当前估算阈值是 115、约对应声明的 110 token 上限；保持简短和可区分，不为凑上限扩写。

### 4.2 分发与许可

现有三个 plugin manifest 相同并指向 `./skills/`，版本为 `0.1.0`；Gemini manifest 只声明 context，不证明安装了 Skill。两个 README 写有 marketplace 安装命令，但仓库没有 marketplace catalog。这是已观察到的配置缺口，**并非已经运行安装得到的失败**。

目标做法：保留 flat 整包目录；同步现有 manifest 的实际支持信息；为保留的 marketplace 路由补 Power 命名的 catalog，而非复制 Matt 品牌。安装验证须针对实际宿主，不能用 JSON 可解析代替“宿主可发现具名依赖”。本地无对应宿主时准确列为未验证，不扩大兼容声明。

许可与来源属于迁入的一部分：

- 保留 Matt MIT 的版权与许可，来源固定到本计划基线，不把其 copyright 当本项目原创署名。
- 保留继承的 superpowers MIT notice；PR 内容采用 HumanLayer/show-me 时保留相应 MIT notice、metadata 和 `pr/CREDITS.md`。
- Fowler/Ousterhout 的概念引用和 Harness Engineering 文章信用保留为文章/著作归属，不自动标为 MIT 软件。
- 现有 Power 声明 MIT 但无根 LICENSE；补齐许可材料时不能猜原创权属或年份。发布前由维护者核准原创署名；这不阻塞本轮设计或已授权的本地融合，不借引入 Matt 的许可替代权属核对。
- 使用实际许可正文与第三方 notice，不以 README 的项目链接代替许可条件。

### 4.3 可复用的检查入口

以下是可复用的检查入口；本轮实际运行与结果见[验证记录](validation.md)。按改动选择，已删除命令不保留空壳。

分发 JSON 用解析器核对，实际 manifest/catalog 用可用宿主的 schema 校验，例如 `claude plugin validate . --strict`；再用隔离安装场景证明发现性。其他宿主不能借用 Claude 的检查结果宣称通过。

当前引用检查器检查本地 Markdown 路径、锚点和识别到的 script 指针，不抓远端 URL，也不验证 JSON/发布行为。默认跳过部分已归档/被取代历史；不显式把整个历史目录传入后要求所有旧名称仍有效，也不为了绿色改写历史。

### 4.4 两类协议的具体变更与保护

**tracker** 按正式设计 §4.6 实施，不另做一轮架构选型：

- M1-N 持有 setup 的三个 backend seed 与项目生成位置；M1-E 只消费同一配置，不各复制一份 tracker 协议。缺配置时，仅依赖 tracker 的动作需要 setup，普通实现/审查不被它阻塞。
- 在本地模板分开 `Kind`、`State`、`Blocked by`、`Owner` 与可选 `Triage`；用同一条目从分诊到认领、完成的场景验证，不再让 `Status` 同时代表不同状态维度。
- 本地任务图由单协调者写调度状态。没有已有原子认领能力的跨会话并发同图工作串行处理，不新增锁服务；唯一标记加 read-after-write 不能成为“保证只有一个执行者”的证据。
- GitHub/GitLab 的版本、tier、native blocking 和退路核对真实契约；同一关系只选 native 或 tracker 正文中的一个真源。验证缺少 `ready`/wayfinder/类别 label 时不会盲目应用不存在的标签或擅自创建。
- 已有 AGENTS 是权威入口时只编辑它，CLAUDE/GEMINI 的转引保持转引。采用 Bundle 时，生成的 `docs/agents/*.md` seed 也适配其元数据，不让 setup 一边生成文档一边触发扫描错误。

**知识维护** 按正式设计 §4.5 和 §8 的资产表实施：

- 保留 dev-docs 下唯一 OKF reference；维护 Skill 相对指向该版本，删除第二副本与唯一服务它的 shared-reference 脚本/当前调用。
- 删除 setup 的两个 CONTEXT 模板及独立 ADR 格式，吸收其有价值判断到唯一所有者；既有用户 CONTEXT、地图和 ADR 一字不因模板退出而批量重写。
- profile 解释项目实际采用的子集；maintenance policy 解释机器语义；完整 OKF 不要求每个文档任务读取。普通 docs 不因安装技能强制启用 Bundle/ledger。
- `bundle_status.py` 只做 plain-index 接受规则的局部调整：无 YAML 是无策略声明，已声明但损坏/非法类型的 YAML 仍报错，symlink 仍拒绝。不借融合改现有策略集合（包括 `generated`）、ledger schema `1.0`、source/scope 指纹语义、报告含义或已有记录。
- 对当前 index 测试拆出新的有效 plain-index 情况，保留非法 YAML/类型边界；保留 37 项测试中的路径/锁/原子写/受控证据/损坏拒写/来源与 ADR 生命周期保护。若其他契约确需变化，先说明实际消费者，不以“没有专门测试”单独证明可以删除。
- 加入或复用一个账本往返场景：未知顶层字段保留、孤立记录报告不删除、scan 零写入；损坏账本 bytes 不变、record 拒绝；有效 scope 与 sources 的既有意义不变。登记仍须真实验证，不为通过结构检查写 fresh。

这些变化不要求新建通用 schema、迁移用户数据库或更改真实项目配置。已部署数据格式若另有变更需要，作为具体新增范围重新确认，不夹带实施。

## 5. 行为验收与成本观察

### 5.1 证据方法

在新的上下文和隔离目标仓库运行自然请求，不预先告诉模型应选择哪份 Skill；分别记录宿主发现、实际加载的正文/依赖和最终结果。只显式调用才能成功的场景，不能用来证明自动发现成功。

可使用用户提供的本机模型入口 `http://127.0.0.1:3425/v1`、`auto/minimax-m3.1-flash`；实施时先确认它能运行本次需要的工具与普通 sub-agent。纯 completion 的答案/自评分不能证明执行、调度、授权或真实 UI。宿主系统指令如覆盖候选政策，记录这个限制，不把宿主结果全归因于 Skill。

沿用现有评测能力或一次性任务驱动，不先造平台。每个场景保留输入、源版本、模型/宿主/工具/授权、实际轨迹、相关产物和结果；不要收集秘密或超出授权的历史。场景可以覆盖多个入口，但“路由经过”不等于该入口的行为验收。

### 5.2 最小场景集合

下面覆盖正式设计的全部 25 个入口；每个入口仍按 S01–S25 的可观察判据核对。合理的实现顺序、工具数量、报告格式和子代理数量不作为硬通过条件。

|场景|覆盖|实际观察与判负条件|
|---|---|---|
|V01 小行为/现成 issue/已有失败|S01、S02、S03、S10|新增行为的红绿重构、已有失败复用、真实修复和两维审查；不建多余票据、不等人工接力、不在本地授权下 commit。只改断言或 suppress 异常判负|
|V02 边界与架构取舍|S04、S14|保留单实现的真实资源边界，拒绝只为 mock 的公开 wrapper；建议请求不改实现；不按 adapter/候选数量判断有效性|
|V03 讨论与知识落盘|S05、S06、S07、S22|只问真实取舍，查证事实；沿用既有 CONTEXT/领域结构，保存值得保留的决定；不双写 glossary，不把普通偏好都建 ADR|
|V04 跨会话任务图|S08、S09、S11、S19|两个独立支路、一个共享集成点和一次交接；真实 blocker 约束调度，恢复从同一个 tracker 取状态，集成行为可用；handoff 不覆盖新状态|
|V05 分诊及读写权限|S12、S25|范围外/重复/缺信息/可执行 issue 的不同处理；read-only 与授权写入分开；既有项目 setup 不覆盖规则，不无条件创建 Matt labels|
|V06 探索地图与一手研究|S13、S15|研究可解的未知自主处理，产品偏好真正交给用户；主张可追一手版本；不强制一决策一会话或 push 研究分支|
|V07 两种原型与实际画面|S16|逻辑状态机和 UI 选项各回答一个问题，运行/真实展示有证据；临时运行处置，重要依据保留；不把演示当生产完成|
|V08 PR 草拟与发布边界|S17|正文对应当前 diff 和真实证据；草拟请求无外部写入；发布分支另在明确授权的沙盒目标验证，不把创建 PR 权限推导为 merge/删分支|
|V09 必要 HITL 与秘密|S18|普通步骤自主完成，敏感输入不泄漏，准确的权限步骤需点位批准；静态语法检查与沙盒运行不冒充真实第三方成功|

|V11 Agent 文本与环境改进|S20、S21|精简后仍保留承重边界和可达 references；无日志的主动 Harness 评估可进行；机械问题优先放检查，不堆禁令或自动改配置|

远端发布、权限授予、安装用户目录等验证只能在明确获授权的具体目标进行。无相应环境/授权时完成本地可验证工作，单列未验证面；控制型工具替身只能证明决策/调用边界，不能记作真实 GitHub/GitLab/第三方服务成功。

### 5.3 “更轻、更自动”的判据

对小任务与含依赖任务，选相同输入、模型、宿主、工具和授权，比较 Matt 基线、Power 基线与候选；没有同口径条件就不报提升百分比。

- 首先看目标是否正确完成、证据是否有效、有没有越权；丢安全或验收换来的短路径不算更轻。
- 正常路径不依赖人工逐站调用；遇到真实偏好/授权缺口才提问，可继续的独立工作继续。
- 记录实际加载的正文与 reference、重复信息、人工往返、状态副本和无价值检查；这些用于解释成本，不要求固定工具步数或模型推理形式。
- 不把 25 个入口逐个加载一遍；不以主文件字数变少但强制更多 references 宣称精简。
- 小样本结论限于实际场景，不从一次成功声称对所有模型都更优。

## 6. 主要风险、恢复与未授权操作

|风险|预防与验证|恢复原则|
|---|---|---|
|两份规则拼接导致相互矛盾|每种判断单一归属，逐项落实删除项；V01/V02/V03 检查实际选择|只修本次候选内容，不修改需求来让结果通过|
|自动化变成权限扩张|动作处核对具体授权；V05/V08/V09 覆盖只读、草稿与精确授权|停止相关副作用，保留已授权本地工作；不得靠新工具绕过拒绝|
|整图局部绿但整体不可用|协调者持有共享契约、写所有权与最终验收；V04 真正运行组合行为|未满足的任务不标 done；不靠汇总子代理声称通过|
|tracker/知识/交接三份状态漂移|唯一状态源，其他文件只放指针/快照用途；恢复重新读取|以当前权威与可核查产物重建运行视图，不覆盖更新的状态|
|裁剪 OKF 丢失验证/来源|区分协议适用，保留有效账本与语义；修改工具有边界回归|不清空/迁移用户数据；格式变更需明确可验证的迁移与单独授权|
|目录退出但残留被打包|flat 目录集合核对 + manifest/实际发现验证|未通过前不发布，不用旧名字 shim 掩盖缺失消费者|
|旧 ADR/README 继续给相反指令|M2 同步当前默认，历史显式取代|不改写历史理由，不让 proposed 文档冒充已实现架构|
|许可/来源遗失|固定源版本、保留实际 notices/credits，核对迁入资产|有来源或权属缺口的发布先停，不猜许可，也不影响无关本地验证|

本地候选可在获授权的隔离分支或工作目录构建；不预先承诺某种 Git 操作。需要回退时先列明本轮文件与用户后续改动，征得具体授权再恢复；不使用 `git reset --hard`、`clean`、批量删目录或覆盖工作区作为默认恢复方法。远端动作一旦发生，恢复另按具体服务和授权处理，不用“可回滚”弱化事前确认。

## 7. 交付记录要求

最终交付简要说明：25 个入口与六个退役入口的实际结果；保留/删除的特殊资产及理由；运行过的结构、脚本、行为与安装检查；发现/修复的本次问题；尚未验证的宿主/外部服务；是否实际 commit/push/发布/修改安装目录。

与行为证据对应的版本、任务输入和产物保留在已约定位置，不把秘密和庞大原始日志塞进 Skill。完成当前交付即可停止，不为下一 Skill 强制产出固定报告 schema。
