## 行为失败、修复与限制

1. Scanner 曾将损坏的 index flow mapping 当作空策略；现拒绝该输入，新增真实来源变化与账本不变回归。Wizard 模板曾在中断时遗留私有临时副本，现由局部 trap 清理；还曾先显示秘密输入提示再关闭终端回显，强制切换时序的 PTY 回归复现了泄露窗口，现先关闭回显并在正常、空输入、EOF、INT/TERM 后恢复。两项脚本修复和相关回归经独立安全复核。
2. Spec 样例曾把不明确的 `words counts` 自行解释为去重数量并写成确定验收。`to-spec` 已明确要求影响可观察结果的合理解释保留未决；复测选择了词频解释并创建票据，仍未确认原需求意图，因此不能宣称该歧义已被可靠识别。
3. 讨论样例中，模型把用户限定的一项选择扩展为多组问题，甚至在收紧指令后的复测仍提出额外问题。`grilling` 已明确优先用户限定的选择，但单次行为不足以证明该问题已解决。
4. 一次模型生成的 wizard 对已有配置行使用 `eval`；在临时文件放入无害命令后，实测它在确认前执行。该生成物不是交付资产；Skill 现要求将配置按不可信数据解析，不执行读取或校验。重生成后对带命令替换的临时配置分别确认和拒绝，标记均未执行，拒绝时原文件不变。该轮脚本的模拟测试还观察到输入提示与关闭回显间的竞态；随后修复共享模板并补充 Skill 约束。最后一次生成运行达到本地时限，未由模型完成验收；它已生成脚本并通过语法检查，父会话另用真实 PTY 测试确认和拒绝：提示出现时回显已关闭，输入未回显，退出后恢复，注入标记均未执行，拒绝时文件不变。这只是特定生成物和测试数据的结果，不能代表真实凭据或权限流程安全。
5. 最初讨论样例位于本仓库下，模型越出样例向上读取真实仓库，并只读查询本机 GitHub 登录状态与仓库信息；没有观察到远端写入。后续样例移到独立临时项目、使用独立 HOME 并明确禁止读取其他项目和远端信息。这是测试隔离失误，不是模型遵守边界的证据。
