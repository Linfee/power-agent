# Skill 与 Harness 设计指南

判断导向 Skill 的目标是让模型在变化的任务中稳定作出好决定，而不是让每次执行看起来一样。当前默认见 [ADR-0010](adr/0010-judgment-oriented-skills.md)。

## 先确认行为缺口

新增或扩写 Skill 前，先问没有它时强模型会稳定做错什么。若答案只是“不一定按我们喜欢的顺序输出”或“没有完整模板”，通常不构成 Skill 价值。

值得沉淀的内容通常属于以下之一：

- 专门领域中不明显、但会改变决策的事实；
- 用户目标与技术选择之间的可靠判断准则；
- 容易被忽略的授权、安全、数据或兼容性边界；
- 什么系统外证据足以接受结果；
- 无法由通用模型稳定恢复的工具、格式或项目知识。

## 写在正确高度

Skill 应具体到能排除坏选择，又保留多条正确路径。优先解释“为什么这个事实承重”和“什么观察会推翻结论”，避免把某次成功执行的步骤固化为普遍剧本。

目标、约束、相关证据、模型自由度和验收是审查维度，不是统一章节。不同 Skill 应按领域自然组织，不为外观一致复制模板。

硬边界与偏好要区分：正确性、安全、授权和外部协议可以使用明确 MUST；工具、顺序、子代理数量、报告样式只有在真实消费者要求时才固定。

批量大小、候选数量、提问节奏和验证频率应说明哪些事实会改变选择，不固化某次成功过程。检查主文件、引用和示例是否使用同一判断边界；尤其核对完成示例是否真的完成行动、引用是否支持主张，以及条件规则是否在另一处又被写成绝对禁令。

## 独立性与组合

一个普通 Skill 应能从用户请求和可获得的普通材料完成自己的目标。它可以使用 sub-agent，也可以消费已有计划、diff 或日志，但不要求另一个具名 Skill 先产生专用状态，也不以“交给下一 Skill”代替结果。

只有知识维护子系统因共同拥有 Knowledge Bundle 而允许具名协作。其他能力的组合由当前任务判断，不写成预绑定链路。

## 渐进披露

`SKILL.md` 保留进入任务必需的判断与边界，专门操作和低频细节按需引用，确定性检查交给脚本。同一次加载内的重复优先合并；跨 Skill 去重仍需保证独立安装可用。比较实际阅读路径，不以主文件行数下降代替成本改善，也不固定先改指针或先内联的顺序。

Description 只负责触发：说明 Skill 帮助解决的独特问题和典型触发，不承载工作流。短而准确比堆叠近义触发词更重要。

## 证据设计

验收必须观察用户实际关心的结果。选择能推翻错误实现的最小证据：真实入口、回归场景、权威来源、UI 操作、性能对照或安全边界测试。不要用文件存在、模板字段齐全、状态变为 `PASS` 或模型自评替代行为证明。

如果一个规则可以稳定由测试、lint、schema、hook 或脚本执行，就把它移出 Prompt。机器边界可以严格；模型判断不应伪装成机器协议。

## 工具设计

工具决定 Agent 的实际能力边界：

- 用清楚、互斥的用途减少选择歧义；
- 参数 schema 直接排除非法输入；
- 返回语义化字段、合理分页和截断说明；
- 错误信息指出可执行的恢复方向；
- 合并天然属于一个原子意图的机械步骤，但不把不同用户决策藏在一个工具里；
- 工具多到淹没上下文时按需发现，而非全部预加载。

精确 schema 是防错机制，不是让所有 Skill 输出结构化状态的理由。

## 维护与 ablation

修改 Skill 时检查触发、正文、references、脚本和仓库索引是否仍一致。通过真实场景或结构检查验证改变的行为；不建立永久评测基础设施，除非有持续消费者。

模型或宿主升级后，可用代表性任务比较基础 harness、当前版本与精简候选。保持模型、工具、输入、权限与验收一致，观察完成质量、越界行为、实际读取、不必要提问和重复验证；保留任务、版本与运行结果。结构通过和规则复述不证明行为改善，少量样本不支持普遍收益结论。

确定无消费者或不再改变行为的文字可以删除；授权、安全与机器协议仍需保留。注意力、措辞和提前完成的因果解释在验证前只是假设，不能据此建立通用流程。对照只在实际改动需要行为证据时运行，不为每次文字修改建立固定评测门禁或平台。
